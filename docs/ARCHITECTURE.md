# Architecture

Allthing is a Farcaster client for reading: it shows Farcaster, and the Worker posts nothing. It is one Cloudflare Worker that serves two things: a static WebAssembly app, and a small JSON API that the app calls once per page. Readers can [sign in with Farcaster](#sign-in), by scanning a QR code with the Farcaster app, to say who is reading, and [like and recast](#liking-and-recasting) with a key their browser keeps. All of it is Rust, except generated glue, a short boot script and a one-line inline script that starts the front page's data request.

```text
 Browser                                   Cloudflare (one Worker, Free plan)            Upstreams
 ───────                                   ──────────────────────────────────            ─────────
 index.html, boot.js        ── static ──▶  Workers Static Assets (free, no Worker run)
 /wasm/allthing-*.wasm      ── Worker ──▶  the module's brotli-11 copy from ASSETS (boot.js falls back to /assets/)
 allthing-*.wasm/.js/.css                  dist/: hashed, cached for a year

 one call per page          ── /api/* ──▶  allthing-worker (Rust, workers-rs)
 GET /api/v1/home …                          rate limit (per IP) → edge cache (Cache API)
                                             → coalesced build → guarded upstream calls  ──▶  Hypersnap /v2 + /v1
                                                                                         ──▶  Base RPC (NS vote)
                                                                                         ──▶  EVM RPCs (wallet activity)
                                                                                         ──▶  farcaster.xyz (votes, channel records)

 images, video, posters     ── direct ──▶  imagedelivery.net, Cloudflare Stream, …  (never proxied)

 sign in (QR code)          ── POST /api/v1/auth/* ──▶  nonce, QR code, signature check,
                                             HMAC-signed session cookie            ──────────▶  OP Mainnet RPC (Farcaster's registries)
                            ── direct ──▶  relay.farcaster.xyz: the channel the Farcaster app answers on

                                           cron, every minute: the indexer
                                             one page of casts             ──────────────────▶  Hypersnap /v2
                                             → D1 allthing-index (casts, rankings); the front page
                                               reads one ranking row for Past month, Past year and All time
```

## Crates

| Crate | Target | Role |
|---|---|---|
| `allthing-core` | native + wasm32 | Everything that can be pure: the data model, normalizing Hypersnap's JSON, ranking, cast text tokenizing, embed classification and image sizes, HLS playlist parsing, provenance decoding, wallet shares, the content spam filter, profile cards, the messages a reader signs and their app key's request (`message`, `app_key`), upstream guards (token bucket, breaker, budget), the API payload types and cache policies. Only `serde`, `serde_json` and `blake3` (a message's hash); no I/O. Most unit tests live here and run against real Hypersnap responses in `tests/fixtures`. |
| `allthing-data` | native + wasm32 | The page builders that assemble each payload, and the Hypersnap and RPC clients behind guards. The runtime is abstracted as a `Host` (clock, HTTP with a timeout, background work), so the same code runs in the Worker and in the browser. |
| `allthing-worker` | wasm32 (Worker) | The `/api/v1` handler: routing, the per-IP rate limit, the edge cache with coalescing, and a `Host` over Workers `fetch`, `AbortController`, `waitUntil` and D1. Its cron handler runs the indexer. `auth.rs` is [sign-in](#sign-in) and `app_key.rs` [endorses readers' keys](#liking-and-recasting); between them they hold the Worker's cryptography (secp256k1 signer recovery and signing, Keccak-256, HMAC-SHA256) and the QR encoder, none of which ships to browsers. A reader's own key is their browser's (WebCrypto's Ed25519). |
| `allthing-web` | wasm32 (browser) | The Leptos app (client-side rendering): routes, pages, components, the media viewer, the HLS player, prefetching and scroll restoration, and liking and recasting with the reader's key (`keys.rs`, `components/writer.rs`). With the `static-host` feature it builds payloads in-process through a browser `Host`. |
| `xtask` | native | `cargo xtask dist` builds `dist/`; `cargo xtask pages` builds the static copy in `dist-pages/`. |

`scripts/build.sh` runs `worker-build` for the Worker and `cargo xtask dist` for the app. The xtask runs `cargo build`, `wasm-bindgen --target web` and `wasm-opt -Oz`, then writes fingerprinted files (`allthing-<hash>.wasm/.js/.css`, `boot-<hash>.js`) and fills them into `web/index.html`. Both WebAssembly builds use `opt-level = "z"`, LTO, one codegen unit and `panic = "abort"`.

## The API

All endpoints are `GET` (`HEAD` also works), except the [sign-in](#sign-in) endpoints under `/api/v1/auth/` and a reader's [scheduled casts](#scheduled-casts), which take same-origin `POST`s. Any other method gets 405, and the API sends no CORS headers.

| Endpoint | Payload | Built from |
|---|---|---|
| `/api/v1/home` | `HomePayload`: a pool of about 100 trending casts, annotations (with the casts they quote) | `feed/trending`, `casts` (quoted casts) |
| `/api/v1/channel?id=<id or parent URL>` | `ChannelPayload`: the channel (with its banner, picture, description, follower and member counts, lead, moderators, pinned cast and link where the Farcaster app has them) and a pool of its casts | `channel`, `feed/parent_urls` (every spelling of the channel's parent URL) and farcaster.xyz `v1/channel` in parallel, then `user/bulk` (lead, moderators, mentions) and `cast` (the pinned cast) |
| `/api/v1/cast?hash=<hash>` | `CastPayload`: the thread (5 levels), the parent, quoted casts, the channel | `cast/conversation`, `cast` |
| `/api/v1/user?name=<username or fid:N>` | `UserPayload`: the profile and a pool of recent casts, with the casts they quote | `user/by_username` (it knows current fnames only; any other name goes through the hub's `userNameProofByName`, then `user/bulk` for the FID it names), `user/bulk`, `feed/user/casts`, and for an account registered before the ID registry moved to OP Mainnet (Nov 2023), the fname server's `transfers?fid=` for when it got its first username, `casts` (quoted casts) |
| `/api/v1/wallets?fid=<fid>` | `WalletActivity`: shares by chain, counts, sources | `user/bulk`, then one batched `eth_getTransactionCount` per chain |

| `/api/v1/home?window=1h\|7d` | the trending pool over the past hour or week, for the front page's time filter (`?t=` in the page URL; 24 hours without the parameter) | `feed/trending` with `time_window` |
| `/api/v1/home?window=30d\|365d\|all` | the top casts of the past month, the past year or all time, ranked from [Allthing's index](#allthings-index-past-month-past-year-all-time), with `index` saying how many casts it was ranked from and how far back they go. | `/api/v1/latest` | `LatestPayload`: the newest ~100 top-level casts, for the front page's "new", with each shard's event cursor | `/v1/events` on shards 1 and 2 (only the events since the previous build's cursors; the newest 1,000 per shard when the previous copy is over 10 minutes old), then `casts?casts=…` once for the new casts and the listed ones' counts, and once more for the casts they quote |
| `/api/v1/search?q=<query>` | `SearchPayload`: casts (with the casts they quote), people and channels | `cast/search` (then `casts?casts=…` to hydrate embeds and counts, and once more for quoted casts), `user/search`, `channel/search` |
| `/api/v1/reactions?hash=<hash>&type=likes\|recasts&limit=10\|100` | `ReactionsPayload`: who liked or recasted, newest first | `reactions/cast` |
| `/api/v1/engagement?likes=<hashes>&recasts=<hashes>` | `EngagementPayload`: who liked and recasted a batch of feed cards, loaded before anyone hovers a count. The hashes are comma-separated, 12 lists in all at most, and are normalized, deduplicated and sorted, so the same lists share one cache entry. Each of its `previews` is exactly what `/reactions?…&limit=10` answers for that cast and kind; a list that couldn't be read is left out, and its popover loads it on hover | `reactions/cast`, once per list, six at a time |
| `/api/v1/replies?hash=<hash>` | `RepliesPayload`: the ten most engaged direct replies | `cast/conversation` with `reply_depth=1` |
| `/api/v1/vote?fid=<fid>` | `VotePayload`: the account's NS vote ([VOTE.md](VOTE.md)) | Base `eth_call` to the opt-in NFT, farcaster.xyz `user-by-fid` |
| `/api/v1/activity` | `ActivityPayload`: Farcaster's [daily active accounts](#daily-active-accounts) as the cron last counted them: the 24 hours to the last whole hour and the 24 before, the 30 days to yesterday, each UTC day's count and messages by kind, and accounts by app (`apps_24h`, with the top apps' accounts), with when counting began, gaps, and how far it has read; the [`/dau`](#daily-active-accounts) page shows it. 503 until the first count (and in the static copy) | the cron's stored payload in D1; no upstream calls |

| `/api/v1/gifs/key` | `GifKey`: KLIPY's app key, for a [signed-in](#sign-in) session's GIF picker (401 without a session, 404 when the `KLIPY_API_KEY` secret is unset; never edge-cached) | nothing |
| `/api/v1/signer` | `Writes`: the account that asks for readers' app keys, where this server [endorses them](#liking-and-recasting) (401 without a session, 404 when the `ALLTHING_FID` and `ALLTHING_CUSTODY_KEY` secrets are unset; never edge-cached) | nothing |
| `/version` (and `/api/v1/version`) | `{"name","version","commit"}` | nothing |
| `POST /api/v1/auth/start` | `Started`: a nonce, the site's domain and address; the nonce also goes into a signed cookie | nothing |
| `POST /api/v1/auth/qr` | `QrCode`: a Farcaster sign-in link (`https://farcaster.xyz/~/siwf?channelToken=…`) or key request link (`farcaster://signed-key-request?token=0x…`), and no other, as one SVG path | nothing |
| `POST /api/v1/auth/verify` | `SignedIn`: the account that signed the message, with the session cookies | one batched OP Mainnet `eth_call` pair (+ 1 fallback RPC), `user/bulk` |
| `POST /api/v1/auth/signout` | `{}`, clearing the session cookies | nothing |
| `/api/v1/scheduled` | `ScheduledList`: the signed-in reader's [scheduled casts](#scheduled-casts), those waiting and those of the past week that went out or didn't (401 without a session; never cached) | D1 |
| `POST /api/v1/scheduled` | `ScheduledCast`: a cast the reader's browser signed for later, kept (or put in the place of one of theirs, `replaces`) once checked | D1 |
| `POST /api/v1/scheduled/cancel` | `{}`: one of the reader's casts that hasn't gone out, cancelled, or one that failed, taken off the list | D1 |
| `POST /api/v1/auth/signer` | `KeyRequest`: for a signed-in session, a `SignedKeyRequest` for the browser's public key, signed by the custody address of Allthing's account and valid for an hour, as the Farcaster app's API takes it | nothing |

Paths are relative to `https://haatz.quilibrium.com/v2/farcaster/` (Hypersnap's Neynar-compatible API). Payloads carry `Meta` (backend, fetch time, staleness) and `Annotations`, shared by every cast on the page:

- **origins**: for each cast, its signer key and the fid of the app that registered that key. The app comes from the signer's `SignedKeyRequest` metadata: `requestFid` from Hypersnap's `/v1/signersByFid`, or decoded from the key's onchain event (`/v1/onChainEventsByFid`) when the key has since been removed. Signers are matched to casts with `/v1/castById` (one cast) or `/v1/castsByFid` (several).
- **apps**: the names and pictures of those app fids.
- **pending**: how many casts are still unattributed. Origins resolve progressively, up to 12 new authors per build, and each payload carries the previous one's origins forward.
- **quotes**: in feeds (home, channels, profiles, search), the casts that the page's casts quote, by hash, so each card shows its quote at once as a small card instead of a link. A build reads the ones it lacks in one bulk `casts?casts=…` request (up to 100), within the build's budget, and carries the previous payload's quotes forward while still quoted. A quoted cast that is spam or a mini app keeps only its author and time, and its card says it is hidden. Quotes that a failed read or the budget leaves out show as links.
- **users**: by fid, what the profile cards of the accounts the page names show beyond their picture and names (`allthing_core::profile::UserCard`): the start of the bio (160 characters, cut between words), follower and following counts, and the registration Hypersnap reports. They come from the user objects Hypersnap sends with each cast (and, on channel pages, with the hosts' `user/bulk` read), so they cost no request, and a build carries the previous payload's cards forward while their accounts are still shown (the author of a carried quote). A profile's own card is its `user`; a person found by search is a whole profile already.

## Edge cache, coalescing and guards

Payloads are cached with the Cache API under `https://<host>/__cache/api/v1/...` keys. Each endpoint has its own policy (`allthing_core::api`):

- **fresh**: served as is;
- **stale**: served at once while one background rebuild runs under `waitUntil`;
- **expired**: rebuilt while the request waits; if that fails, the last good copy is served (stale-if-error).

Unknown users and casts are cached as 404s for 5 minutes.

**Coalescing**: one build per key per isolate. The request that misses starts the build, and the build also runs under `waitUntil`, so it is cached even if that client disconnects. Requests for the same key join it. They wait on their **own** timers and read the result from a shared slot, instead of awaiting the first request's I/O: the runtime would treat that as a hang, and it could outlive the first request. A build older than 30 s is presumed dead and no longer blocks its key.

**Guards** (`allthing_core::guard`, used in `upstream.rs`):

- per-isolate token buckets for each upstream; preloaded popover previews (`/engagement`) never take Hypersnap's below 16 of its 40 tokens, so page builds keep a share;
- a circuit breaker per upstream: three consecutive failures open it for 5 s, doubling up to 5 min, and `Retry-After` is honored;
- 8 s and 5 s timeouts through `AbortController`;
- a budget of 45 subrequests per invocation (the limit is 50), which counts cache reads and writes too. Work beyond the budget is skipped, not failed.

Numbers and the request budget are in [BUDGET.md](BUDGET.md).

**Mini apps and frames are filtered out server-side.** Allthing doesn't run them, so a cast whose embeds or text link to a mini app or frame is dropped:
- **Detection by URL.** `normalize.rs` sets `Cast.mini_app` from URLs: `farcaster.xyz/miniapps/…`, `farcaster.xyz/~/mini-apps…`, `warpcast.com/~/frames…`, `*.neynar.app`. It also uses `fc:frame` or `fc:miniapp` metadata when an API provides it.
- **Detection by page.** Hypersnap returns no embed metadata, so mini apps on their own domains are found by reading the linked page's meta tags (`fc:miniapp`, `fc:frame`, `fc:frame:*`, `of:*`). The Worker reads a few unknown links per build, remembers each verdict per URL, and carries the verdicts in the payload (`Annotations.links`); `thread::mark_mini_apps` then flags the casts. Ordinary casts and quoted casts share the same six-link quota per invocation, one parallel batch. Quoted links are checked before stripping hidden quote content, and locally deferred checks remain eligible on the next build. See [BUDGET.md](BUDGET.md#3-subrequests-per-invocation).
- **Spam.** `spam.rs` flags casts by the owner's content rules: links or embeds on `*.vercel.app`, anything mentioning or linking gig-bot, DEGEN reward or airdrop bait ("Just unlocked my DEGEN rewards", `?degen=1` links), and DEGEN staking promotions (yeetr.fun links or names, "stake your DEGEN"). `normalize.rs` sets `Cast.spam`, and spam goes wherever mini apps go. The rules read only the cast's own text, links and mentions, never anything about the account that posted it.
- **Lists.** The builders drop hidden casts (`Cast::hidden`: mini apps and spam) from home, channels, profiles, search and reply previews (`thread::without_hidden`; a replies preview made from a post payload goes through the same `thread::reply_preview`). A quoted cast that is hidden, in a listing or on a post page, comes without its content (`quotes::as_quote`) and shows as "Quoted cast hidden" (spam: no label is shown) or "Quoted cast hidden: mini app". Like and recast previews, single or batched, list people, not casts.
- **Threads.** `thread::prune_hidden` drops a hidden reply. If it has replies of its own, it keeps the node with its content stripped, shown as "Mini app post hidden" or, for spam, "Post hidden". Allthing never labels a cast or an account as spam on screen; the content rules in `allthing-core/src/spam.rs` only decide what is left out.

Provider quirks stay in `hypersnap.rs` and `normalize.rs`. Examples: channel feeds return twice the requested limit, a channel's `member_count` is its number of distinct casters (`Channel.casters`), user lookups by ENS-style names need a search fallback, errors come back as HTTP 400, and reaction lists come shard by shard, each shard oldest first (`normalize::reactors` orders them by reaction time), one kind per call (`types=likes,recasts` answers with the likes alone). The Farcaster app's channel record is merged in by `normalize::enrich_channel`. The rest of the code sees the `allthing_core::model` types only.

## Allthing's index (Past month, Past year, All time)

Hypersnap ranks trending casts over 7 days at most, and its search ignores dates, so the longer ranges come from Allthing's own index of notable casts, in the D1 database `allthing-index` (the `INDEX` binding; schema in `migrations/`). The logic is in `allthing_core::index`, the run in `allthing_data::indexer`, and the SQL in `crates/allthing-worker/src/index.rs`.

- **The indexer** is the Worker's cron handler, run every minute. Each run reads one page of 100 casts: every fourth run, a page of the past week's trending casts (the ten pages in turn, so each is refreshed about every 40 minutes); the others, the next page back in time of one feed, in turn. Feeds start with seven big channels (`SEED_CHANNELS`), and every author of a cast with 250 points or more joins the queue (at most 120 feeds; feeds read to their start are remembered and not read again). It keeps the top-level casts that are not spam or mini apps and whose points could rank: at least 20, and once a ranking is full, at least its last cast's points. Only those are normalized, which keeps a run's CPU to about one page's parse.
- **Storage.** `casts` holds each kept cast's hash, time and points; storing it again updates its points, and writes nothing if they haven't changed. `rankings` holds each span's top 1,000 casts as one JSON row, recomputed inside D1 by one statement, so the Worker never reads more than a page of casts. A ranking is due again a minute per 50 indexed casts after it was computed, between 5 minutes and 6 hours. `state` holds where each feed is, and the day's D1 usage.
- **Limits.** The indexer estimates its D1 rows read and written and stops reading for the day at 50,000 rows written or 2,000,000 read, half of the free plan's 100,000 and 5,000,000 or less, leaving the rest to the front page. See [BUDGET.md](BUDGET.md#9-the-index-cron-and-d1).
- **Reading.** `/api/v1/home?window=30d|365d|all` reads the span's ranking row, then the page's 100 casts in one bulk `casts?casts=…` call, so counts, text and media are fresh; deleted casts drop out, and spam and mini apps are filtered again. The payload's `index` (`IndexCoverage`) says how many casts the span was ranked from and the oldest one's date, and the page shows it under the time filter. Until a span has a ranking (a new index, or D1 not answering), the payload is the past week's trending pool without `index`, and the page says so. The static copy has no index: its menu leaves these ranges out.
- **Coverage** grows as the feeds are read back: Past month and Past year fill within hours, and All time keeps deepening for days as the queued authors' histories are read. The ranking reflects what has been indexed, which the note under the filter states.

## Daily active accounts

Allthing counts Farcaster's daily active accounts as [SnapMeter](https://github.com/ael-dev3/SnapMeter) does (its `docs/metrics.md`): an account is active when one of its messages was merged into the network, and each account counts once in a window, whatever it did. SnapMeter reads every node's events with a collector of its own; Allthing reads the same canonical events from Hypersnap's public node, in the Worker, as its newest casts are read. The logic is in `allthing_core::activity`, the run in `allthing_data::activity`, and the SQL in `crates/allthing-worker/src/index.rs`.

- **What counts.** A successful `MERGE_MESSAGE` whose type is on SnapMeter's closed list for Snapchain (types 1–8 and 11–21): casts, reactions, follows, verifications, profile changes, username proofs, frame actions, storage lending, keys and channels, and their removals. Pruned, revoked and failed merges, onchain events and blocks don't count, nor do types the list doesn't name.
- **When.** The time of the block that confirmed the message: its `BLOCK_CONFIRMED` event comes first. If that event is on an earlier page, the message's signed time is used instead.
- **The follower** is a cron trigger of its own, every 2 minutes. Each run reads the next page of up to 1,000 events on each shard from where the last run stopped (the cursors are in D1's `state`), and adds each active fid to its UTC hour's and UTC day's set. A first run starts at the start of yesterday, estimated from the newest block at a block a second, so yesterday is counted whole. It catches up about 6 times faster than events come (5.4 to 6.3 times, measured after the first deploy), gaining about 5 hours on the clock an hour: about 5 hours after a deploy just after midnight UTC, up to 10 after one late in the day. A shard whose page can't be read is read again from the same place. If the node no longer has the blocks after a cursor (an outage longer than its retention, about 3 days), the stretch is recorded as a gap.
- **Sets, not rows.** Each hour's and day's active fids are one sorted set (`Fids`), stored as gaps between fids in LEB128 and base64. Days are UTC calendar days. An hour ends on its last second, `(h, h + 1 h]`, as SnapMeter's windows do (`bucket`), so the 24 hours before a time on the hour are exactly SnapMeter's rolling window `(t − 24 h, t]`. A day of 6,000 accounts is about 16 KB, an hour's about 2 KB. So the counts are exact (an account seen on both shards, or in many hours, counts once), yet a run writes 3 or 4 rows. Unions are counted with a bitmap over fids, in linear time. Hourly sets are kept 49 hours and daily ones 30 days, in D1's `activity` table.
- **What it serves.** After each run the follower stores the payload `/api/v1/activity` serves:
  - the 24 hours to the start of the hour in progress (`rolling_to`), and the 24 before them;
  - the 30 days to the end of yesterday, counted once a day while keeping up;
  - each UTC day's count, with its messages by kind.

  A window that wasn't read throughout (before counting began, or across a gap) is left out, and a day that wasn't is marked incomplete.
- **By app.** The key that signed a message says which app sent it: the app whose fid requested the key (`provenance`). The follower keeps each hour's signing keys too, as a set (`Keys`) of `key_pair`s, the account's fid above the key's first four bytes, in `activity` as `k<hour>`. The app of each key is kept in D1's `signer_apps` and never changes, so it is learned once:
  - from the event stream, for a key added onchain while the follower reads (its signed key request names the app);
  - otherwise by looking up the account's active keys (`signersByFid`), or its onchain history for a key removed since: up to 24 accounts a run, 6 while catching up. The keys of the run's own messages go first, then those the last count didn't know.

  Once an hour, D1 counts the past 24 hours' keys by app, `COUNT(DISTINCT fid)` per app in runs that never split an account (`Keys::chunks`), so an account that used two apps counts for each, exactly. Keys whose app isn't known yet are counted apart. While they are more than 1% of accounts, the count is redone every 10 minutes as lookups proceed (after a deploy, about 10 hours). The result (`AppsWindow`) is `apps_24h` in `/api/v1/activity`, and the front page's payload carries it for the apps its casts came from: one D1 read, on the first page's build. The first count comes 24 hours after a deploy, once a whole window of keys has been kept.
- **The page.** `/dau` (`pages/dau.rs`) lays the payload out after SnapMeter's dashboard: the past 24 hours against the 24 before, today so far, yesterday and the past 30 days, the month's UTC days as bars (partly counted days lighter, today apart, and a table of them), the last whole day's messages by kind, accounts by app with the apps' own accounts (the 20 apps with the most, read once a day by the count by app, one `user/bulk` read), and how it was counted: what counts, the windows, the source, since when, and any gaps. Its one request is `/api/v1/activity`, which the inline script starts. On the client bar's cards, an app's count of active accounts links to it. Today and yesterday follow the clock, not how far reading has got: while the cron catches up after a deploy or an outage, the page says how far it has read, marks the day being read as read so far (not as today), keeps today's slot in the chart, empty and unlabelled (the chart's labels, a week apart, count back from the newest day with a bar), and shows what accounts did on the last day read whole, or else on the day being read, said so. The static copy has no count, and says where to find it.

## The browser app

- **Boot.** `index.html` shows a static header and a soft glow while `boot.js` imports the wasm-bindgen glue and instantiates the module. The app then mounts into `#app` and removes the placeholder. `www.allthing.social` is sent to the apex before anything loads.
- **Routing.** Routes: `/`, `/c/<id>` (or `/c?id=`), `/p/<hash>` (or `/p?hash=`), `/u/<name>` (or `/u?name=`), `/channels`, `/search?q=`, `/dau`, `/scheduled`. The query forms keep links from the old static site working. Any other path renders "not found".
- **One request per page.** Each page reads one payload (`api.rs`, with a 5-minute in-memory cache). Sorting (hot, new, top) re-ranks the pool locally (`allthing_core::ranking`). Lists show 25 cards at a time and grow as the reader scrolls. Profiles also read `/wallets` and `/vote`, and so does a profile card when it opens.
- **Favorites and Show less.** On anyone's profile but the reader's own, Favorite makes the account one of the reader's favorites, and Show less has them see less of it (`leanings.rs`, `components/favorite.rs`, `components/show_less.rs`). The two sit together at the profile header's top right, or in a row of their own under the picture and name on a phone. An account is one or the other, or neither: choosing one undoes the other.
  - They are kept in this browser's localStorage (`allthing.favorites`, `allthing.show-less`) and sent nowhere, so they need no sign-in and the static copy has them too. The reader's other tabs follow a change (the `storage` event).
  - In the reader's hot and top feeds, on the front page and in channels, a favorite's cast weighs as if it had four times its points, and carries a small star (not on the account's own profile, where Favorite is). The cast of an account they see less of weighs as if it had half its points, and carries no mark. (`allthing_core::ranking::sorted_for`; in hot, the log of the points moves by the weight's.) A feed on screen re-sorts in place when either changes.
  - New stays in time order, and nothing is hidden: they only move the reader's own feeds, and only theirs.
- **Speed** ([PERFORMANCE.md](PERFORMANCE.md)):
  - posts open instantly from the feed's own data;
  - cards prefetch on hover and in idle time, within caps, and the cards in view have who liked and recasted them preloaded in batches;
  - `nav.rs` restores scroll on back and forward, and makes the whole card open the post; a quoted cast's card inside it opens the quoted cast.
- **Channel pages.** `pages/channel.rs` heads the feed with the channel's banner (a fixed 3:1 box, cover-cropped), its picture over the banner's edge, its name and `/id`, description, follower and member counts, link, lead and moderators (six, then "+N"), and puts the pinned cast above the feed. Each part shows only when the payload has it, so a channel known only to Hypersnap shows its name and how many accounts have cast there.
- **Popovers.** `popover.rs` is one accessible popover (hover or focus after 280 ms, tap on touch, Escape, outside click). `who.rs` uses it for who liked, recasted and replied; a like or recast count has its button as the popover's `lead`, which pointing at opens the preview too but whose click is its own, and a count of 0 is plain text (`idle`). It is also behind the profile's "Wallets" button, which lists every verified address with copy-to-clipboard, and the front page's client bar: once the cron has counted accounts by app, pointing at an app's segment or legend entry (or tapping it, or resting keyboard focus on it) opens its card, with its active accounts in the past 24 hours, its share of the trending casts and a link that shows only its casts. The segments are `aria-hidden` duplicates of the legend's links, which are the ones to tab to. No native tooltips: a browser's `title` tooltip would be drawn over the solid popovers in the system's style, so nothing on a post or in a popover has a `title`. What one would say is read out instead (`aria-description`), or shown, as the post's signing key is in its meta line.
  - **Preloaded previews.** `preload.rs` loads who liked and recasted the feed cards in view before anyone hovers a count: the cards' shared prefetch observer reports them, and each card in view brings its run of six cards, in list order, as one `/api/v1/engagement` batch. `api::preload_engagement` files each list under its own `/reactions?…&limit=10` path in the client cache, dated as the batch. A preview reads that cache synchronously, so its people are there in the frame the popover opens, with no "Loading…" (a resource would resolve a tick later). Limits: [PERFORMANCE.md](PERFORMANCE.md#popover-previews).
  - **Replies previews** come from the post's own payload when hovering the card prefetched it (its thread holds the direct replies, ranked as `/replies` ranks them), and from `/api/v1/replies` otherwise. Putting replies in the batch would have cost a conversation read per cast (10 to 140 KB each, parsed and normalized as full casts) and the replies' link checks for mini apps: for six casts, up to 18 more subrequests and most of a build's 10 ms of CPU, for a popover the hover has usually paid for already.
- **Profile cards.** `profile_card.rs` puts the popover on a profile's own links (`links`): user chips in feeds, quotes and replies, the post's author, the full list of likes and recasts, people found by search and a channel's hosts.
  - Hovering a picture or name for 100 ms, or keyboard focus resting on it, opens the account's card. It stays open while the pointer is over it, closes on leaving, Escape or a click elsewhere, and Tab moves through its links and on, without trapping focus.
  - A tap on a touch screen (`pointerType` "touch") opens the card instead of the profile, and its "View profile" link opens the profile. A mouse click or the keyboard follows the link as before.
  - The bio, counts and join date come from the payload (`notes.users`), or from what this visit already showed of the account (`api::seen_card`; a profile visited knows when the account got its first username). The vote and wallet activity of feed cards' authors are prefetched as the cards come into view (`api::prefetch_card_facts`), and those of the people a likes, recasts or replies preview names once the reader comes into its list (`api::prefetch_row_facts`); a card reads them synchronously (`api::ready`), so it opens complete. Otherwise they load when it opens, through the components the profile uses (`facts.rs`), and the card stays out of sight until they come (`settling`, half a second at most). One that shows before they come keeps its size when they do: its vote row is always there (a 20 px pill, its placeholder, or "Unknown" when the vote can't be read), and its wallet section is one 38 px block whatever it says (`WalletShares`'s `compact`): the bar and one line of legend, two chains by name and "+N" for the rest (the bar's label names them all), or one message, with any note folded into a word on the label's line ("partial", or "earlier counts") that the note explains on hover and to screen readers. The profile keeps the full legend and notes. A card never reads `/api/v1/user`.
  - Clicks in a card are its own (`nav::card_click` skips popovers), and text selected in it keeps it open. Cards in a dialog's list or a channel's header, which clip what overflows them, are placed against the viewport and close when anything scrolls.
- **Media.** `media.rs` turns embeds into a gallery with generated alt text that names the author and quotes the cast. The lightbox is a modal dialog with a focus trap, Escape, arrow keys and pointer swipes, and it returns focus to the tile that opened it.
- **Emoji.** Allthing has a pack of Pepe emoji (`allthing_core::emoji::PACK`): 179, 137 of them animated, self-hosted as WebP under `/assets/emoji/v1/`. `cargo xtask dist` copies them from `web/emoji/v1/`. Each is 64 px tall and at most 150 KB (the 76 added second at most 100 KB), and each animated one has a still, its fullest frame. Each belongs to one of eleven groups (`emoji::Group`), Classics first, in the pack's order. `web/emoji/CREDITS.md` credits each one's maker and source, and gives its terms: why it may be here, by its source's rules. `:pepe_name:` in a cast's text, in any case, becomes the emoji when the name is in the pack (`Token::Emoji` in `allthing_core::text`); any other `:word:` stays text, and other Farcaster apps show the shortcode as written.
  - An emoji is 1.6 em tall in the text, and 48 px when a cast is one to six of them and nothing else.
  - Each is a `<picture>` whose `prefers-reduced-motion: reduce` source is the still. Its alt text is the shortcode, so copied text keeps it, and what Pepe does is read out as its description (`aria-description`), not shown in a native tooltip. Each loads lazily.
  - `/assets/` files are cached for a year as immutable, so a changed image takes a new folder (`v2/`).
  - `web/emoji/CREDITS.md` names each one's source and maker. A unit test keeps the files, the table and the credits in step, reading each size from the WebP header.
- **Stickers.** 32 of the animated emoji are stickers too (`allthing_core::emoji::STICKERS`): 7TV's 128 px GIF of each, unchanged, under `/assets/stickers/v1/`, with a still of its fullest frame.
  - A cast carries a sticker as an image embed of its GIF at `https://allthing.social/assets/stickers/v1/<name>.gif`, so every Farcaster app shows it. GIF is what they all play.
  - Allthing knows its own stickers by that address (`emoji::sticker_of`). `MediaGrid` shows each one apart from the cast's photos: 128 px tall with no frame, loaded from the site itself, and as its still with reduced motion. Its alt text is "Sticker: Pepe …".
  - `web/stickers/CREDITS.md` names each one's source and maker; a unit test keeps the files, their sizes (from the GIF and WebP headers) and the credits in step.
- **Video.** `player.rs` and `video.rs`: an IntersectionObserver loads the master playlist 600 px before a video scrolls into view. Browsers that play HLS themselves get the playlist: Safari, and Chrome (on computers since about version 142; checked with Chrome 155). Videos autoplay when at least 60% visible and pause when scrolled away. They autoplay muted unless the reader turned sound on: playing a video or unmuting one turns it on, and muting one turns it off. The choice is kept in localStorage (`allthing.sound`). Each player notes the muted state it set, so a `volumechange` it didn't cause is the reader's. Before the reader has interacted with the page, browsers refuse sound; the video then plays muted, and its sound comes on at the first tap or key press. Only one plays at a time, and none autoplay with reduced motion, Save-Data or a 2g connection. An autoplaying video's sound badge turns its sound on or off: on a computer it shows, in words, only while the pointer is over the video or keyboard focus is on it; on a phone it is a small speaker in the corner. Elsewhere (Firefox) the Rust player parses master and media playlists (`allthing_core::hls`), picks a rendition by height (720p inline, 1080p in the viewer), and feeds fMP4 segments into separate video and audio `SourceBuffer`s. It keeps 24 s buffered ahead, follows seeks and steps over gaps. Within a run it goes on segment by segment from the last one appended, since a playlist's times can drift from its media's, and it ends the stream once the last segment is in, even where the playlist claims more time than the media holds: a video then loops (inline videos have `loop`) instead of stalling on its last frame. Plain `.mp4` and `.webm` files play natively. YouTube, Vimeo, Loom and Streamable links render as facades that load the provider's iframe only on click; YouTube uses `youtube-nocookie.com`.
- **Threads.** `CommentTree` renders replies recursively. Collapsing animates the row height and marks the hidden subtree `inert`.
- **Design.** `style/allthing.css` is a light theme: warm paper, an indigo accent, cyan and gold for the "portal" details, and Instrument Serif for display type. It adds a faint lattice and glows behind the page and a slowly drifting line under the header. Cards rise in and lift on hover, threads expand, and skeletons shimmer. `prefers-reduced-motion` turns the motion off.

## The static copy (GitHub Pages)

A static host can't run the Worker, so `cargo xtask pages` builds a second variant of the app:

- compiled with the `static-host` feature, `api.rs` answers `/api/v1/...` paths in-process: `allthing_data::Endpoint::from_path` and `build` run with a browser `Host` (`window.fetch`, `AbortController`, `setTimeout`) and a budget of 30 upstream calls per page;
- it preloads nothing from the viewport, popover previews included: they load when they open, as they did before the batches. `/api/v1/engagement` still builds in-process if asked for (its 12 reads fit the budget of 30), and a replies preview still comes from the post that hovering its card built;
- compiled with `ALLTHING_BASE_PATH=/Allthing`, every link, asset and the router live under that prefix;
- `404.html` is a copy of `index.html`, which is how GitHub Pages serves deep links to a single-page app.

Annotations memoized in the page (origins, apps) carry over between pages during a visit. There is no shared cache, so each visitor's browser makes its own upstream reads, and the module is about 30% larger because it carries the builders. The Farcaster app's API sends no CORS headers, so the browser can't read it: channel pages show Hypersnap's data alone, and votes recorded only by the app are unknown. The Cloudflare deployment is the primary one. This copy keeps the project usable from any static host.

## Sign-in

Readers sign in with Farcaster by QR code, through the Farcaster app on their phone ([Sign In With Farcaster](https://docs.farcaster.xyz/developers/siwf/), over Farcaster's AuthKit relay). There is no other way to sign in: no wallet connection, password or email. Signing in only says who is reading: it gives Allthing no key to write with. Liking and recasting take an approval of their own ([below](#liking-and-recasting)).

1. **Start.** The header's "Sign in" button opens a dialog, which asks `POST /api/v1/auth/start` for a nonce. The Worker makes 16 random bytes into a 32-character hex nonce and puts it, with an expiry 10 minutes away, in the `__Host-allthing-siwf` cookie, signed with HMAC-SHA256 (HttpOnly, Secure, SameSite=Strict). It also answers that expiry (`expiration_time`), on its own clock.
2. **Channel.** The browser opens a channel on `relay.farcaster.xyz` with that nonce, this site's domain, its address and that expiry (`expirationTime`), as AuthKit does, so the relay sees the reader's browser, and the message the app signs lapses with the nonce: a device whose clock is wrong can't cut it short. It answers with a channel token and the link the Farcaster app opens.
3. **QR code.** The Worker draws the link as a QR code (`POST /api/v1/auth/qr`, error correction level M), sent as one SVG path that the app renders inline, so browsers ship no QR encoder. It draws only Farcaster's links: sign-in links, [key request](#liking-and-recasting) links, and the farcaster.xyz links writes are [handed to](#handing-writes-to-the-farcaster-app) (`allthing_core::compose::is_handoff_link`). The dialog shows the code alone, with no link that opens the Farcaster app: signing in takes a second device, the phone that scans it.
4. **Approval.** The browser polls the relay's channel status every 1.5 s for up to 5 minutes, one request at a time; a poll that fails is tried again at the next. A hidden page doesn't poll, and polls at once when it is back in view (`visibilitychange`, `focus`, `pageshow`). A code that runs out while the dialog is in view is replaced by a new one, twice, before the dialog offers one. The person scans the code and approves in the Farcaster app, which signs a Sign-In with Ethereum (EIP-4361) message. When the status is `completed`, the dialog shows who approved (the relay's username and picture) and the browser sends the message and signature to `POST /api/v1/auth/verify`. If the Worker can't check it just now (503, when Optimism can't be read, or no answer), the same approval is sent again after 1, 2 and 4 seconds, and then "Try again" sends it again: no new code to scan while the nonce lasts.
5. **Verify.** The Worker checks what `@farcaster/auth-client` checks (`allthing_core::siwf`, `allthing-worker/src/auth.rs`):
   - the message: the statement "Farcaster Auth", chain id 10, exactly one `farcaster://fid/<fid>` resource, this site's domain and address, the nonce in this browser's cookie, and its expiration and not-before times;
   - the signature: the address that signed it (EIP-191 `personal_sign`, recovered with secp256k1 and Keccak-256) is the message's;
   - the signer: on OP Mainnet, in one batched request, the address is the account's custody address (`IdRegistry.idOf`) or one of its auth addresses (`KeyRegistry.keyDataOf`, an added key of type 2).
6. **Session.** The Worker sets `__Host-allthing-session`, `<fid>.<expiry>` signed with HMAC-SHA256 (HttpOnly, Secure, SameSite=Lax, 30 days), and `__Host-allthing-user`, the account's name and picture, which the header reads to show who is signed in without an API call. It is only a label: the HttpOnly cookie is the session. The header's picture links to the account's profile; hovering it, keyboard focus resting on it, or a tap on a touch screen opens the account menu, whose "Sign out" (`POST /api/v1/auth/signout`) clears both cookies. Tabs of the site tell each other when someone signs in or out (a `BroadcastChannel`), and each follows from the cookie they share.

### Writing a cast

Any reader can write a cast, a reply or a quote (`components/compose.rs`): **Cast**, a pill at the top right of the front page's feed and of a channel's (on a phone, a round button floating at the bottom right of those feeds, with notices above it), starts a cast, in the channel on a channel page, and **Reply** and **Quote** under a post or one of its replies start a reply to it or a cast that quotes it. A draft closed unposted is kept for the same cast, reply or quote.

- **With the reader's key** (where [likes and recasts](#liking-and-recasting) are set up), the composer's **Cast**, **Reply** or **Quote** posts it from the browser. Each "@name" in the text is looked up at Hypersnap (`/v1/userNameProofByName`, once a visit per name) and becomes a mention: taken out of the text and listed with its byte offset, as Farcaster stores mentions (`allthing_core::text::split_mentions`); names that are no one's stay as text. The draft becomes a `CastAdd` (`allthing_core::compose::Draft::new_cast`, `message::NewCast`): the text, up to 10 mentions, the GIF and the quoted cast as embeds (two at most), and as its parent the cast replied to or the channel's parent URL, from the channel page's payload. Over 320 bytes it is a long cast, up to 1,024 bytes; the composer counts bytes from 280 and won't post past 1,024. It is signed and handed to the node like a like. A cast that goes out closes the composer, with a notice that links to it; one the network refuses keeps the draft, and says why. A reader without a key yet approves one first, by the same QR-code dialog, over the composer.
- **In the Farcaster app**, for a reader signed out and wherever the Worker endorses no keys (no `ALLTHING_FID` and `ALLTHING_CUSTODY_KEY`, as on allthing.social): **Post in Farcaster** opens farcaster.xyz's compose link (`allthing_core::compose::Draft::compose_url`) with the text, the GIF, a quoted cast's link (`allthing_core::compose::cast_url`), and the channel (`channelKey`) or the cast replied to (`parentCastHash`). On a phone, the link opens the Farcaster app at once; on a computer, the [hand-off](#handing-writes-to-the-farcaster-app) shows it as a QR code for the reader's phone, with the link to farcaster.xyz beside it, and **Done** clears the draft. The reader posts the cast there. There is no clock, since nothing is kept to post later.

**GIFs** come from [KLIPY](https://docs.klipy.com). Its terms require the API and the media to be reached from the reader's browser, never through a partner's server or cache, and results to show in KLIPY's order, in a grid of their own, under a search box whose placeholder is "Search KLIPY". So:
- The browser calls `api.klipy.com` itself, with the app key `/api/v1/gifs/key` hands a signed-in session (from the `KLIPY_API_KEY` secret). It asks for what's trending when the picker opens, then searches once typing pauses for 350 ms. Pages are kept for 10 minutes this visit, so going back to an earlier search asks for nothing.
- Requests use `content_filter=high` and `format_filter=gif,webp`. A tile is the small animated WebP (`sm`, about 120 KB). A cast embeds the medium GIF (`md`), or the nearest size whose link fits a cast's 256-byte embed.
- Without the secret, the key endpoint answers 404 and the composer has no GIF button.

**Emoji** come from Allthing's own pack ([above](#the-browser-app)), so the picker (`components/emoji_picker.rs`) needs no key and asks no one for anything.
- **The button.** A Pepe, before the GIF button, opens the pack under a search box; one picker is open at a time, and Escape closes it before the dialog.
- **Groups.** The pack shows group by group (`emoji::Group`), each under its heading. Above the grid, a bar has a button for each group, with its first emoji as its face: it brings the group's heading to the top of the grid, and the group whose heading has reached the top is marked (`aria-current`). The last groups, which can't scroll that far, stay marked when chosen. With the bar, the grid is shorter by as much, so the picker grows no taller.
- **Search.** The search matches the start of a word, in names first, then descriptions (`allthing_core::emoji::search`), and shows one grid of what it found, without groups; Enter picks the first match.
- **Recently used.** Up to 16 come first, newest first, kept in localStorage (`allthing.emoji`).
- **Motion.** Each emoji shows its still and moves while pointed at or focused (not with reduced motion), and the picker's foot shows the one pointed at with its shortcode.
- **A pick** puts the shortcode in at the caret, or in place of the selection, spaced from the words beside it, and leaves the caret after it (`emoji::insert`, which counts in UTF-16 as a text box does). The composer keeps the caret itself while the text box hasn't focus, since a tap elsewhere can reset an unfocused text box's selection.
- **Closing.** A click or Enter closes the picker and returns to the text, unless Shift is held; a tap on a touch screen leaves it open for another, and doesn't call up the phone's keyboard.
- **Room.** While a picker is open, the text box is two lines tall, so text and picker fit the dialog together.
- **Stickers.** The sticker button, a sticker peeling, opens the picker on its Stickers tab. The composer holds the tab, so the emoji and sticker buttons each say whether the picker shows theirs, and the arrow keys move between the two tabs. The stickers are searched as the emoji are, with up to 8 recently used first (`allthing.stickers`, kept apart from the emoji). A pick attaches the sticker in the GIF's place, as the cast's image embed, and closes the picker: a cast takes one.
- **Emoji reactions.** Farcaster's own reactions are only likes and recasts: the node refuses any other kind. So an emoji reaction is a reply that is one Pepe and nothing else (`allthing_core::emoji::reaction`), which every Farcaster app shows as a reply, `:pepe_name:`. React, after Reply and Quote under a post or a reply (its icon alone on a phone), opens the picker, emoji only, in a popover; a pick goes out at once as that reply, with the reader's key (`Writer::react`), closes it, and says so with a link to the reply. Under a post and under each reply, `components/reactions.rs` gathers the replies that are reactions into chips (`emoji::reactions`): one per emoji, each account counted once, most first, naming who reacted. The reader's own this visit join them, pressed, and a chip they haven't pressed reacts with its emoji too. The replies stay in the thread as replies. Feeds carry no replies, so their cards have no chips.

The secret that signs the cookies is the Worker secret `SESSION_SECRET` ([DEPLOY.md](DEPLOY.md#secrets)); without it, `start` and `verify` answer 503. Sessions are stateless: no store holds them, and changing the secret signs everyone out. Every `/api/v1/auth/` call must be a POST whose `Origin` is the site's own, so other sites can't start, finish or end a sign-in, and its answers are never cached. The static copy has no Worker and so no sign-in; its header says it only reads.

### Handing writes to the Farcaster app

Allthing has no Farcaster account and no custody key of its own: on allthing.social the owner decided against one (and against importing a seed phrase or connecting a wallet), and a [signed key request](#liking-and-recasting) can only be made by an account's custody key. So, for a reader signed out and wherever the Worker endorses no keys, every write goes to the Farcaster app, where the reader does it as themselves (`components/handoff.rs`):

- **What opens there.** A like, a recast or a delete opens the cast (`allthing_core::compose::cast_url`: `https://farcaster.xyz/<username>/<hash's first 8 digits>`, or `~/conversations/<hash>` for an author without a username). A follow or an unfollow opens the profile (`profile_url`: `https://farcaster.xyz/<username>`, or `~/profiles/<fid>`). A Pepe reaction, a cast, a reply and a quote open the composer with the draft ready to post (`Draft::compose_url`).
- **The dialog.** The buttons are where they always are, for every reader: the heart and the recast icon, Follow beside a profile's name, Delete under the reader's own casts (signed in), React and the reaction chips, and the composer's **Post in Farcaster**. Each opens one dialog that names the action ("Like in Farcaster"), says what the app opens and what to do there, and links to it. The link takes focus; Escape, the close button or a click outside closes it, and focus goes back to the button. Opening the link closes it.
- **A computer and a phone.** Where a pointer hovers, the dialog shows the link as a QR code too, for the reader's phone, and the link reads "Open on farcaster.xyz", for the app on the web. The Worker draws the code (`POST /api/v1/auth/qr`), which draws only Farcaster's links, once a visit for each link. On a phone the dialog has no code, and the link, "Open in Farcaster", opens the app; the composer's Post in Farcaster is that link itself.
- **What the page shows.** The buttons aren't toggles there (no `aria-pressed`): Allthing doesn't know what the reader then does in the app, and counts follow when the page is read again. A signed-in reader's Follow says Following when they follow the account (one public read of the node), and offers Unfollow in the app. Signing in isn't needed for any of it.
- **Scheduled casts** need Allthing to post, so there is no clock in the composer and no "Scheduled casts" in the account menu, and `/scheduled`, with nothing waiting, says why.

Where a server does endorse keys (a Farcaster account of its own in the `ALLTHING_FID` and `ALLTHING_CUSTODY_KEY` secrets), a signed-in reader writes from Allthing instead, with a key they approve once ([Liking and recasting](#liking-and-recasting)); a reader signed out still hands off.

### Scheduled casts

A reader who can post from here can schedule a cast, a reply or a quote for later (`allthing_core::scheduled`, `components/compose.rs`, `pages/scheduled.rs`, `allthing-worker/src/scheduled_casts.rs`, `allthing_data::scheduled`). It is signed in the browser like any other cast; the Worker only keeps it until its time.

1. **Picking a time.** The composer's clock, after the GIF button, opens a date-and-time field in the reader's own time zone, which it names, set to the first quarter hour an hour or more ahead, and **Cast** becomes **Schedule**. The time must be a minute to 30 days ahead; the composer says so before anything is signed. The clock again posts it now after all.
2. **Signing.** The browser builds the cast as it would to post it, mentions and all, and signs it with the reader's key, with the chosen time as its timestamp (`Writer::schedule`). It hands the signed message, in base64, and the draft (what the composer had: its text, GIF or sticker, the cast it answers or quotes, its channel) to `POST /api/v1/scheduled`, not to the node.
3. **Keeping it.** The Worker takes it only from a signed-in session, and from Allthing itself (`Origin`). It checks that the message is a cast by the session's account, well formed (its hash is BLAKE3 of its data), for a minute to 30 days ahead (`scheduled::check`), and keeps it in D1 (`scheduled`, `migrations/0005_scheduled.sql`): 25 waiting per reader at most, drafts up to 6 KB. It doesn't check the signature: the node does, when it is given the cast. Farcaster's nodes refuse a message timestamped more than ten minutes ahead, so a kept cast can't go out early, even if someone took it.
4. **Going out.** Every minute, the indexer's cron run first gives the node `submitMessage`, through Hypersnap's guard, up to 5 casts whose time has come, as they were signed, and keeps what the node says: posted; failed, with the node's reason (a key no longer on the account says so, and that editing signs it again with the key the browser has now); or, while the node is busy or down, again the next minute, 30 times at most. A cast goes out within a minute of its time.
5. **The list.** `/scheduled`, in the account menu and linked from the notice and the clock's row, lists the reader's casts waiting, soonest first, with when they go out in the reader's time and how long until; those that didn't go out, with why; and those posted this past week, linked. **Edit** opens the composer with the cast as it was, still scheduled; **Save** signs it again and puts it in the old one's place (a cast edited in the minute it goes out may go out as it was). **Cancel** deletes the kept message, once the reader confirms; a cast that didn't go out can be edited to try again, or removed. Casts that went out or failed are dropped after a week. The list is one request, `GET /api/v1/scheduled`, never cached.

### Liking and recasting

A signed-in reader can like and recast from Allthing, and post [casts, replies and quotes](#writing-a-cast), once they have approved an app key in the Farcaster app (`allthing_core::app_key` and `message`, `allthing-worker/src/app_key.rs`, `allthing-web/src/keys.rs` and `components/writer.rs`). That is how Farcaster's apps write for their users: an app key is an Ed25519 key added to the reader's account, and it signs their messages.

1. **Who can.** The heart and recast icons under every cast are buttons (`aria-pressed`, a hit area about 30 px across, the icon where it was), and none opens the list of who liked or recasted: pointing at an icon or its count previews them, as before, and the preview's "See everyone" or a click on the count opens the full list (on a touch screen a tap on the count, a target of its own, previews them). A reader signed out who clicks one, or any reader where the Worker endorses no keys, likes or recasts in the Farcaster app ([Handing writes to the Farcaster app](#handing-writes-to-the-farcaster-app)). For a signed-in reader, the app asks `GET /api/v1/signer` once, which the browser keeps for an hour, and a click before the answer waits for it. Where the Worker has the `ALLTHING_FID` and `ALLTHING_CUSTODY_KEY` secrets, a click likes or recasts, after approving a key if the reader has none; where it hasn't, the click hands off to the Farcaster app, as a signed-out reader's does. The static copy's icons are pictures.
2. **The key.** The first like or recast opens a dialog. The browser makes an Ed25519 key pair with WebCrypto, unexportable, and keeps it in IndexedDB (`allthing-keys`), one per account. IndexedDB holds the browser's own key object, so the private key never exists as bytes a script could read, and Allthing's servers never see it. A browser without WebCrypto's Ed25519 says so.
3. **The endorsement.** `POST /api/v1/auth/signer` with the public key answers a `SignedKeyRequest`: an EIP-712 signature over (requestFid, key, deadline), in the domain of Farcaster's SignedKeyRequestValidator on OP Mainnet, by the custody address of Allthing's own Farcaster account, valid for an hour. With `ALLTHING_SPONSOR=1`, the account also pays the onchain fee: a second signature, EIP-191 over the first, which the Farcaster app charges to the account in warps. The validator's own `validate()` accepted a request the Worker signed (`eth_call` on OP Mainnet, 19 October 2026).
4. **The request and the code.** The browser hands the endorsement, as it is, to the Farcaster app's API (`POST api.farcaster.xyz/v2/signed-key-requests`), which answers a token and a `farcaster://signed-key-request?token=…` link. The Worker draws the link as a QR code (`/api/v1/auth/qr`, which draws only these and sign-in links), and, as with sign-in, the dialog shows the code alone.
5. **Approval.** The browser polls the request every 2 s (a hidden page doesn't). It shows "Approved" when the reader has approved and, once the Farcaster app has added the key (`completed`), asks Hypersnap for the account's keys (`/v1/signersByFid`) until the new one is listed, for 30 s at most. An approval from an account other than the one signed in is refused, and its key forgotten. A request left when the dialog is closed is kept until its endorsement lapses: the next like shows the same code, and a page load finds it approved if it was meanwhile. Then the like or recast that opened the dialog goes out.
6. **A like.** The browser builds the message as Snapchain's `message.proto` defines it (`allthing_core::message`: `MessageData` with the reader's fid, Farcaster time, mainnet and a `ReactionBody`), hashes it with BLAKE3 (its first 20 bytes), signs the hash with the key, and posts the envelope to Hypersnap's `submitMessage` (`application/octet-stream`), which relays it to Snapchain's validators. The button and its count change at once, and change back, with a notice, if the node refuses. A message that undoes another is dated at least a second later, so it wins. A key the node doesn't know was removed in the Farcaster app, unless it was approved in the last 5 minutes, when the message is sent again after 2, 4 and 8 s: it is forgotten, and the next like asks for a new one.
7. **What the reader liked.** With a key, the browser reads the reader's latest 100 likes and 100 recasts from Hypersnap (`/v1/reactionsByFid`), and on a post page whether they liked and recasted that cast (`/v1/reactionById`). A count read before the reader changed it here is off by one, and is shown with that one added or taken away.
8. **Following, and deleting one's casts.** On anyone else's profile, a reader who can like sees **Follow** beside the name, once Hypersnap has said whether they follow the account already (`/v1/linkById`, one read from the browser per profile view, which needs no key); until then its place is kept, empty. Hovering **Following** offers **Unfollow**. Each is a `LinkAdd` or `LinkRemove` of type `follow` (`message::Body::Follow` and `Unfollow`), signed and handed to the node like a like, dated a second after the one it undoes, and the profile's follower count follows along. Under their own post and replies the reader sees **Delete**, which asks once more in place ("Delete this cast?", with **Keep** focused) and sends a `CastRemove` with the cast's hash (`Body::CastRemove`), showing "Deleting…" meanwhile. The cast then reads "You deleted this cast." wherever it shows in that tab, after a reload too (`sessionStorage`), since cached pages may still carry it for a while.
9. **Off.** The account menu's "Stop liking from this browser", and signing out, forget the key; the reader can also remove Allthing in the Farcaster app. Tabs tell each other when a key is approved or forgotten.

The Worker never holds a reader's key or signs as a reader, and submits to Farcaster nothing but the [scheduled casts](#scheduled-casts) readers' browsers signed; its custody key endorses keys and nothing else. Any signed-in browser can have a key of its own endorsed, so someone could show another person a key request in Allthing's name: the Farcaster app shows that Allthing asks, and whoever approves gives the request's key holder write access to their account. Endorsements last an hour, so such a request lapses quickly; it is the same trust that any app making signed key requests extends to its signed-in users.

## Security and privacy

- **Reads, and a reader's own likes, recasts, casts, follows and deletions**: the Worker posts nothing of its own. On allthing.social, which has no Farcaster account of its own, the reader does them in the Farcaster app ([Handing writes to the Farcaster app](#handing-writes-to-the-farcaster-app)). Where a server endorses keys, they are signed in the reader's browser, with a key they approved in the Farcaster app, and go from the browser to Hypersnap ([Liking and recasting](#liking-and-recasting), [Writing a cast](#writing-a-cast)); a [scheduled cast](#scheduled-casts) is signed in the browser too, and kept by the Worker, which hands it to Hypersnap at its time. Until then its text and draft are in D1, which the operator can read, and a week after. The Worker's exchanges that aren't reads are [sign-in](#sign-in), the endorsement of a key and scheduled casts: their endpoints take same-origin POSTs, and the session is an HMAC-signed, HttpOnly cookie. Every other endpoint accepts only `GET` and `HEAD`.
- **Credentials**: Farcaster and the public RPCs need no key. The key that signs session cookies lives in the Worker's `SESSION_SECRET` secret. The custody key of a Farcaster account of the server's own, which would only endorse readers' keys, would live in the Worker's `ALLTHING_CUSTODY_KEY` secret; allthing.social has none, by the owner's decision. Readers' keys never leave their browsers. KLIPY's app key lives in the Worker's `KLIPY_API_KEY` secret and goes only to signed-in browsers, which must call KLIPY themselves: it is in every request they make to KLIPY, public by KLIPY's design. The optional keyed Solana RPC URL lives in the Worker's `SOLANA_RPC_URL` secret; new wallet payloads omit its transport and parse diagnostics. Previously cached copies are checked at the public response boundary too, retaining their counts and cache lifetimes while removing opaque diagnostics. `/status` reports only its host. The Workers Builds token lives in Cloudflare, never in the repository.
- **Content Security Policy** (`web/_headers`): scripts are self-hosted, with `'wasm-unsafe-eval'` for WebAssembly only. The one exception is `static.cloudflareinsights.com`, for Cloudflare Web Analytics, which Cloudflare injects when it is switched on for the zone. It is cookieless, and turning it off in the dashboard removes the script. Its POST of page timings to `/cdn-cgi/rum`, handled by Cloudflare rather than the Worker, is the only non-GET request a page makes. Frames are limited to the four video providers. `connect-src` allows any https origin, because HLS playlists are fetched from wherever a video is hosted (it also covers Farcaster's sign-in relay, which the browser polls, KLIPY's API, and the Farcaster app's API and Hypersnap, which take a reader's key request and messages). There is no `unsafe-eval` and no framing of the site, and the only inline scripts are the early data request and the speculation rules in `web/index.html`, each allowed by its hash.
- **Links** in casts get `rel="noopener noreferrer nofollow ugc"`. Cast text is tokenized and rendered as text nodes, never as HTML.
- **Abuse**: a per-IP rate limit (`API_LIMITER`, 120 a minute), the caching above, and guards that refuse to send rather than queue. See [BUDGET.md](BUDGET.md).

## Testing

- **Unit tests**: `cargo test` covers the core against recorded Hypersnap responses, link shortening in the app, and the xtask's CSS minifier and fingerprinting.
- **Lints**: `scripts/check.sh` runs rustfmt and Clippy with `-D warnings` for the native and wasm32 targets, and the `cargo deny` license audit.
- **Tooling**: `npm run test:tools` checks the static test server with temporary fixture directories (malformed paths, root boundaries, redirects and deep-link fallback), and the production deployment wait against a local HTTP server (revision matching, transient failures and bounded timeouts). CI runs it before the browser fixtures.
- **Browser regressions**: `npx playwright test '\.fixture\.spec\.ts$'` runs deterministic browser tests against the local build, with API and media responses supplied by fixtures. CI runs these on pull requests and pushes to `main`; new deterministic suites should use the `.fixture.spec.ts` suffix. They exercise the code under review without depending on live data. Failure reports are uploaded for 7 days.
- **Static payloads**: CI also builds the `/Allthing` copy and runs `E2E_PAGES=1 npx playwright test e2e/static-body-limit.fixture.spec.ts e2e/static-metadata.fixture.spec.ts`. These fixtures exercise the browser Host's capped HTML streams, cleanup after read failures, complete uncapped JSON responses, and linked-page metadata filtering with inert fallback text and actual frame declarations.
- **Performance**: `e2e/perf.spec.ts` checks the budget in [PERFORMANCE.md](PERFORMANCE.md); CI runs it against production after each push to `main`.
- **End to end**: `e2e/allthing.spec.ts` runs Playwright against `wrangler dev`, or against production with `E2E_BASE_URL`, using live data. Video playback runs against a small VP9/Opus HLS fixture (`e2e/fixtures/hls`), because Playwright's Chromium cannot decode H.264.
