# Architecture

Allthing is a Farcaster client for reading: it shows Farcaster, and the Worker posts nothing of its own. It is one Cloudflare Worker that serves two things: a static WebAssembly app, and a small JSON API that the app calls once per page. Readers can [sign in with Farcaster](#sign-in), by scanning a QR code with the Farcaster app, by one approval that also lets them [like, recast, cast, reply, quote, follow and delete](#liking-and-recasting) with a key their browser keeps; the Worker holds [scheduled casts](#scheduled-casts) the browser signed until their time. [Messages](#messages-on-spacetimedb) are SpacetimeDB chat and end-to-end encrypted DMs. The Worker also keeps the images and videos readers [attach](#attachments) to their casts, in R2, and serves them at `/m/`. Application behavior and most build/check tooling are Rust. The early-card renderer stays in JavaScript after a measured cold-load comparison; the loader and inline hints start data and WebAssembly downloads; Messages and notification read-state sync share a narrow TypeScript adapter to the official SpacetimeDB SDK. Generated bindings, the official Playwright TypeScript test runner and the Node static-site test server stay at those platform boundaries.

```text

 HTML document routes      ── Worker ──▶  this deployment's ASSETS index.html (no-store)

 /assets/allthing-*.wasm                  immutable static fallback

                                             → coalesced build → guarded upstream calls  ──▶  Hypersnap /v2 + /v1
                                                                                         ──▶  Base RPC (NS vote)
                                                                                         ──▶  EVM RPCs (wallet activity)
                                                                                         ──▶  farcaster.xyz (votes, channel records)

 images, video, posters     ── direct ──▶  imagedelivery.net, Cloudflare Stream, …  (never proxied)
```

## Crates

| Crate | Target | Role |
|---|---|---|
| `allthing-core` | native + wasm32 | Everything that can be pure: the data model, normalizing Hypersnap's JSON, ranking, cast text tokenizing, embed classification and image sizes, HLS playlist parsing, provenance decoding, wallet shares, the content spam filter, profile cards, the messages a reader signs and their app key's request (`message`, `app_key`), a reader's notifications grouped (`notifications`) and monotonic read progress (`notification_state::ReadState`), upstream guards (token bucket, breaker, budget), the API payload types and cache policies, and the rules of readers' attachments (`media`: their types, sizes, quotas, names and ranges). The end-to-end encryption of messages after the X25519 agreement (`e2e`: HKDF-SHA256, XChaCha20-Poly1305). Only `serde`, `serde_json`, `blake3` (a message's hash) and RustCrypto's `hkdf`, `sha2` and `chacha20poly1305`; no I/O. Most unit tests live here and run against real Hypersnap responses in `tests/fixtures`. |
| `allthing-data` | native + wasm32 | The page builders that assemble each payload, and the Hypersnap and RPC clients behind guards. The runtime is abstracted as a `Host` (clock, HTTP with a timeout, background work), so the same code runs in the Worker and in the browser. |
| `allthing-worker` | wasm32 (Worker) | The `/api/v1` handler: routing, the per-IP rate limit, the edge cache with coalescing, and a `Host` over Workers `fetch`, `AbortController`, `waitUntil` and D1. Its cron handler runs the indexer. `media.rs` keeps readers' [attachments](#attachments) in R2 and serves them. `auth.rs` is [sign-in](#sign-in) and `app_key.rs` [endorses readers' keys](#liking-and-recasting); between them they hold the Worker's cryptography (secp256k1 signer recovery and signing, Keccak-256, HMAC-SHA256) and the QR encoder, none of which ships to browsers. A reader's own key is their browser's (WebCrypto's Ed25519). |
| `allthing-web` | wasm32 (browser) | The Leptos app (client-side rendering): routes, pages, components, the media viewer, the HLS player, prefetching and scroll restoration, and liking and recasting with the reader's key (`keys.rs`, `components/writer.rs`). With the `static-host` feature it builds payloads in-process through a browser `Host`. |
| `xtask` | native | Build orchestration, Brotli-11 compression, esbuild CLI/SDK-version checks, metadata and credit audits, attestation key generation, optimizer discovery, fixture phases, npm audit, isolated SpacetimeDB validation and deployment waiting. `dist` builds `dist/`; `pages` builds `dist-pages/`. |

`scripts/build.sh` only bootstraps rustup and the pinned toolchain on images without Rust, then runs `cargo xtask build`. The native build selects the locked tools, builds the Worker, strips its relocations and builds the browser assets. `cargo xtask dist` runs `cargo build`, wasm-split for the interactive app, `wasm-bindgen --target web` and `wasm-opt -Oz`. It writes fingerprinted Wasm, glue, loaders, CSS and HTML, and compresses the optional `.wasm.br` copies in Rust at quality 11, window 24. The shared SpacetimeDB adapter is bundled through the installed esbuild CLI after checking its SDK version. WebAssembly release builds use `opt-level = "z"`, LTO, one codegen unit and `panic = "abort"`.

HTML document routes run through `allthing-worker::shell`: the versioned `ASSETS` binding reads `/index.html`, and the response carries `no-store` for browsers/CDNs plus `X-Allthing-Commit`. It reuses the global security policy from `web/_headers`, including the checked inline CSP hashes. Existing fingerprinted code, styles, fonts and pack assets remain free asset-first requests with immutable caching. Automatic SPA/HTML fallbacks are disabled: absent asset URLs return a no-store 404 rather than an HTML200 cached under an old JavaScript path. Known app routes and unknown document navigations still render the client router. A document invocation adds no API payload read; its separate request cost is in [BUDGET.md](BUDGET.md#1-what-a-page-view-costs).

The CSP-hashed inline `entry-recovery` guard covers the earlier failure where the fingerprinted `boot.js` itself cannot load. Its capture listener reacts only to that script’s resource-load error. A same-origin Resource Timing status of 404 or 410 permits one new module URL with `__allthing_entry_retry=1`, bypassing the failed module-map entry; successful startup adds no requests. Other or persistent failures retain an accessible Reload panel in `#app`, which also prevents a delayed early Home response from drawing inert cards over the error. The guard does not reload automatically, change the document URL, or write reader storage. Browsers without the status expose the manual panel. This narrow pre-WebAssembly JavaScript boundary cannot run in Rust before the Rust app’s loader arrives. A production cold-load trace recorded the same entry URL returning 404 and then 200; it does not establish the underlying CDN cause. The existing Wasm/glue recovery and cold-performance checks remain unchanged.

## Language boundaries

Rust is the default for new application logic and native tooling. Pure shared behavior belongs in `allthing-core`; the interactive app, data layer, Worker and SpacetimeDB module keep their separate Rust targets. Build, filesystem, validation and deployment policy belongs in `xtask`.

The JavaScript early-card renderer (`web/paint.js`) is an explicit measured exception: the owner kept it after it beat the Rust prototype in a [paired cold-load comparison](PERFORMANCE.md#measured-exception-the-javascript-first-card-renderer). The small `boot.js` loader and inline data/preload hints also run before WebAssembly can start. Messages and notification read-state sync retain the official TypeScript SDK adapter and generated bindings; browser tests retain Playwright's official TypeScript runner, browser-side probes, independent protocol oracles and the existing Node static test server (`e2e/pages-server.mjs`). The test server stays after an unresolved pre-mount stall during migration CI, with causality unproven; [PERFORMANCE.md](PERFORMANCE.md#retained-node-static-test-server) records the conservative rollback. Wrangler and esbuild remain platform tools. CSS, SQL, HTML, fixtures and configuration stay in their appropriate formats. Keep exceptions narrow and documented; preserve licensing and measured behavior instead of reclassifying handwritten files to change language statistics.

## Private Library and seen posts

`/library` collects Bookmarks, Likes, Recasts and Seen, with URL-selected tabs, a filter explicitly limited to loaded posts, activity times, bounded Load more, retry without losing the cursor, and Back restoration. Missing upstream casts are reported as unavailable, separately from content-filtered rows; neither an upstream failure nor a private sync failure becomes an empty successful history. Mini apps follow Settings. A bookmark is private Allthing state, not a Farcaster reaction, and needs sign-in but no Farcaster write-key grant. The static copy links to the signed-in site.

Signed-in reading history and bookmarks live in private SpacetimeDB tables (`spacetime/spacetimedb/src/library.rs`), authenticated by the same immutable identity-to-FID attestation as notification state. Only caller-scoped views are exposed: `my_library_state`, membership of at most 100 supplied hashes, and at most 50 activity rows plus a continuation row. Indexed ordered ranges paginate in descending activity time/hash order, without loading an account's full history. Server history has no 30-day expiry or 2,000-post eviction. Likes and recasts are the currently retained Farcaster reactions, paginated through Hypersnap's single-FID hub endpoint and hydrated in ordered batches; removed or pruned reactions are not an archive.

The Rust Library broker shares the notification connection and SDK script, never Messages' credentials, chat subscriptions or DM keys. The Worker advertises `spacetime.library` only with its attestation key available. A missing capability on an older/unconfigured host retains local seen handling. An actual network/server failure is not evidence that a post is unread: a capable signed-in Home waits for authoritative membership before drawing new candidates. Signed-in visits also skip inert early cards, so a fresh device cannot flash a remotely seen cast before the app starts. Anonymous visits retain the measured JavaScript first-card renderer.

IndexedDB `allthing-library-v1` stores per-FID cache rows and a bounded-read durable outbox. Atomic read/merge/write transactions protect acknowledgements and tombstones from stale tabs; writes are considered queued only after transaction commit. Account epochs fence A → B → A and late page/socket responses. Per-post revisions make a later remote remove/mark-unread win over stale offline intent. A global generation and deduplicated clear operation fence old impressions and lost acknowledgements. Clear history keeps bookmarks; individual Mark unread makes a post eligible on a future feed visit. Concurrent conflicts do not silently replay the disconnected device's older decision.

Only front-page `CastList`s opt into recording. Actual mounted cards require one continuous second of at least half their possible viewport exposure in a visible document. Early/inert cards, fetched off-screen rows, quotes and prefetches never count. Account or reset generation changes cancel old dwell timers. Already drawn cards stay in place as reading syncs; future visits, sort/range/tab changes and not-yet-drawn candidates omit seen posts. Kept Home preserves already drawn geometry for Back. Direct posts, profiles, search, threads and Library remain available for deliberate revisiting, subject to the reader's explicit Mute and Block choices, which remove matching content immediately.

The existing `allthing.seen.v1` localStorage cache remains bounded to 2,000 hashes, 30 days and four reader scopes for anonymous/legacy hosts. A signed-in reader's surviving legacy rows are imported once only after metadata and membership have arrived, respecting server clear times and per-post tombstones. Data that had already expired from that old cache cannot be recovered. Storage denial is surfaced for durable private changes rather than claiming they are saved.

## Private Mute and Block

Mute and Block are explicit reader choices, separate from automatic content spam filtering and from the browser-local Favorite/Show less ranking controls. Another account's profile and hover card expose independent toggles; Settings → Muted and blocked accounts provides a handle/FID search and separate Unmute/Unblock actions. Help opens on hover, keyboard focus or a touch press. Pending and failed synchronization are shown with Retry sync. These actions require sign-in, never a Farcaster signing key or a new approval. The public-only static copy has no private controls.

`spacetime/spacetimedb/src/moderation.rs` adds a private `account_filter` table, keyed by `<owner fid>:<target fid>`, with owner and target FIDs, target username matching metadata, independent `muted`/`blocked` booleans and `mute_revision`/`block_revision` counters, and `updated_at`. The owner FID comes only from the immutable, attested `notification_reader` binding. The parameterless `my_account_filters` caller view returns that owner's rows, including false/false tombstones; no base-table or blocked-by view is public. `set_account_filter(target_fid,target_username,kind,desired,expected_revision)` changes only kind 0 (mute) or kind 1 (block), with that field's compare-and-set revision. Invalid/self targets are rejected. Repeating an already settled value is idempotent; clearing a field retains its revision so a stale offline write cannot restore it.

`allthing-web/src/moderation.rs` shares the notification synchronization socket, SDK script and verified private identity. The Worker advertises `spacetime.moderation` with its pinned attestation capability. One additional `my_account_filters` subscription follows all retained choices. Typed, per-FID records and pending intent use an isolated key range in the existing `allthing-library-v1` IndexedDB database; atomic read/merge/write transactions commit intent before it is sent. Per-field revisions merge independently, acknowledgements cannot reintroduce old outbox entries, and newer authoritative revisions supersede stale intent rather than rebasing it over another session's choice. Account epochs fence A → B → A and late storage/socket completions. A stable visibility projection prevents connection-status or outbox bookkeeping from remounting posts and editors. Explicit Library or filter Retry rereads failed local filter storage without discarding saved choices. Storage or connection failure remains visible.

A capable signed-in session waits for the authoritative filter snapshot and local outbox before drawing content, including notifications and badge counts; it cannot assume a new device has no filters. Signed-in inert first cards stay disabled, while anonymous JavaScript early paint is unchanged. Adding a filter hides immediately; removing one reveals content after server acknowledgement. Remote changes also remove already drawn matching content. Filtering is reactive at cast, quote, thread, preview, search and Library presentation boundaries; notification groups and the lightweight badge timestamps use the same rules. A hidden group is removed completely rather than leaking a hidden actor through its count, excerpt or an empty-state hint.

Detached UI retains complete source references too: an open media viewer closes when its source becomes hidden, removing its caption, alt text and media; a composer replaces hidden reply/quote target context with a generic explanation while preserving the reader's editable draft. Saved draft targets carry those references through reload, so Drafts labels cannot reintroduce a hidden target from a shortened excerpt.

Pure matching is in `allthing-core/src/moderation.rs`. Stable FIDs, structured mentions, full cast text, explicit `@handles`, supported Farcaster profile links and normalized reply/recast/quote provenance identify involvement. Compact `References` preserve identities before notifications truncate text or their actor list to five; hydrated quotes are inspected through the existing inline depth. Each reference collection retains at most 512 unique FIDs and 512 usernames, and quote traversal visits at most 128 nodes. Overflow is marked incomplete and hidden while any account filter is active, rather than silently dropping an identity. Recognized identities are not inferred from an arbitrary display name, a plain-text nickname or text in an image; missing upstream identity/provenance cannot be reconstructed. Structured resolved mentions avoid treating the new owner of an old username as the same FID.

Block additionally hides the reader's existing Allthing DM conversation UI and prevents new direct messages in either direction on the server. `send_dm` requires both parties' nonzero verified FIDs, rejects inconsistent immutable reader bindings and recipient key ownership, then checks both account-level block directions before accepting ciphertext. Even the development fallback cannot use an unverified mutable FID claim to evade that check. The rejection is the generic “conversation unavailable,” with no blocked-by list or direction. Existing ciphertext is retained; public-room content and typing are filtered in the reader's UI, not deleted from the database. Decrypted DM text can be checked locally for identifiable mentions; the server does not inspect plaintext.

These preferences govern the reader's Allthing view, not access to public Farcaster data. Public API payloads remain shared and can contain content the private client omits. A block creates no Farcaster protocol write, does not affect another client and does not delete posts or old messages. Publish the additive module with matching bindings and `--delete-data=never` before enabling the Worker capability; preserve the attestation pin and existing notification, Library, chat and DM data.

## The API

All endpoints are `GET` (`HEAD` also works), except the [sign-in](#sign-in) endpoints under `/api/v1/auth/`, a reader's [scheduled casts](#scheduled-casts), the upload of an [attachment](#attachments), a vote in [Allthing's poll](#allthings-poll) and the [presence](#presence) beat, which take same-origin `POST`s. Any other method gets 405, and the API sends no CORS headers.

| `POST /api/v1/media` | `Uploaded`: a signed-in reader's image or video, the body itself, kept in R2: `{"url","type","bytes"}` | D1 1–2, R2 put 1 |
| `POST /api/v1/presence` | `Answer`: how many are [reading Allthing now](#presence), up to 12 of them shown by name, and when to beat again: `{"online","readers","next"}`, for a browser's beat, `{"id","hidden","refresh"}` (404 unless `PRESENCE` is `on`, 503 without `SESSION_SECRET`; never cached by browsers, and kept 30 s in each Cloudflare location) | D1 1 (one batch), and on a location's recount `user/bulk` |
| `/m/<fid>/<id>.<ext>` (not under `/api/`) | an attachment, to anyone: all of it, or the range asked for; 304 for a copy the browser has; `OPTIONS`, a CORS preflight (204) | R2 read 1 |
| `/m/<fid>/<id>.m3u8`, `/m/<fid>/<id>.v.m3u8` | a [remuxed video](#attachments)'s master and media playlists, written from the index kept with its MP4; 404 for a file without one | R2 `head` 1 |

Paths are relative to `https://haatz.quilibrium.com/v2/farcaster/` (Hypersnap's Neynar-compatible API). Payloads carry `Meta` (backend, fetch time, staleness) and `Annotations`, shared by every cast on the page:

- **origins**: for each cast, its signer key and the fid of the app that registered that key. The app comes from the signer's `SignedKeyRequest` metadata: `requestFid` from Hypersnap's `/v1/signersByFid`, or decoded from the key's onchain event (`/v1/onChainEventsByFid`) when the key has since been removed. Signers are matched to casts with `/v1/castById` (one cast) or `/v1/castsByFid` (several).
- **apps**: the names and pictures of those app fids.
- **pending**: how many casts are still unattributed. Origins resolve progressively, up to 12 new authors per build, and each payload carries the previous one's origins forward.
- **quotes**: in feeds (home, channels, profiles, search), the casts that the page's casts quote, by hash, so each card shows its quote at once as a small card instead of a link. A build reads the ones it lacks in one bulk `casts?casts=…` request (up to 100), within the build's budget, and carries the previous payload's quotes forward while still quoted. A quoted cast that is spam or a mini app keeps only its author and time, and its card says it is hidden. Quotes that a failed read or the budget leaves out show as links.
- **users**: by fid, what the profile cards of the accounts the page names show beyond their picture and names (`allthing_core::profile::UserCard`): the start of the bio (160 characters, cut between words), follower and following counts, and the registration Hypersnap reports. They come from the user objects Hypersnap sends with each cast (and, on channel pages, with the hosts' `user/bulk` read), so they cost no request, and a build carries the previous payload's cards forward while their accounts are still shown (the author of a carried quote). A profile's own card is its `user`; a person found by search is a whole profile already.

## Edge cache, coalescing and guards

Payloads are cached with the Cache API under `https://<host>/__cache/api/v1/...` keys. Each endpoint has its own policy (`allthing_core::api`):

- **fresh**: served as is;
- **stale**: served at once while one background rebuild runs under `waitUntil`;
- **expired**: rebuilt while the request waits; if that fails, the last good copy is served (stale-if-error).

Unknown users and casts are cached as 404s for 5 minutes.

A missing or expired first-page 24-hour Home edge copy can start from the public D1 snapshot `home-day-v1` (`pages::home`). A bounded metadata-only scan identifies retained previous data at least 600 seconds old: an edge `miss` can mean an absent entry or a foreground rebuild of an expired one still kept for a day. The normal 60–600-second stale-while-revalidate background refresh still builds from upstream. Malformed, future or oversized previous metadata cannot prove expiry and takes the normal build. The shared copy is used only while younger than the existing 60-second Home freshness limit, with a finite, positive, nonfuture build time matching its payload metadata, no stale marker or indexed-range metadata, and at most 1 MiB of JSON. Its pool is filtered against the current clock's day and future bound. An unchanged pool keeps the exact bytes; a filtered pool is serialized again, without changing or saving the source copy. Either keeps its original age when admitted to the edge cache. A missing, invalid or expired shared copy takes the normal full build. Other ranges, later offsets and private Following never read or save it.

Successful normal first-page Day builds reserve one charged D1 write before annotations and save best-effort under their own invocation's `waitUntil`, so neither a slow nor a failed optional save delays the response. The source timestamp is retained through background scheduling. A conditional upsert keeps a concurrent older build from replacing a newer present snapshot; an impossible future-built stored row can be repaired, judged against SQLite's UTC clock at statement execution rather than before the D1 await. This uses the existing migrated table, never runs schema creation on the request path, and adds no cron or warm-up. Scarce budgets skip optional lookups or saves before taking the normal source's only slot.

The first global build or globally expired copy still has normal upstream latency. Persistence adds a D1 row write to each eligible full build, about 1,440 per continuously active data center per day at a steady rebuild per minute; concurrent isolates and cache failures can exceed that estimate. These share D1's existing daily write ceiling. See [BUDGET.md](BUDGET.md) for the reads, writes and unchanged invocation limit.

**Coalescing**: one build per key per isolate. The request that misses starts the build, and the build also runs under `waitUntil`, so it is cached even if that client disconnects. Requests for the same key join it. They wait on their **own** timers and read the result from a shared slot, instead of awaiting the first request's I/O: the runtime would treat that as a hang, and it could outlive the first request. A build older than 30 s is presumed dead and no longer blocks its key.

**Guards** (`allthing_core::guard`, used in `upstream.rs`):

- per-isolate token buckets for each upstream; preloaded popover previews (`/engagement`) never take Hypersnap's below 16 of its 40 tokens, so page builds keep a share;
- a circuit breaker per upstream: three consecutive failures open it for 5 s, doubling up to 5 min, and `Retry-After` is honored;
- 8 s and 5 s timeouts through `AbortController`;
- a budget of 45 subrequests per invocation (the limit is 50), which counts cache reads and writes too. Work beyond the budget is skipped, not failed.

Numbers and the request budget are in [BUDGET.md](BUDGET.md).

**Mini apps and frames are hidden unless the reader shows them.** Allthing doesn't run them. The Worker marks a cast whose embeds or text link to a mini app or frame (`Cast.mini_app`) and keeps it in feed, profile, channel and thread payloads; the browser leaves it out unless the reader turned on **Show mini app casts** (in the header's Settings panel, available signed in or out, or on a mini app post), and then shows it with a "Mini app · Open in Farcaster" link to the cast in the Farcaster app, which runs it (`crates/allthing-web/src/miniapps.rs`, `Cast::hidden_for`, `thread::prune_hidden_for`). The choice is kept in the browser's localStorage (`allthing.show-mini-apps`), which web/paint.js reads too; it is not synced to the account. Shown quoted mini apps follow the switch in place and carry the same Open in Farcaster link. The feed shows no hidden-mini-app count. The early cards end before a shown mini app cast or quote, whose extra UI the app draws. The default is hidden. Spam is unaffected: it is dropped server-side as before.
- **Detection by URL.** `normalize.rs` sets `Cast.mini_app` from URLs: `farcaster.xyz/miniapps/…`, `farcaster.xyz/~/mini-apps…`, `warpcast.com/~/frames…`, `*.neynar.app`. It also uses `fc:frame` or `fc:miniapp` metadata when an API provides it.
- **Detection by page.** Hypersnap returns no embed metadata, so mini apps on their own domains are found by reading the linked page's meta tags (`fc:miniapp`, `fc:frame`, `fc:frame:*`, `of:*`). The Worker reads a few unknown links per build, remembers each verdict per URL, and carries the verdicts in the payload (`Annotations.links`); `thread::mark_mini_apps` then flags the casts. Ordinary casts and quoted casts share the same six-link quota per invocation, one parallel batch. Quoted links are checked before stripping hidden quote content, and locally deferred checks remain eligible on the next build. See [BUDGET.md](BUDGET.md#3-subrequests-per-invocation).
- **Spam.** `spam.rs` flags casts by the owner's content rules: links or embeds on `*.vercel.app`, anything mentioning or linking gig-bot ("Gig Bot" as two words too), DEGEN reward or airdrop bait ("Just unlocked my DEGEN rewards", `?degen=1` links), and DEGEN staking promotions (yeetr.fun links or names, "stake your DEGEN"). `normalize.rs` sets `Cast.spam`, and spam goes wherever mini apps go. The rules read only the cast's own text, links and mentions, never anything about the account that posted it.
- **Lists.** The builders drop spam from home, the newest casts, channels and profiles (`thread::without_spam`) and keep mini app casts, marked; search and reply previews drop both (`Cast::hidden`, `thread::without_hidden`; a replies preview made from a post payload goes through the same `thread::reply_preview`, and one a popover batch brings is built by the same `replies_previews` as `/replies`, its replies' links checked for mini apps as `/replies` checks them). A quoted cast that is spam, in a listing or on a post page, comes without its content (`quotes::as_quote`) and shows as "Quoted cast hidden" (no label is shown); a quoted mini app comes whole and shows as "Quoted cast hidden: mini app" unless the reader shows them. Like and recast previews, single or batched, list people, not casts.
- **Threads.** The Worker prunes spam (`thread::prune_spam`) and keeps mini app replies; the post page prunes them as the reader chose (`thread::prune_hidden_for`). A hidden reply is dropped; if it has replies of its own, it keeps the node with its content stripped, shown as "Mini app post hidden" or, for spam, "Post hidden". Allthing never labels a cast or an account as spam on screen; the content rules in `allthing-core/src/spam.rs` only decide what is left out.
- **Post pages.** `/p/<hash>` shows the casts a reply answers above it as full cards (`CastCard`, as in a feed: avatar, name, text, media, counts and actions, with their hover cards), root first, each avatar joined to the next by a 2 px line (`components/thread.rs`, `Ancestors`). The line runs under the avatars' centres: a card's avatar is 22 px at 17 px in, the reply's 44 px at 22 px in. A chain of more than three folds its middle behind "Show N earlier", which opens in place (`thread::collapsed_gap`: the root and the last two stay shown). The chain comes in the same payload as the reply, built by the Worker's `pages::cast` (`walk_ancestors`, up to 8 casts read one after another, since each names its parent), spam left out, mini app ones kept and marked for the reader to show or leave out (`thread::chain_in_order`, then the page prunes them as the reader chose). A seen reply that has a parent shows a placeholder card above it until the payload comes, so the chain has room. Casts above a reply that couldn't be read show a note, "Earlier casts in this thread aren't loaded."

Provider quirks stay in `hypersnap.rs` and `normalize.rs`. Examples: channel feeds return twice the requested limit, some channels' newest casts come after a page or two with none on them, each with a cursor for more (`RawFeed::is_empty_with_more`; /veg's after two), which a channel page follows, up to three, before keeping its last good copy; a channel's `member_count` is its number of distinct casters (`Channel.casters`), user lookups by ENS-style names need a search fallback, errors come back as HTTP 400, and reaction lists come shard by shard, each shard oldest first (`normalize::reactors` orders them by reaction time), one kind per call (`types=likes,recasts` answers with the likes alone). The Farcaster app's channel record is merged in by `normalize::enrich_channel`. The rest of the code sees the `allthing_core::model` types only.

## Allthing's index (Past month, Past year, All time)

Hypersnap ranks trending casts over 7 days at most, and its search ignores dates, so the longer ranges come from Allthing's own index of notable casts, in the D1 database `allthing-index` (the `INDEX` binding; schema in `migrations/`). The logic is in `allthing_core::index`, the run in `allthing_data::indexer`, and the SQL in `crates/allthing-worker/src/index.rs`.

- **The indexer** is the Worker's cron handler, run every minute. Each run reads one page of 100 casts: every fourth run, a page of the past week's trending casts (the ten pages in turn, so each is refreshed about every 40 minutes); the others, the next page back in time of one feed, in turn. Feeds start with seven big channels (`SEED_CHANNELS`), and every author of a cast with 250 points or more joins the queue (at most 120 feeds; feeds read to their start are remembered and not read again). It keeps the top-level casts that are not spam (mini apps included, marked, for readers who show them) and whose points could rank: at least 20, and once a ranking is full, at least its last cast's points. Only those are normalized, which keeps a run's CPU to about one page's parse.
- **Storage.** `casts` holds each kept cast's hash, time and points; storing it again updates its points, and writes nothing if they haven't changed. `rankings` holds each span's top 1,000 casts as one JSON row, recomputed inside D1 by one statement, so the Worker never reads more than a page of casts. A ranking is due again a minute per 50 indexed casts after it was computed, between 5 minutes and 6 hours. `state` holds where each feed is, and the day's D1 usage.
- **Limits.** The indexer estimates its D1 rows read and written and stops reading for the day at 50,000 rows written or 2,000,000 read, half of the free plan's 100,000 and 5,000,000 or less, leaving the rest to the front page. See [BUDGET.md](BUDGET.md#9-the-index-cron-and-d1).
- **Reading.** `/api/v1/home?window=30d|365d|all` reads the span's ranking row, then the page's 100 casts in one bulk `casts?casts=…` call, so counts, text and media are fresh; deleted casts drop out, spam is filtered again and mini apps are marked. The payload's `index` (`IndexCoverage`) says how many casts the span was ranked from and the oldest one's date, and the page shows it under the time filter. Until a span has a ranking (a new index, or D1 not answering), the payload is the past week's trending pool without `index`, and the page says so. The static copy has no index: its menu leaves these ranges out.
- **Time windows.** A trending window holds only the casts posted within it, judged by each cast's own time against the Worker's clock, before the page is cut (`TrendingWindow::holds`, the same edges in the browser and early paint). The lower edge is exclusive and the present is inclusive: `now - span < ts <= now`. All time has no lower edge, but still excludes future timestamps. Following and newest-cast responses, including those read from a stored snapshot, also exclude the future, and index rankings cannot let future rows fill their slots. Ingest alone allows five seconds of source clock skew (`may_ingest_timestamp`, an Allthing buffer allowance, not a protocol threshold): the existing 100-cast newest buffer and index may retain those casts, while later dates are discarded before the buffer is cut. A retained cast can become visible when the clock catches up, but overflow or advancing a filtered stateless cursor does not guarantee another chance to serve it; there is no deferred queue. These checks use existing reads; the stored newest-casts fast path parses its payload to validate timestamps and serializes again only when rows are removed, without changing the stored source or its age. Hypersnap's `time_window` has 1 hour, 6 hours, 24 hours and 7 days; it answers 12 hours with its 24-hour list, which is cut to 12 hours. A page can hold fewer casts than a full batch, when the window holds fewer: the list then ends, and the page says so ("Only 3 casts in the past 12 hours.") instead of padding it with older casts. A copy is kept no longer than its window (`api::home_cache`).
- **Coverage** grows as the feeds are read back: Past month and Past year fill within hours, and All time keeps deepening for days as the queued authors' histories are read. The ranking reflects what has been indexed, which the note under the filter states.

## Daily active accounts

Allthing counts unique Farcaster accounts with at least one successful message merge in a window, using [SnapMeter's definitions](https://github.com/ael-dev3/SnapMeter/blob/main/docs/metrics.md). These are accounts, not people or Allthing readers. Its Worker follows the two data shards of [Hypersnap's public event API](https://haatz.quilibrium.com/v1/events). The logic is in `allthing_core::activity`, the follower in `allthing_data::activity`, and the SQL in `crates/allthing-worker/src/index.rs`.

- **Source contract and its limits.** The counter checks the ordered events this Hypersnap node supplies. The endpoint and block metadata are described in the pinned [Hypersnap event API](https://github.com/farcasterorg/hypersnap/blob/bdef7b75c1fdf1c84611abfa6e1457ea6261f8ee/site/docs/pages/reference/httpapi/events.md), [event definitions](https://github.com/farcasterorg/hypersnap/blob/bdef7b75c1fdf1c84611abfa6e1457ea6261f8ee/proto/definitions/hub_event.proto) and [event store](https://github.com/farcasterorg/hypersnap/blob/bdef7b75c1fdf1c84611abfa6e1457ea6261f8ee/src/storage/store/account/block_event_store.rs). Read-only samples on 27 October 2026 matched the declared totals of 147 complete blocks across both shards; 30 sampled Ed25519 signatures verified over the hashes supplied by the node. Those samples establish observed endpoint behavior, not a full-window count, the deployed binary's revision, independently recomputed message hashes or signer authorization. The runtime does not independently attest consensus, detect reorgs or audit the whole network.
- **What counts.** A successful `MERGE_MESSAGE` whose type is on SnapMeter's closed Snapchain list, types 1–8 and 11–21: casts, reactions, follows, verifications, profile changes, username proofs, frame actions, storage lending, keys and channels, including removals. Pruned, revoked and failed merges, onchain events, blocks and unknown message types do not count. The action chart and daily action totals count **message merge events**, not unique message hashes: a shared message can appear on both shards and contribute twice there. Account sets deduplicate the account across messages and shards.
- **Canonical time and complete blocks.** Ascending events must match their requested shard, `id >> 14` block number and consecutive within-block sequence. A block starts with sequence-zero `BLOCK_CONFIRMED`; its declared `totalEvents` includes that confirmation. Its timestamp, declared total and progress are carried across page boundaries. A signed message's timestamp never substitutes for a missing confirmation. A malformed or unsupported page contributes nothing and leaves that shard's cursor retryable; a skipped block or unfinished predecessor records a gap rather than certifying the missing interval. Future block times are rejected. Several consecutive blocks can share one timestamp, so completion at second `T` advances the coverage watermark only through `T − 1`; the first observed second is excluded from the verified start for the same reason.
- **The verified epoch.** Format version 2 uses separate `activity_v2` state and snapshot names, `v2h`/`v2d`/`v2k`/`v2w` set names and `verified_signer_apps` (`migrations/0011_verified_activity.sql`). Legacy rows remain stored and are never retrospectively certified or mixed into the new totals. Invalid saved v2 state fails closed instead of silently restarting; a newly built summary must pass the same evidence validator before publication. Each shard keeps its actual start, completed watermark, cursor, current block timestamp and read/declared event counts. The common start is the later shard start and common completion the earlier watermark; both configured shards must be present. A complete interval requires both shards throughout, no intersecting gap and no unread time. Initial, partial and gapped counts are lower bounds; missing complete windows stay absent.
- **The follower** retains its existing cron trigger, every 2 minutes. Each run reads up to 1,000 events on each shard after its saved cursor. An initial reverse probe estimates a starting block near yesterday; only subsequent canonical events establish the actual verified start. It does not promise that yesterday is covered. A failed shard resumes from the same cursor next run. Retention and event rate determine how much history can be recovered; the node exposed roughly three days in the 27 October sample. The earlier follower caught up 5.4–6.3 times faster than events arrived after its first deploy; that historical measurement is not a v2 runtime measurement or an availability deadline. Complete rolling and by-app counts appear only after a whole qualifying window has been observed.
- **Atomic progress.** A run supplies the exact state it read and claims a fresh, random 128-bit fence inside the existing D1 batch. Every mutable count, reaction, checkpoint and snapshot write checks that fence. A stale concurrent writer cannot change the winner's progress or totals, including when two runs proposed the same revision. The extra claim is a SQL statement and fence-row write in that batch, not another network subrequest.
- **Sets and windows.** Active FIDs are sorted sets (`Fids`), gap-encoded with LEB128 and base64. A window unions account identities, so the same account on several hours or shards counts once; unions do not allocate a bitmap through the largest FID. Daily sets use UTC calendar days; hourly buckets preserve SnapMeter's `(t − 24 h, t]` rolling windows. A 6,000-account day is about 16 KB and an hour about 2 KB. Normally hourly sets remain for 49 hours and daily sets for 30 days. While waiting for an initial shard, retention freezes at the earliest observed start; after an exceptional wait of over 30 days, bounded local expiry records a gap so deleted data can never become a certified zero. These compact FID estimates exclude signing keys, their indexes and retained legacy data; see [BUDGET.md §10](BUDGET.md#10-daily-active-accounts-cron-and-d1).
- **What it serves.** `/api/v1/activity` reads the stored summary. It includes the canonical source URL, verification version, actual verified start and per-shard evidence, plus the last completed rolling hour, its 24-hour and previous 24-hour unions, up to 48 individual hourly counts, the latest 30 daily counts and merge-event mix, and the union of the 30 days to yesterday. A complete window that lacks coverage is omitted; an uncovered hour is `null`, and an incomplete day is marked partial. A partial 30-day union is labelled as such. The summary builder and browser validate source/checkpoint consistency, timestamps and complete-window claims; a version marker alone is insufficient.
- **By app.** An app is the account that requested the signing key. `ExactKeys` stores the full FID and all 32 public-key bytes, rather than a four-byte prefix; `verified_signer_apps` stores the full identity, FID and app, with a FID/app index. Observed onchain registrations can supply attribution directly. Otherwise the follower reads the account's active signers and, for a removed key, its onchain history, matching exact account, key and registration metadata. Missing, malformed, truncated or failed evidence stays **unknown** and retryable. App zero requires an explicit supported no-app registration; absence is never cached as zero. These activity lookups use their own checked source path rather than the looser cast-origin cache.

  At most 24 accounts are selected for lookup per run, or 6 while catching up. `HISTORY = 6` reserves subrequests for onchain paging; it is not a hard six-request cap. The invocation's global 45-subrequest guard still applies. Once a complete 24-hour key window is available, D1 expands its 24 hourly JSON arrays with `json_each` and counts `COUNT(DISTINCT fid)` per app directly. Current-run key-hour rows replace their stored versions in that query. D1 validates canonical, sorted full-identity arrays and requires their global distinct-FID count to equal the independently verified rolling account total before accepting any app result. The query follows immutable attribution inserts in the existing D1 batch, with no extra query round trip.

  The Worker reads only the key hours touched by the current run and receives aggregate counts plus at most 400 unresolved identities, about 32 KB of identity JSON. It does not decode, union or serialize the full 24-hour key window. The total number of accounts with unresolved keys is counted across the whole window, independently of that bounded lookup backlog. An account using two apps counts for each; unresolved keys produce app lower bounds and a known-share note. Windows normally recount hourly, or every 10 minutes while over 1% of accounts still have unresolved attribution. No fixed warm-up time is promised. A first-page Home payload carries only verified app counts for the apps it shows, using its existing D1 read.
- **For account lists.** `Index::apps_of` queries full identities through the verified table's FID/app index; results are FIDs and app FIDs, not encoded key pairs. `Index::active_week` reads the latest kept `v2w<day>` union of seven complete days, only once all seven have verified coverage. The existing optional two-read interface remains; no page asks yet.
- **Emoji reactions, for listings.** The same checked event page extracts replies containing one Pepe, plus the casts removed and reactions revoked or pruned. The fenced save updates `reactions` (reply hash, target cast, emoji, FID and block time), removes withdrawals and entries older than 400 days. Listing builds keep their existing single query and `notes.reactions`; the static copy has none. This does not reconstruct reactions from before observation began.
- **Navigation and the page.** DAU is a persistent main-navigation link on desktop and phones, named “DAU, daily active accounts” for assistive technology, built with the route helper and marked as the current page. The inert boot header reserves the same space. A two-row header through 800 px keeps navigation, presence, search and account controls usable; Library retains its existing phone breakpoint. The static `/Allthing` copy links to its own `/dau` route, which points to allthing.social for counts.

  `/dau` (`pages/dau.rs`) makes one `/api/v1/activity` request, started by the inline loader. Its near-top coverage card links Hypersnap and shows when the snapshot was updated, the verified start, common completion and each shard's completed watermark and current block progress, with expandable cursors. Snapshot update time records the count attempt and can advance after a failed source read; common and per-shard completion timestamps establish how far events were verified. Legacy, future or incoherent proof suppresses the meter, charts and app figures and offers the provider and JSON links. Explicit waiting shard records show coverage building. Partial tiles use `≥` and explain lower bounds. The meter, 48-hour/7-day/30-day charts, keyboard/touch readouts and tables retain their existing behavior; today and yesterday follow the clock while catch-up progress is shown separately. Definitions distinguish unique account counts from merge-event totals and explain the provider scope.

## The browser app

- **Boot.** `index.html` shows a static header and a soft glow while `boot.js` imports the wasm-bindgen glue and instantiates the module. The app then mounts into `#app` and removes the placeholder. `www.allthing.social` is sent to the apex before anything loads.
- **The front page's first cards, before the app.** The page's data usually comes seconds before the WebAssembly on a slow line, so `paint.js` draws the cards the app draws first from it, under the boot screen's header: the app's order (hot or top, with the reader's favorites and those they see less of) and its markup (a GIF's tile marked by `is_gif`'s rules, mirrored as `isGif`), inert and hidden from screen readers, and only from a fresh answer. A quote shows as the app's quote card, to the depth the app shows them (`QUOTE_DEPTH`), its single images sized like the card's own. It stops at a card it can't draw as the app does (a video, a sticker, a single image it can't size), and, narrower than 1280 px, after the fourth card, where the app puts its poll, and draws nothing for new, an app's casts, the longer ranges or any other page. A single image's tile has its box before the image comes, from Cloudflare Images' description of it, which the app's tile takes too; the images wait for the WebAssembly. Once mounted, the app is drawn hidden under them, and takes their place when its own cards are drawn (`boot.rs`, `hand_over`), in the same boxes and without their entrance again; leaving the front page, its error, or 4 seconds do so too. If the app can't load, `boot.js`'s panel replaces them. Numbers: [PERFORMANCE.md](PERFORMANCE.md#1-reuse-what-the-page-already-has).
- **Code loaded when used.** Parts of the app that few visits use are WebAssembly modules of their own, fetched the first time they're used: the DAU page's dashboard, the composer's pickers, bar and posting (its frame and text box stay, so it opens at once), React's Pepe picker, signing in (from the relay's code to the Worker's check), the list on /scheduled, the Messages page's conversations and threads (fetched with the page, and as the account menu's Messages is pointed at, touched or focused), writing (signing and sending, approving a key and reading the one kept, and looking on the node for a hand-off), which a signed-in reader's page fetches as soon as it knows who they are, and the pages of a post, a profile, an account's followers or following, a channel, search, the channels and the reader's notifications: a post's fetched a few seconds after the app starts and as a card is pointed at, the others as a link to them is pointed at, touched or focused, and any of them with the app when a visit starts on one (`index.html`'s `early-parts`). A function marked `#[wasm_split]` is the way into a part, and its code is fetched as soon as it's likely wanted: with the page's data for the DAU page, and as a Cast, Reply, Quote, React or Sign in button is pointed at, focused or pressed (`compose::warm`, `Popover`'s `on_warm`, `signin::warm`). `split.rs` shows a part once its code has come. When it can't come (as after a deploy, which removes the previous version's files), a page loads again, once, a part of a page says so in its place, with Reload, and a signed-in reader's writes go to the Farcaster app. How it's built and what it saves: [PERFORMANCE.md](PERFORMANCE.md#code-loaded-when-used).
- **Routing.** Routes: `/`, `/c/<id>` (or `/c?id=`), `/p/<hash>` (or `/p?hash=`), `/u/<name>` (or `/u?name=`), `/u/<name>/followers`, `/u/<name>/following`, `/channels`, `/search?q=`, `/dau`, `/scheduled`, `/messages` (with `?room=general`, `?to=<fid>` or `?new=1`), `/notifications` (`?tab=mentions` or `replies`). The query forms keep links from the old static site working. Any other path renders "not found".
- **One request per page.** Each page reads one payload (`api.rs`, with a 5-minute in-memory cache). Sorting (hot, new, top) re-ranks the pool locally (`allthing_core::ranking`). Lists show 25 cards at a time and grow as the reader scrolls. Profiles also read `/wallets` and `/vote`, and so does a profile card when it opens. A signed-in reader's bell reads their notifications besides, when the app starts and every 3 minutes while it's in view ([Notifications](#notifications)).
- **A signed-in reader's front page.** Signed in, `/` has two tabs, as X's, above the sort tabs (`pages/home.rs`, `FeedTabs`; `allthing_core::following::Feed`): links, each 44 px tall, the chosen one with `aria-current="page"`, keeping the time range and client filter and selecting the destination tab's default sort: hot for For you, new for Following. An explicitly chosen sort stays selected when the time range changes. **For you**, the default, is the trending pool with its time ranges, as signed out, with the casts of the accounts the reader follows lifted in hot and top (`allthing_core::ranking::Leanings::followed`, `FOLLOWED_HOT_WEIGHT` 20 and `FOLLOWED_TOP_WEIGHT` 6, times a favorite's, none for one seen less of); its new is everyone's newest casts, in time order. Whom they follow is the authors of their last Following page, kept in this browser (`followed.rs`) and renewed in the background at most every 10 minutes (see [BUDGET.md](BUDGET.md)). **Following** (`?feed=following`) lists only the casts of the accounts they follow, read from `/api/v1/following`: hot and top ranked as the trending pool (`sorted_for`), with favorites and those they see less of, new newest first, and the time range applied to what is loaded; older pages come as they scroll (`?cursor=`). Automatic Following reads stop once a nonempty source page is older than the chosen range, retaining its cursor so widening the range resumes even when every visible row is filtered. There are at most ten payloads per visit until the reader presses Load more posts, which permits ten more; empty source pages count toward the same limit. Old `?feed=everyone` links open For you. Signed out, and in the static copy, there are no tabs: the front page is For you without the lift. `paint.js` draws only anonymous For you cards; signed-in feeds wait for authoritative seen-post membership before showing new cards.
  - **Few to rank.** Where the reader follows few accounts that cast lately (fewer than 30 top-level casts in Hypersnap's first page), the Worker reads its next page too. Following lists only theirs: an account following no one, or few who cast lately, sees a short list, or the note that no one they follow cast lately, and For you for everyone's.
  - **Whose.** The Worker reads whose feed it is from the session alone, keeps it at the edge per account and page (a minute fresh), and answers `private, no-store`; the app keeps it a minute and forgets it when someone else signs in (`api::forget`). A session that has ended (401), or a Worker without the endpoint while a deploy rolls out (404), shows everyone's feed.
  - **Before the app.** `index.html`'s early fetch asks for `/api/v1/following` when the user cookie names a reader and the URL has `?feed=following`, and `/api/v1/home` (or `/api/v1/latest` in new) otherwise. `paint.js` paints anonymous For you only. Signed-in For you and Following wait for the app and its authoritative seen-post membership; the early fetch still supplies their page data.
- **Favorites and Show less.** On anyone's profile but the reader's own, Favorite makes the account one of the reader's favorites, and Show less has them see less of it (`leanings.rs`, `components/favorite.rs`, `components/show_less.rs`). The two sit together at the profile header's top right, or in a row of their own under the picture and name on a phone; the reader's own profile has neither, and its [Cast](#writing-a-cast) is the header's, or floats on a phone. An account is one or the other, or neither: choosing one undoes the other.
  - What each does shows under the two buttons, in Allthing's style (`favorite::Hint`): when the pointer rests on it, when keyboard focus is on it, and for 3 seconds after a press, as a phone can't hover. It's also the button's description. No native tooltip: one shows late, in the system's style, and never on a phone. Their hover styles apply only where a pointer hovers, so on a phone a button just turned off doesn't keep the look of one that's on.
  - They are kept in this browser's localStorage (`allthing.favorites`, `allthing.show-less`) and sent nowhere, so they need no sign-in and the static copy has them too. The reader's other tabs follow a change (the `storage` event).
  - Profile cards have them too (`components/profile_card.rs`): one row of two small buttons, 28 px tall, between the card's counts and its facts, on anyone's card but the reader's own. They are the profile's buttons and its state: pressed in a card, they show pressed on the profile and in the reader's other tabs, and the other way round. In a card a press says what it did to screen readers ("@alice's casts rise in your feeds") instead of showing the hint, so the card keeps its size.
  - In the reader's hot and top feeds, on the front page and in channels, a favorite's cast weighs as if it had 25 times its points, and carries a small star (not on the account's own profile, where Favorite is). Show less first omits a stable approximately 90% of that author's feed candidates, then weights the remainder at 1/100 in Hot and Top, with no mark. Selection hashes the FID and full post hash, so it does not reshuffle across pages, refreshes or sorts; it overrides Favorite and Followed boosts. A percentage describes larger samples: a small batch may retain no posts from that account. In top a cast counts its points plus one, so one nobody has reacted to yet moves too; in hot the log of the points moves by the weight's once for each day the list spans, from its oldest cast to its newest (`span_days`, a day at least), as if the cast were 17½ hours newer or older for each. Over many days hot is nearly time order, so a move of fixed hours would barely move a cast there; this way a cast moves as far through a quiet channel's week of casts, or the past week's front page, as through a day's (`allthing_core::ranking::sorted_for`, `FAVORITE_WEIGHT`, `SHOW_LESS_WEIGHT`). On a list of a day or of a week, a typical account's casts go from its middle to its first or last few places: the unit tests and `e2e/leaning-strength.fixture.spec.ts` measure it. The front page ranks each page of 100 casts as it comes, so that cards already shown stay where they are, and a cast goes as far as the end or the top of its own page. A feed on screen keeps its order when either changes in its own tab, so the cast under a profile card stays under it: the change applies when the feed is next loaded, sorted or filtered (`Leaning::for_list`), and a favorite's star shows at once. A change made in another tab re-sorts it in place.
  - On Home, Following and channels, New stays strictly chronological within its selected time range after Show less sampling; Favorite and Followed boosts never change that order. The time selector stays available in every sort. Direct profiles, search and post pages remain available in full.
  - Show less changes only this reader's feed candidates and can be undone with the same button. It does not mute notifications, hide mentions, remove public posts or block communication; private Mute and Block provide those separate controls. Preferences remain in this browser and sync with its other tabs. Anonymous early cards wait for the Rust filter when Show less preferences exist, avoiding a flash of candidates the app will omit; ordinary early paint retains the measured renderer.
- **Speed** ([PERFORMANCE.md](PERFORMANCE.md)):
  - posts open instantly from the feed's own data;
  - cards prefetch on hover and in idle time, within caps, and the cards in view have who liked and recasted them, and their replies, preloaded in batches; a link to a post or a channel fetches that page's data as it's pressed or touched, or once a mouse has rested on it for 100 ms (`split.rs`; not a profile's link, whose press opens the account's card);
  - `nav.rs` opens the page a link or a card leads to once the press has painted, not in the press's own task (`go`, and `InstantLinks` for every link the router would follow). A page with nothing to show yet (no data kept, nor a cast or person a page showed) waits for its data, and a page whose code is its own for that code, 250 ms at most, with the page left on screen and the press held; past that it opens with its placeholders. What's drawn anew (a post, a list's cards) rises a few pixels into place, readable from its first frame; there's no view transition, which delayed the next page by hundreds of milliseconds ([PERFORMANCE.md](PERFORMANCE.md#3-client-side-navigation)). It restores scroll on back and forward, and makes the whole card open the post; a quoted cast's card inside it opens the quoted cast, and media opens the media viewer.
  - `kept.rs` keeps the front page while another page shows: drawn once, it's taken out of the page and put back as it was, so Back (or Home) shows it at once with its cards where they were, where drawing them again took 110 to 260 ms on a slow phone. Each card keeps the height it had: out of view, a card is laid out at the height it last had in view (`content-visibility: auto`), which it forgets out of the page, so put back without it the page was 1,600 to 2,800 px taller in its first frame. One shared `ResizeObserver` remembers mounted Home cards' exact content and border sizes after layout. Leaving Home verifies both current border dimensions and the card's style/class fingerprints before reusing a content height; missing or changed sizes, transforms and unsupported observers retain the exact CSS measurement fallback. All height reads precede animation and retention writes, and disposing a card removes its observation and cached size. Out of the page it reads the address it last showed, so another page doesn't redraw it, and its popovers close; out for over 5 minutes, it's drawn anew.
- **Channel pages.** `pages/channel.rs` heads the feed with the channel's banner (a fixed 3:1 box, cover-cropped), its picture over the banner's edge, its name and `/id`, description, follower and member counts, link, lead and moderators (six, then "+N"), and puts the pinned cast above the feed. Each part shows only when the payload has it, so a channel known only to Hypersnap shows its name and how many accounts have cast there.
- **Popovers.** `popover.rs` is one accessible popover (hover or focus after 280 ms, tap on touch, Escape, outside click). A panel a tap or a click opened, and that the pointer leaving doesn't close (any on a touch screen, and React's picker), is dismissed lightly: the first press outside it only closes it, in the window's capture phase, before the card under it can open its post, a link can be followed or another panel can open; a modal dialog opened from the panel keeps its own presses. One the pointer opened closes as it leaves, and a click elsewhere does what it does. `who.rs` uses it for who liked, recasted and replied; a like or recast count has its button as the popover's `lead`, which pointing at opens the preview too but whose click is its own, and a count of 0 is plain text (`idle`). It is also behind the profile's "Wallets" button, which lists every verified address with copy-to-clipboard, and the front page's client bar: once the cron has counted accounts by app, pointing at an app's segment or legend entry (or tapping it, or resting keyboard focus on it) opens its card, with its active accounts in the past 24 hours, its share of the trending casts and a link that shows only its casts. The segments are `aria-hidden` duplicates of the legend's links, which are the ones to tab to. The legend is one line, scrolling sideways where it doesn't fit, so the feed under it doesn't move as apps are read; its cards are placed against the viewport, so the line doesn't clip them. No native tooltips: a browser's `title` tooltip would be drawn over the solid popovers in the system's style, so nothing on a post, in a popover or around one has a `title` (a title on an element a panel sits inside, like the client bar, shows over the panel too). What one would say is read out instead (`aria-description`), or shown, as the post's signing key is in its meta line.
  - **Preloaded previews.** `preload.rs` loads who liked and recasted the feed cards in view, and their replies, before anyone hovers a count: the cards' shared prefetch observer reports them, and each card in view brings its run of six cards, in list order, as one `/api/v1/engagement` batch, from the counts each card carries (`data-likes`, `data-recasts`, `data-replies`). Then the next run brings its batch once its first card is less than a screen below the viewport and all its cards are on the page, so the reader finds it loaded. `api::preload_engagement` files each list under its own `/reactions?…&limit=10` path in the client cache, and each replies preview under its own `/replies?hash=…` path, dated as the batch. A preview reads that cache synchronously, so its people or replies are there in the frame the popover opens, hovered or tapped, with no "Loading…" (a resource would resolve a tick later). Limits: [PERFORMANCE.md](PERFORMANCE.md#popover-previews).
  - **Replies previews** come with the batch for cards with 1 to 100 replies: the Worker reads each card's conversation (`reply_depth=1`) and builds its preview as `/replies` does, the ten most engaged direct replies without spam or mini apps, by the same code (`replies_previews`), the replies' links checked in one batch of the build's six link pages. Hypersnap sends every direct reply of a conversation, about 1 KB a reply, parsed as whole casts, so a batch parses replies only in what its lists leave of its share of CPU, the smallest conversations first ([BUDGET.md](BUDGET.md#3-subrequests-per-invocation)). A card the batch has no replies for (more than 100, too long to fit, or a read that failed) takes them from the post's own payload when hovering the card prefetched it (its thread holds the direct replies, ranked as `/replies` ranks them), and from `/api/v1/replies` otherwise.
- **Profile cards.** `profile_card.rs` puts the popover on a profile's own links (`links`): user chips in feeds, quotes and replies, the post's author, the full list of likes and recasts, people found by search and a channel's hosts.
  - Hovering a picture or name for 100 ms, or keyboard focus resting on it, opens the account's card. It stays open while the pointer is over it, closes on leaving, Escape or a click elsewhere (on a touch screen, the first tap elsewhere only closes it), and Tab moves through its links and on, without trapping focus.
  - A tap on a touch screen (`pointerType` "touch") opens the card instead of the profile, and its "View profile" link opens the profile. A mouse click or the keyboard follows the link as before.
  - The bio, counts and join date come from the payload (`notes.users`), or from what this visit already showed of the account (`api::seen_card`; a profile visited knows when the account got its first username). The vote and wallet activity of feed cards' authors are prefetched as the cards come into view (`api::prefetch_card_facts`), and those of the people a likes, recasts or replies preview names as it opens (`api::prefetch_row_facts`), the name pointed at or touched first (`api::prefetch_facts_first`); a card reads them synchronously (`api::ready`), so it opens complete. Otherwise they load when it opens, through the components the profile uses (`facts.rs`), and the card stays out of sight until they come (`settling`, half a second at most). One that shows before they come keeps its size when they do: its vote row is always there (a 20 px pill, its placeholder, or "Unknown" when the vote can't be read), and its wallet section is one 38 px block whatever it says (`WalletShares`'s `compact`): the bar and one line of legend, two chains by name and "+N" for the rest (the bar's label names them all), or one message, with any note folded into a word on the label's line ("partial", or "earlier counts") that the note explains on hover and to screen readers. A profile's header keeps its height the same way as its vote and wallets come, each from its own endpoint after the profile: its vote row is always there, and its wallet section is one block whatever it says, its bar and one line of legend, as many chains by name as the line has room for (four, two or one, room kept for the longest names) and "+N" for the rest, with any note behind a word at the line's end ("partial: why", or "earlier counts: why") that shows it when pointed at, focused or tapped. An account with no verified wallets, which the profile itself says, shows the line that says so at once, with no room kept for a bar, and its wallets aren't asked for. A card never reads `/api/v1/user`.
  - Clicks in a card are its own (`nav::card_click` skips popovers), and text selected in it keeps it open. Cards in a dialog's list or a channel's header, which clip what overflows them, are placed against the viewport and close when anything scrolls.
- **Followers and following.** A profile's follower and following counts are links to `/u/<name>/followers` and `/u/<name>/following` (`pages/follows/`, a part of its own); pointing at one, or pressing it, prefetches the list's first page. The page's header has the account, a way back to its profile, and the two lists as tabs, which keep the address's query when switching. Under it, a toolbar for searching and sorting stays under the site's header; its controls are in place, and disabled until they work.
  - **One list, all of it tall.** Every row is the same height (64 px; 72 px up to 640 px wide), so the list is as tall as everyone loaded from the start, and only the rows in view and 8 either side are in the page (`window.rs`): a thousand people are under 40 rows. Rows are placed absolutely, without transforms, so an open profile card is above the rows after its own.
  - **Reading on.** The next page is read as the reader comes within two screens of the end, one request at a time, and not while the tab is hidden; a page that fails is asked for again after 2, 4 and 8 seconds, then offers Try again, keeping the people shown (`loader.rs`). Later pages name the account `fid:<n>`, from the first page's `owner`. What a visit loaded of a list is kept for 5 minutes (`store.rs`), so Back from a person's profile shows all of it, at its height, and `nav.rs` puts the reader where they were.
  - **A row** opens the person's profile anywhere it's clicked, as a feed card opens its post (`nav::card_click`); its name is the link, and shows their profile card, which needs nothing more than the row carries (the start of the bio, the counts and the registration) but its vote and wallets. Anything a row gains later (a Follow button) goes beside the link, never inside it.
  - **Time order across the node's shards.** A follow is a message of the account that makes it, and the node keeps each account in one of its shards (two on 21 October 2026). Whom an account follows is all its own messages, so `linksByFid` pages them in order. Its followers are in every shard: a `linksByTargetFid` page holds each shard's next 50 links, newest first, one shard after the other, and its token continues every shard; the shards don't page in step, so a page's newest link can be newer than the previous page's oldest. The Worker lists only the links no later page can come before, those as new as the oldest link each shard still being read has reached, and carries the rest in its cursor with each shard's place (`allthing_core::follows::merge`). A shard a page ahead of the other sits out the next read, so few links wait: 79 at most, paging @dwr's followers 25 pages deep. Which shard a link came from is told by the token: a shard whose next key came back read a full page, one without read to its end, one left out read nothing, and the links are counted off in shard order. The node's token is base64 of a JSON array of the shards' keys, with `null` for a shard at its end, and a `null` sent back starts that shard over, so a list whose shards end apart never ended; the Worker sends `[]` for a shard that has ended, which reads nothing of it (`hypersnap::follow_links`). A read whose counts don't add up is put in order by itself, with what waited, and the list reads on. The cursor is URL-safe base64 (each shard's key and how far back it has read, and the links waiting, a few bytes each), checked whole before anything is read: a malformed one is a 400. An account the node lists that `user/bulk` doesn't know is left out, and so is an account's follow of itself.
- **Media.** `media.rs` turns embeds into a gallery with generated alt text that names the author and quotes the cast. A list of casts is dense, as in the Farcaster app: in a feed's cards and the casts they quote, media is at most 270 px tall, or half the window on a phone (`--feed-media` in `style/allthing.css`), each image and video at its own shape (a tall one whole, narrower), and a cast's images are one row of squares on a computer. A post's page keeps large media, for the cast it opens and its replies: a single image or video spans the post at its own shape, at most 70% of the window tall (80% when portrait). A click or a tap on an image opens it in the lightbox at full size, in a list as on the post's page, and a video, which plays in place with its own controls, has a button that opens it there. A single image has its box before it comes, so nothing below it moves when it does: the browser asks Cloudflare Images for its size (`embeds::inline_size_url`, the inline variant's description, about 110 bytes; `media::size_up`), each image once a visit and six at a time, never through the Worker, and an image hosted elsewhere that is about to show is read until its first bytes tell its size. A list draws its next screenful of cards, where it ends in view, once their images' sizes have come or a second has passed (`CastList`, `media::sizing`), and a post's page, and a channel's with a pinned cast, show once the images at their top have them. A size seen before, or by the front page's first cards (`known_size`), boxes the tile at once; one not known yet holds a square, no larger than the place's cap. A single GIF shows at about the size Discord gives one instead: its own shape, at most 300 px wide and 300 px tall (in a list, no taller than its media), from the text's left edge, and on a phone at most 70% of the card's width (its tile is marked `gif`). A GIF is an embed from Tenor's, KLIPY's or GIPHY's media hosts, one that comes as an MP4 included, an image whose path ends in `.gif`, or one its provider says is `image/gif` (`allthing_core::embeds::is_gif`). Hypersnap sends no content type, so a GIF on Cloudflare Images, whose address has no extension, shows as a photo. Among other media, a GIF is a tile like theirs. The lightbox is a modal dialog with a focus trap, Escape, arrow keys and pointer swipes, and it returns focus to the tile that opened it; it shows a GIF at its own size.
- **Emoji.** Allthing has a pack of Pepe emoji (`allthing_core::emoji::PACK`): 219, 159 of them animated, self-hosted as WebP under `/assets/emoji/v1/`. `cargo xtask dist` copies them from `web/emoji/v1/`. Each is 64 px tall and at most 150 KB (the 116 added since at most 100 KB), and each animated one has a still, its fullest frame. Each belongs to one of eleven groups (`emoji::Group`), Classics first, in the pack's order. `web/emoji/CREDITS.md` credits each one's maker and source, and gives its terms: why it may be here, by its source's rules. `:pepe_name:` in a cast's text, in any case, becomes the emoji when the name is in the pack (`Token::Emoji` in `allthing_core::text`); any other `:word:` stays text, and other Farcaster apps show the shortcode as written.
  - A cast's excerpts show them too (`ExcerptText`, from `text::text_and_emoji`): the Replies preview, search suggestions, the composer's reply and quote, the media viewer's caption (who posted the cast, then its words, cut to two lines beside "1 of 2" when there are several; each item's alt text stays on the item, for screen readers), and the scheduled list. Nothing in an excerpt is linked, since it sits in a link or a button. An excerpt (`text::truncate_title`) counts an emoji as three characters, about the room it takes, and never cuts a shortcode in two; the emoji comes whole or not at all.
  - An emoji is 1.6 em tall in the text, 1.4 em in a one-line excerpt (a search suggestion, the composer's), which clips what leaves its line, and 48 px when a cast is one to six of them and nothing else.
  - Each is a `<picture>` whose `prefers-reduced-motion: reduce` source is the still. Its alt text is the shortcode, so copied text keeps it, and what Pepe does is read out as its description (`aria-description`), not shown in a native tooltip. Each loads lazily in cast text, and at once in an excerpt, which is in view as it shows.
  - `/assets/` files are cached for a year as immutable, so a changed image takes a new folder (`v2/`).
  - `web/emoji/CREDITS.md` names each one's source and maker. A unit test keeps the files, the table and the credits in step, reading each size from the WebP header; another keeps `emoji::MAKERS` the same as the credits, for the picker, which names the maker of the Pepe pointed at or focused beside its shortcode. `cargo xtask check-credits` reads every source, emoji and stickers, and checks that it is still there under the terms its credit gives, by the maker it names (7TV's and FrankerFaceZ's APIs, emoji.gg's page); it only reads, and exits 1 naming any that isn't.
- **Stickers.** 32 of the animated emoji are stickers too (`allthing_core::emoji::STICKERS`): 7TV's 128 px GIF of each, unchanged, under `/assets/stickers/v1/`, with a still of its fullest frame, and a moving tile for the picker (`.tile.webp`, an animated WebP of the same size made from the GIF, lossy at quality 40 or lossless, whichever is smaller: about a third of its bytes).
  - A cast carries a sticker as an image embed of its GIF at `https://allthing.social/assets/stickers/v1/<name>.gif`, so every Farcaster app shows it. GIF is what they all play.
  - Allthing knows its own stickers by that address (`emoji::sticker_of`). `MediaGrid` shows each one apart from the cast's photos: 128 px tall with no frame, loaded from the site itself, and as its still with reduced motion. Its alt text is "Sticker: Pepe …".
  - `web/stickers/CREDITS.md` names each one's source and maker; a unit test keeps the files, their sizes (from the GIF and WebP headers) and the credits in step.
- **Video.** `player.rs` and `video.rs`: an IntersectionObserver loads the master playlist 600 px before a video scrolls into view. Browsers that play HLS themselves get the playlist: Safari, and Chrome (on computers since about version 142; checked with Chrome 155). Videos autoplay when at least 60% visible and pause when scrolled away. They autoplay muted unless the reader turned sound on: playing a video or unmuting one turns it on, and muting one turns it off. The choice is kept in localStorage (`allthing.sound`). Each player notes the muted state it set, so a `volumechange` it didn't cause is the reader's. Before the reader has interacted with the page, browsers refuse sound; the video then plays muted, and its sound comes on at the first tap or key press. Only one plays at a time, and none autoplay with reduced motion, Save-Data or a 2g connection. An autoplaying video's sound badge turns its sound on or off, and stays hidden until wanted: on a computer while the pointer is over the video or keyboard focus is on it, and on a touch screen for 3 seconds after a tap on the video (`sound-shown`), which a press's `pointerType` tells from a click or a key. A tap while it shows plays the video with sound and controls. Elsewhere (Firefox) the Rust player parses master and media playlists (`allthing_core::hls`), picks a rendition by height (720p inline, 1080p in the viewer), and feeds fMP4 segments into separate video and audio `SourceBuffer`s. It keeps 24 s buffered ahead, follows seeks and steps over gaps. Within a run it goes on segment by segment from the last one appended, since a playlist's times can drift from its media's, and it ends the stream once the last segment is in, even where the playlist claims more time than the media holds: a video then loops (inline videos have `loop`) instead of stalling on its last frame. Plain `.mp4` and `.webm` files play natively. YouTube, Vimeo, Loom and Streamable links render as facades that load the provider's iframe only on click; YouTube uses `youtube-nocookie.com`.
- **Threads.** `CommentTree` renders replies recursively. Collapsing animates the row height and marks the hidden subtree `inert`.
- **Press feedback.** Every control a reader presses (a button, a tab, a select, a link) answers in the frame after the press: it shrinks a little (`scale: 0.96`, a transform of its own beside any `transform` it has, so nothing around it moves) and dims, and eases back over 90 ms when it's let go; a link in a line of text, which can't scale, only dims, and with reduced motion everything only dims. One passive listener on the document (`press.rs`) marks the control `data-press="down"` on the primary pointer's main button, Space or Enter, and `"up"` on letting go, a touch that turns into a scroll (`pointercancel`), a long press's menu or a drag; it eases back once the frame that answers the press is painted, so that frame draws only the answer, and a control the answer takes off the page (a tab drawn anew, a page left) isn't animated. Not `:active`, which a touch screen shows late (Chrome on Android once a touch has lasted a moment) or not at all (iOS Safari only on a page that listens to touches, so the listener has an empty passive `touchstart` too), and whose styles here eased in, so its first frame showed nothing. Controls take `touch-action: manipulation`, so a tap is never half a double-tap zoom. A toggle's pressed state (`aria-pressed`), hover styles and focus rings are as they were.
- **Design.** `style/allthing.css` is a light theme: warm paper, an indigo accent, cyan and gold for the "portal" details, and Instrument Serif for display type. It adds a faint lattice and glows behind the page and a slowly drifting line under the header. Cards rise in and lift on hover, threads expand, and skeletons shimmer. `prefers-reduced-motion` turns the motion off.

## The static copy (GitHub Pages)

A static host can't run the Worker, so `cargo xtask pages` builds a second variant of the app:

- compiled with the `static-host` feature, `api.rs` answers `/api/v1/...` paths in-process: `allthing_data::Endpoint::from_path` and `build` run with a browser `Host` (`window.fetch`, `AbortController`, `setTimeout`) and a budget of 30 upstream calls per page;
- it preloads nothing from the viewport, popover previews included: they load when they open, as they did before the batches. `/api/v1/engagement` still builds in-process if asked for (its 18 reads fit the budget of 30, and its replies' link checks leave the last ten), and a replies preview still comes from the post that hovering its card built;
- compiled with `ALLTHING_BASE_PATH=/Allthing`, every link, asset and the router live under that prefix;
- `404.html` is a copy of `index.html`, which is how GitHub Pages serves deep links to a single-page app.

Annotations memoized in the page (origins, apps) carry over between pages during a visit. There is no shared cache, so each visitor's browser makes its own upstream reads, and the module is about 30% larger because it carries the builders. The Farcaster app's API sends no CORS headers, so the browser can't read it: channel pages show Hypersnap's data alone, and votes recorded only by the app are unknown. The Cloudflare deployment is the primary one. This copy keeps the project usable from any static host.

## Sign-in

Readers sign in with Farcaster, through the Farcaster app on their phone. Where the Worker endorses keys (`ALLTHING_CUSTODY_KEY`, as on allthing.social), there is one QR flow: the reader approves Allthing's key request, and that one approval signs them in and lets them [cast, reply, quote, like, recast, follow and delete from here](#liking-and-recasting) ([below](#signing-in-by-approving-the-key)), with no second scan or grant step; the same dialog, in its approve form, is the only other approval a reader meets ([one dialog](#one-dialog-one-approval)). Elsewhere, where the Worker endorses no keys (a fork, or `wrangler dev` without the secret), they sign in with [Sign In With Farcaster](https://docs.farcaster.xyz/developers/siwf/), by QR code over Farcaster's AuthKit relay (steps 1 to 6), which only says who is reading: it gives Allthing no key to write with, and writes go to the Farcaster app. Where keys are endorsed, the relay isn't asked anything. There is no other way to sign in: no wallet connection, password or email.

1. **Start.** The header's "Sign in" button opens a dialog, which asks `POST /api/v1/auth/start` for a nonce. The Worker makes 16 random bytes into a 32-character hex nonce and puts it, with an expiry 10 minutes away, in the `__Host-allthing-siwf` cookie, signed with HMAC-SHA256 (HttpOnly, Secure, SameSite=Strict). It also answers that expiry (`expiration_time`), on its own clock.
2. **Channel.** The browser opens a channel on `relay.farcaster.xyz` with that nonce, this site's domain, its address and that expiry (`expirationTime`), as AuthKit does, so the relay sees the reader's browser, and the message the app signs lapses with the nonce: a device whose clock is wrong can't cut it short. It answers with a channel token and the link the Farcaster app opens.
3. **QR code.** The Worker draws the link as a QR code (`POST /api/v1/auth/qr`, error correction level M), sent as one SVG path that the app renders inline, so browsers ship no QR encoder. It draws only Farcaster's links: sign-in links, [key request](#liking-and-recasting) links, and the farcaster.xyz links writes are [handed to](#handing-writes-to-the-farcaster-app) (`allthing_core::compose::is_handoff_link`). The dialog shows the code alone, with no link that opens the Farcaster app: signing in takes a second device, the phone that scans it.
4. **Approval.** The browser polls the relay's channel status every 1.5 s for up to 5 minutes, one request at a time; a poll that fails is tried again at the next. A hidden page doesn't poll, and polls at once when it is back in view (`visibilitychange`, `focus`, `pageshow`). A code that runs out while the dialog is in view is replaced by a new one, twice, before the dialog offers one. The person scans the code and approves in the Farcaster app, which signs a Sign-In with Ethereum (EIP-4361) message. When the status is `completed`, the dialog shows who approved (the relay's username and picture) and the browser sends the message and signature to `POST /api/v1/auth/verify`. If the Worker can't check it just now (503, when Optimism can't be read, or no answer), the same approval is sent again after 1, 2 and 4 seconds, and then "Try again" sends it again: no new code to scan while the nonce lasts.
5. **Verify.** The Worker checks what `@farcaster/auth-client` checks (`allthing_core::siwf`, `allthing-worker/src/auth.rs`):
   - the message: the statement "Farcaster Auth", chain id 10, exactly one `farcaster://fid/<fid>` resource, this site's domain and address, the nonce in this browser's cookie, and its expiration and not-before times;
   - the signature: the address that signed it (EIP-191 `personal_sign`, recovered with secp256k1 and Keccak-256) is the message's;
   - the signer: on OP Mainnet, in one batched request, the address is the account's custody address (`IdRegistry.idOf`) or one of its auth addresses (`KeyRegistry.keyDataOf`, an added key of type 2).
6. **Session.** The Worker sets `__Host-allthing-session`, `<fid>.<expiry>` signed with HMAC-SHA256 (HttpOnly, Secure, SameSite=Lax, 30 days), and `__Host-allthing-user`, the account's name and picture, which the header reads to show who is signed in without an API call. It is only a label: the HttpOnly cookie is the session. The header's picture links to the account's profile; hovering it, keyboard focus resting on it, or a tap on a touch screen opens the account menu, whose "Sign out" (`POST /api/v1/auth/signout`) clears both cookies. Tabs of the site tell each other when someone signs in or out (a `BroadcastChannel`), and each follows from the cookie they share.

### Signing in by approving the key

Where the Worker endorses keys, the approval that lets a reader [write from Allthing](#liking-and-recasting) signs them in too, so one approval does both, and the relay isn't used (`components/signin.rs`, and writing's `signing_in` in `components/writer.rs`).

1. **Start.** The header's "Sign in" opens the dialog, which asks `POST /api/v1/auth/start` for a nonce, as above; the Worker's answer says it endorses keys (`keys: true`).
2. **The key and its request.** The browser makes its key, unexportable, as for a [like](#liking-and-recasting), and keeps it in IndexedDB for the sign-in (`keys::SIGNING_IN`, until the account that approves it is known). A browser holding the nonce cookie `start` set may have its key endorsed (`/api/v1/auth/signer`) before anyone is signed in. It hands the endorsement to the Farcaster app's API, which answers a token and a link. A request still waiting from an earlier try, whose endorsement has two minutes or more left, is used again: the same code, not another key.
3. **The code, or the link.** Where a pointer hovers, the dialog shows the link as a QR code for the reader's phone ("Scan the code with your phone's camera, then approve Allthing in the Farcaster app"); on a phone, which can't scan its own screen, it shows **Approve in Farcaster**, the link itself, which opens the Farcaster app. Before the scan, it says that one approval signs the reader in and lets them cast, reply, quote, like, recast, follow and delete from here, shown "via Allthing", and, where the request's endorsement names Allthing's own account, @allthingapp, that the Farcaster app shows the request as from it. Until the Worker has said whether it endorses keys, the dialog says nothing of what signing in allows, rather than Sign In With Farcaster's note for a moment.
4. **Approval.** The browser polls the request every 2 s (a hidden page doesn't, and polls at once when back), until the Farcaster app has added the key; the request then names the account that approved. The browser asks Hypersnap for the account's keys until the new one is listed, for 30 s at most.
5. **The Worker's check.** The browser asks `start` for a fresh nonce, since the first may have lapsed while the reader approved, signs `<domain> asks you to sign in with your Allthing key.` and `Nonce: <nonce>`, on two lines, with the key (`allthing_core::siwf::key_sign_in_message`), and sends the account, the key and the signature to `POST /api/v1/auth/key`. The Worker checks, in turn:
   - the nonce: it is this browser's, from its signed cookie, and current;
   - the signature: Ed25519, by the key, of that message for this site, checked by the runtime's WebCrypto (`crypto.subtle.verify`), so no WebAssembly works it;
   - the key: Hypersnap lists it among the account's keys (`/v1/signersByFid`), added by approving a request from Allthing's account (`ALLTHING_FID`). If it isn't listed yet (`siwf::KEY_UNKNOWN`), the browser asks again after 2, 4 and 8 s, with no new approval.

   Only a browser holding a key the account approved for Allthing can make that signature, and the nonce ties it to this sign-in in this browser: it can't be replayed elsewhere or later.
6. **Signed in, and able to write.** The Worker sets the session as in step 6 above. The browser keeps the key for the account, approved, so the reader's first like, recast or cast goes out at once with it.

### One dialog, one approval

A reader signed in with no approved key in this browser (signed in by Sign In With Farcaster before keys, after [Revoke permissions](#liking-and-recasting), or with its storage cleared) isn't asked anything when a page loads: no dialog opens by itself. Their first write (a like, a recast, a follow, a delete, a cast, a reply, a quote, a Pepe reaction, a scheduled cast) opens the sign-in dialog in its approve form, "Approve Allthing to write from here" (`Session::grant`, and writing's `granting` in `components/writer.rs`): the same code or link, the same states and the same words for what the approval allows, which here signs no one in. Once approved ("Approved. Adding Allthing's key to your account…", the reader's picture in the code's place), the key is kept for the account and the write that asked goes. Closing it unapproved drops that write (a cast stays a draft in the composer, which the dialog opens over); a request still waiting shows the same code next time. They aren't signed out: a session without a key here can read, and its first write asks. There is no other approval dialog, and no relay request where keys are endorsed.

On the stand-ins (`e2e/one-qr.fixture.spec.ts`, measured 21 Oct 2026), signing in took 4.3 to 5.0 s from the approval, in two runs at 390 and two at 1280 (4.3 and 4.4 s at 390, 4.5 and 5.0 s at 1280): the poll that sees the key added (every 2 s), the node, a moment behind, listing the key at its second ask 2 s later, and the Worker's check. On Farcaster, the time the Farcaster app takes to add the key on chain, and the node to see it, comes on top. All the while the dialog says "Approved. Signing you in…", with a check in the code's place.

### Writing a cast

Any reader can write a cast, a reply or a quote (`components/compose.rs`): **Cast** starts a cast, in the channel on a channel page, and **Reply** and **Quote** under a post or one of its replies start a reply to it or a cast that quotes it. Cast is on the front page's feed, a channel's, Notifications and a signed-in reader's own profile; outside a channel it starts a cast in no channel (`own_profile`: `/u/` and their username, in any case, or `fid:N`), and it stays in reach as the page scrolls. Drafts last (below).

- **On a computer**, Cast is a pill in the site header, before the account's picture (`HeaderCast`): the header is sticky, so it is always in view, and the page has no other Cast. It is as tall as the search box, so the header is as tall with it as without, and on a page without Cast its place is kept, unseen and out of reach, so the search box doesn't move from page to page.
- **On a phone**, it is a round button, 48 px, floating at the bottom right, 10 px from the edge and 12 px from the bottom (each with the screen's safe area), with notices above it (`CastFab`). Those pages leave room after the footer for it, so the last card's like, recast and reply and the footer's links scroll clear of it and take a tap. It steps out of the way while a modal dialog, the lightbox or a content popover is open, and while the keyboard is up for a text box: unseen and untouchable, but still focusable, so a dialog it opened gives it focus back as it closes. Settings keeps Cast visible and accessible; one Cast click or tap dismisses Settings and opens the composer.

**The bar** is as compact as the Farcaster app's (`composer_bar`): on the left, its tools, 32 px icons with no frame (a 40 px tap on a phone): attach (where this server takes files), emoji, sticker, GIF (where there's a key) and the clock (where it posts from here); on the right, how long the text is, then Cast, Reply or Quote. The length is a 20 px ring, as in the Farcaster app (`LengthRing`, `allthing_core::compose::length`): it fills toward a cast's 320 bytes, then toward a long cast's 1,024, amber in its last 75 bytes, and under 25 gives way to the bytes left, red and below zero past the limit. A screen reader hears it only as it crosses one of those lines (`length_note`, a `role=status` that changes only then).

**A reply** shows what it answers above its text box, as the Farcaster app's composer does (`ReplyParent`, from `allthing_core::compose::ParentPreview`): the author's picture, name, @username and how long ago; the start of the cast, clamped to five lines (three on a phone), with its Pepes drawn and nothing linked; its first four images and videos as squares of a fixed size, cropped to fill them (96 px, 64 on a phone; an image is the page's own size of it, so the browser has it already, and a video shows its poster when the page has loaded it, or Cloudflare Stream's, with a play sign); and "Replying to @username". A 2 px line runs from the author's picture down to the reader's, beside the text box, whose placeholder is "Cast your reply". All of it is drawn from the cast on the page as Reply is pressed, so opening the composer asks for nothing, the box has focus by the next frame, and every part has its size before its pictures load. The block is hidden from screen readers, who hear one line with the text box instead (`aria-describedby`): "Replying to @alice: " and the cast's first 120 characters (`compose::replying_to`). A scheduled reply being changed keeps less of the cast it answers (`SavedCast`), so it shows a line instead, "Replying to @alice" and an excerpt; the reader's own cast, deleted since, reads "This cast has been deleted".

**On a phone** (640 px wide or less) the composer is a sheet from the bottom of the screen that sits on the keyboard, as the Farcaster app's composer does. Its head has **Cancel** on the left and Cast, Reply or Quote on the right, where the keyboard can't cover them (the title still names the dialog for screen readers), and its tools are right above the keyboard: while it's open, it follows the browser's visual viewport (`fit_to_keyboard`, `allthing_core::compose::keyboard_inset`), what lies below the visual viewport being the keyboard (`--keyboard`), and is no taller than what's in view (`--sheet-max`), as the keyboard comes and goes and the page scrolls under it. Both are set on the sheet alone, and only while a keyboard is up: on the page's root they would have every element on the page styled again, which on a phone with a long feed held the tap that opens the composer past a frame. iOS's WebKit brings up its keyboard only for focus given in the tap itself, and the text box is drawn a moment after the tap, so on iOS the tap that opens the composer gives focus at once to a text field out of sight (`hold_keyboard`: `#keyboard-proxy`, out of the tab order and hidden from screen readers), and the text box takes focus from it as it's drawn, which keeps the keyboard up. Other phones' browsers (Chrome on Android) bring the keyboard up for the box's own focus, a moment after the tap, so there the tap gives no other focus, which would cost it a few milliseconds. CI's Chromium has no on-screen keyboard: `e2e/reply-sheet.fixture.spec.ts` stands in a visual viewport whose height it sets, and checks the order focus moves in.

**Under a post**, a reader signed in finds **Cast your reply**, as under a cast in the Farcaster app's conversations (`ReplyPrompt`): their picture, the faint words and a dimmed Reply, in a row 52 px tall, as wide as the post, between it and its replies. A click, a tap, Enter or Space opens Reply for the post, as Reply does. It is drawn with the post, in the frame it first shows (the session is known from its cookie at once), so nothing moves when it comes; signed out, or once the reader has deleted the post, there is none, and the static copy has none.

- **With the reader's key** (where [likes and recasts](#liking-and-recasting) are set up), the composer's **Cast**, **Reply** or **Quote** posts it from the browser. Each "@name" in the text is looked up at Hypersnap (`/v1/userNameProofByName`, once a visit per name) and becomes a mention: taken out of the text and listed with its byte offset, as Farcaster stores mentions (`allthing_core::text::split_mentions`); names that are no one's stay as text. The draft becomes a `CastAdd` (`allthing_core::compose::Draft::new_cast`, `message::NewCast`): the text, up to 10 mentions, its images and videos, the GIF and the quoted cast as embeds (two at most), and as its parent the cast replied to or the channel's parent URL, from the channel page's payload. Over 320 bytes it is a long cast, up to 1,024 bytes; the composer won't post past 1,024. **Cmd** or **Ctrl** and **Enter** in the text box posts it, as the Farcaster app's does (not in the GIF search, where Enter searches). It is signed and handed to the node like a like. Typing "@" and a name at the start of a word lists the accounts it may mean under the caret (`components/mention.rs`, `allthing_core::text::mention_query`, in the composer's part of the app): the search box's `/api/v1/search` people, once typing pauses for 200 ms, people the reader follows first and marked "Following" (`linkById`, asked by the browser). Up and Down move, Enter or Tab picks, Escape closes the list and not the composer, a click or a tap picks; the pick puts "@username " in place of what was typed (`text::complete_mention`). The text box is the list's owner for screen readers (`aria-controls`, `aria-activedescendant`, `aria-autocomplete="list"`). One the node takes closes the composer and shows where it will be listed, "Posting…", until the node shows it ([How a write lands](#how-a-write-lands)), and a notice then links to it; one the node refuses keeps the draft, and says why. A reply goes as in the Farcaster app: **Reply** closes the composer at once, and the reply shows in the thread before its mentions are even looked up (below). A reader without a key yet approves one first, in the sign-in dialog's approve form, over the composer.
- **Showing what went out.** A cast the node takes shows at once where it will be listed, as the reader's (`Writer::cast_posted`, `components::outgoing`): a cast or a quote above the home feed and the Casts tab of the reader's own profile (a cast in a channel above that channel's feed too), and a reply on their profile's Replies tab. It reads "Posting…" until the node shows it, then "Posted", linking to it; one the node doesn't show in time goes, and its draft is back in the composer.
- **A reply in its thread.** On a post's page, the reader's reply shows as a reply (`components::thread`): under what it answers, at the top of its replies, nested for a reply to a reply, with their picture, name, text, images and videos, and the count of replies one more there and on feed cards (`Writer::replies_shown`). It shows the moment **Reply** is pressed (`Writer::reply_going`), as posting: "Posting…" in its time's place, its actions doing nothing yet (`inert`), a little faded, until the node's store has it (`Writer::send_reply`, [How a write lands](#how-a-write-lands)). Then it's a reply like the others, with its time, which links to it, and its actions, and screen readers hear "Reply posted." (a polite live region; no notice shows). Once the page lists it itself, by its hash, the page's own shows instead. Refused, out of reach or not shown in time, it goes, the count goes back, and the composer opens again with the draft and why (`Composer::reopen`); for one out of reach or not shown in time, **Retry** hands the node the same signed message, while the draft is as it was. One the node refused goes again only as a new message, with **Reply**. With another draft in the composer by then, a notice says it instead, with Retry. A reply handed to the Farcaster app shows in the thread the same way, "Posting in Farcaster" until it is. Its card goes once the page lists the cast itself, or the cast is deleted. The tab keeps it for 10 minutes (`sessionStorage`, `allthing-posted`), so a reload still shows it while the Worker's copy of the page may not have it yet. Then the Worker is asked to refresh the pages the write changes (`POST /api/v1/refresh`, below): the reader's profile, the cast replied to with its replies, the post the reader wrote it on, the channel. The browser reads each again past its HTTP cache (`api::reload`, `cache: "reload"`), so the copies it keeps, and the next page load, have it. A page that doesn't have it yet, as the node's indexes catch up, is asked for again after 4 and 10 s. A delete and a Pepe reaction refresh their pages the same way.
**Drafts last**, as in the Farcaster app: the browser keeps one for each thing the composer is for, a reply to a cast (`reply:<hash>`), a quote of one (`quote:<hash>`), a cast in a channel or on the front page (`cast:<channel>`, `cast:home`), in `localStorage` (`allthing-drafts`, `allthing_core::drafts`). Each holds the text, its files' URLs once uploaded, its GIF or sticker, for a reply what the composer showed of the cast it answers, and when it last changed. It is kept as it changes (once typing pauses for 400 ms) and as the composer closes, which says "Draft kept"; so starting another, closing, or reloading the page loses none, and opening the composer for something takes up its draft. They last 14 days, and the 30 newest are kept; a draft that can't be read, or storage that refuses them, is let go quietly. Their JSON is read and written in the composer's part (`composer_read_drafts`, `composer_store_drafts`), not the app's first part, which holds them as read (`KEPT`), so the tap that opens the composer takes its draft up at once: a reader with drafts kept has them read once the browser is idle, any other reader as Cast, Reply or Quote is about to be used (`warm`), and another tab's changes are read as it makes them (the `storage` event). A cast that goes out lets its draft go. **Discard**, in the bar while there's a draft, asks once (on Keep) and lets it go. The composer's tabs, **Compose** and **Drafts** (with how many), are as the Farcaster app's; the dialog's title names it for screen readers. On a phone they have a row of their own, under Cancel and the post button, which can be as wide as "Post in Farcaster". Drafts lists them, newest first: what each is for ("Reply to @alice", "Quote of @bob", "Cast in /books"), its first two lines and how long ago it changed; pressed, one is taken up in Compose, a reply with what it answers, and × deletes one. A scheduled cast being changed is the Worker's to keep, not the browser's.
- **Refreshing.** `POST /api/v1/refresh` takes what was written (`allthing_core::api::Wrote`: the reader's username, the cast replied to, liked or recasted, the post it was written on, the channel) from a signed-in session, from Allthing itself (`Origin`), 20 times a minute per reader in an isolate. It expires each page's entry in the edge cache (`cache::expire`): kept, so a rebuild that fails still serves it, but dated long ago, so the next read builds it anew. A profile is expired only when it is the session's own. It asks nothing upstream and caches nothing (`allthing-worker/src/refresh.rs`).
- **In the Farcaster app**, for a reader signed out and wherever the Worker endorses no keys (no `ALLTHING_CUSTODY_KEY` secret, as on allthing.social until it is set): **Post in Farcaster** opens farcaster.xyz's compose link (`allthing_core::compose::Draft::compose_url`) with the text, its images and videos, the GIF, a quoted cast's link (`allthing_core::compose::cast_url`), and the channel (`channelKey`) or the cast replied to (`parentCastHash`). On a phone, the link opens the Farcaster app at once; on a computer, the [hand-off](#handing-writes-to-the-farcaster-app) shows it as a QR code for the reader's phone, with the link to farcaster.xyz beside it, and **Done** clears the draft. The reader posts the cast there. There is no clock, since nothing is kept to post later.

**Images and videos** go with a cast too, where this server keeps them ([Attachments](#attachments)), from the composer's part (`components/attach.rs`). As the composer opens for a reader signed in, it asks `GET /api/v1/media`, while its code comes (kept 5 minutes), and shows the attach button only once that answers 200 with the server's limits. Until then, and wherever it doesn't (no bucket bound: 404; a reader signed out isn't asked), the composer is as it was without them: no attach button, a paste is text, and a dropped file isn't taken.
- **Adding.** The attach button, a picture, first in the composer's bar, opens the browser's file picker for the seven types, several at once, which on a phone is its photos (on a touch screen it takes a tap 44 px square). A screenshot pasted in the text box attaches too, as do files dropped anywhere on the composer, which says where they go while they're dragged over it. Text copied with a picture of itself (from a word processor, a spreadsheet or a page: plain text with HTML or RTF) is pasted as text. Each file is checked before it is sent, against the types and sizes the server gave (`allthing_core::media::check_file`); one that can't go is said at once, with its name.
- **Two embeds.** A cast carries two: its files, its GIF or sticker, and the cast it quotes, together (`media::embeds_left`). At two, the attach, GIF and sticker buttons say so (`aria-disabled`, with why as their description, and a note when pressed), and a file pasted or dropped is refused with the same note. A GIF there already can be changed for another.
- **Metadata.** A JPEG, PNG or WebP is read in the browser and sent without its metadata (`allthing_core::metadata`), so where a photo was taken, the camera and its own descriptions stay on the reader's device: a JPEG loses its Exif, XMP and IPTC segments (APP1, APP13) and anything after its picture (a phone's extra images); a PNG its `eXIf`, `tEXt`, `iTXt` and `zTXt` chunks; a WebP its `EXIF` and `XMP ` chunks, with its RIFF size and VP8X flags put right. The picture's bytes are copied as they are, never decoded or encoded again. A turned JPEG keeps its orientation, alone, in an Exif of its own, so it shows upright. A file that can't be read as its type isn't sent. GIFs and videos go as they are, metadata and all: a phone's video can say where it was taken.
- **Uploading.** Each file goes as soon as it's added, by `XMLHttpRequest` for its upload's progress, as the body of `POST /api/v1/media`. Its tile shows the picture (an object URL, so `img-src` takes `blob:`) or the video's first frame (`<video muted playsinline preload=metadata>`), with a progress bar (`role=progressbar`) while it goes. Remove (×) takes it off, stopping an upload on its way, and its object URL is let go. A file the Worker refuses (413, 429, 507) says why, as the Worker words it, with Retry and Remove. Cast waits, as "Uploading…", until every file is in.
- **Posting.** The cast embeds the files' URLs in order, then the GIF or sticker; the hand-off to the Farcaster app carries them as `embeds[]=`; a scheduled cast keeps them in its draft (`SavedDraft::media`), so /scheduled shows them and changing it keeps them. The reader's cast, shown at once where it will be, shows its first file.

**GIFs** come from [KLIPY](https://docs.klipy.com). Its terms require the API and the media to be reached from the reader's browser, never through a partner's server or cache, and results to show in KLIPY's order, in a grid of their own, under a search box whose placeholder is "Search KLIPY". So:
- The browser calls `api.klipy.com` itself, with the app key `/api/v1/gifs/key` hands a signed-in session (from the `KLIPY_API_KEY` secret). It asks for what's trending when the picker opens, then searches once typing pauses for 350 ms, or at once on Enter. Pages are kept for 10 minutes this visit, so going back to an earlier search asks for nothing.
- Each tile shows its GIF whole, at the shape KLIPY gives (`--shape`), in rows that share a height and keep KLIPY's order: a tile grows from a basis of its shape at the row's height (104 px, 84 in a phone's sheet, three square GIFs to a row), to at most 1.75 times that, and the last row keeps its tiles' size. On a phone the search box isn't focused as the picker opens, so the keyboard doesn't cover the GIFs, and Enter puts the keyboard away.
- Requests use `content_filter=high` and `format_filter=gif,webp`. A tile is the small animated WebP (`sm`, about 120 KB). A cast embeds the medium GIF (`md`), or the nearest size whose link fits a cast's 256-byte embed.
- Without the secret, the key endpoint answers 404 and the composer has no GIF button.

**Emoji** come from Allthing's own pack ([above](#the-browser-app)), so the picker (`components/emoji_picker.rs`) needs no key and asks no one for anything.
- **The button.** A Pepe, before the GIF button, opens the pack under a search box; one picker is open at a time, and Escape closes it before the dialog.
- **Groups.** The pack shows group by group (`emoji::Group`), each under its heading. Above the grid, a bar has a button for each group, with its first emoji as its face: it brings the group's heading to the top of the grid, and the group whose heading has reached the top is marked (`aria-current`). The last groups, which can't scroll that far, stay marked when chosen. With the bar, the grid is shorter by as much, so the picker grows no taller. The groups in view are drawn as it opens and the rest one a frame after, and each emoji's picture loads as it comes into view, so opening it is quick ([PERFORMANCE.md](PERFORMANCE.md#the-composer-and-its-pickers)).
- **Search.** The search matches the start of a word, in names first, then descriptions (`allthing_core::emoji::search`), and shows one grid of what it found, without groups; Enter picks the first match.
- **Recently used.** Up to 16 come first, newest first, kept in localStorage (`allthing.emoji`).
- **Motion.** Each emoji shows its still and moves while pointed at or focused (not with reduced motion), and the picker's foot shows the one pointed at with its shortcode.
- **As they're typed.** The text box shows the pack's emoji as soon as their shortcode is complete: ":pepe_smug:" becomes the smug Pepe, as a cast shows it, while the draft, and the cast that posts, keep the shortcode (`components/editor.rs`, `allthing_core::text::written_emoji`). The box is editable text (`contenteditable`): its text nodes hold what was typed, with newlines as line breaks, and each emoji is an image whose `data-text` is its shortcode as typed, in any case. Unknown shortcodes and colons inside a link stay text, as in a cast. Offsets into the draft count UTF-16 units, as a text box's selection does, with an emoji counting as its shortcode, so the caret and selections land where they did. Backspace and the arrow keys take an emoji as one character, and a selection with one in it is replaced as a whole. Enter is a newline. A paste is its plain text, with its shortcodes shown as emoji and the caret after it, and markup is left behind. A copy or a cut gives the draft's text, shortcodes and all. Undo and redo go by the draft (`allthing_core::compose::Edits`: typing within a second is one step), since the box is drawn again after a change, which a browser's own undo can't follow. What a phone's keyboard composes (IME) is read once it is done.
- **A pick** puts the shortcode in at the caret, or in place of the selection, spaced from the words beside it, and leaves the caret after it, as the Pepe (`emoji::insert`, which counts in UTF-16 as a text box does). The composer keeps the caret itself while the text box hasn't focus, since a tap elsewhere can move an unfocused box's selection, and focus brings it back.
- **Closing.** A click or Enter closes the picker and returns to the text, unless Shift is held; a tap on a touch screen leaves it open for another, and doesn't call up the phone's keyboard.
- **Room.** While a picker is open, the text box is two lines tall, so text and picker fit the dialog together, and it stays at the top of what scrolls, so on a short screen the picker scrolls under the draft rather than taking it out of view. The composer opens near the top of the window and grows down as a picker opens, so its top and the draft stay where they are; on a phone (640 px wide or less) it is a sheet from the bottom of the screen, as wide as it, that grows up.
- **Stickers.** The sticker button, a sticker peeling, opens the picker on its Stickers tab. The composer holds the tab, so the emoji and sticker buttons each say whether the picker shows theirs, and the arrow keys move between the two tabs. The stickers are searched as the emoji are, with up to 8 recently used first (`allthing.stickers`, kept apart from the emoji). A pick attaches the sticker in the GIF's place, as the cast's image embed, and closes the picker: a cast takes one. As on Telegram, the stickers in view move: the panel is taller (four rows on a phone; on a computer, five larger stickers to a row), and each tile's moving WebP loads as it comes within 32 px of the grid's view (an `IntersectionObserver` on the grid, as `loading="lazy"` would load all of them in a scroll box this short). With reduced motion, or Save-Data, they show their stills. A sticker held down for 350 ms shows large over the grid, with its name, until let go, and the press picks nothing.
- **Emoji reactions.** Farcaster's own reactions are only likes and recasts: the node refuses any other kind. So an emoji reaction is a reply that is one Pepe and nothing else (`allthing_core::emoji::reaction`), which every Farcaster app shows as a reply, `:pepe_name:`. React, after Reply and Quote under a post or a reply (its icon alone on a phone), opens the picker, emoji only, in a popover; a pick goes out at once as that reply, with the reader's key (`Writer::react`), closes it, and says so with a link to the reply. Under a post and under each reply, `components/reactions.rs` gathers the replies that are reactions into chips (`emoji::reactions`): one per emoji, each account counted once, most first, naming who reacted. The reader's own this visit join them, pressed, and a chip they haven't pressed reacts with its emoji too. Their own chip, pressed again, takes the reaction back: the reply that is it is deleted (`Writer::delete`; `Reacted::replies` keeps each reply's hash, and `Writer::reaction_reply` the reply each reaction this visit became), at once with their key, or in the Farcaster app, where the reply opens to delete. A reply deleted this visit no longer counts on its chip. The replies stay in the thread as replies. Feeds carry no replies; a listing carries its casts' reactions as the follower keeps them instead ([Daily active accounts](#daily-active-accounts)), and its cards show them as chips under their foot (`reactions::card_reactions`, gathered by `emoji::reactions_kept`). They come with no names, so a card's chip counts the accounts (`emoji::who_reacted`: "by 3 accounts"), and the reader's own is "you"; it reacts and takes back as a post's does, and the reader's reactions this visit join them, on a card that had none too. Their code is a part of its own (`split_chips.wasm`, [PERFORMANCE.md](PERFORMANCE.md#code-loaded-when-used)), fetched the first time a card has some; an empty row of their height holds their place until it comes, and if it can't, the card goes without them. The static copy has none.

The secret that signs the cookies is the Worker secret `SESSION_SECRET` ([DEPLOY.md](DEPLOY.md#secrets)); without it, `start` and `verify` answer 503. Sessions are stateless: no store holds them, and changing the secret signs everyone out. Every `/api/v1/auth/` call must be a POST whose `Origin` is the site's own, so other sites can't start, finish or end a sign-in, and its answers are never cached. The static copy has no Worker and so no sign-in; its header says it only reads.

### Handing writes to the Farcaster app

A [signed key request](#liking-and-recasting) can only be made with the custody key of the account that asks. Allthing asks as its own account, @allthingapp (`ALLTHING_FID`, 3356318), and that account's custody key is the Worker's `ALLTHING_CUSTODY_KEY` secret ([DEPLOY.md](DEPLOY.md#secrets)). Until the secret is set, as on allthing.social for now, and for a reader signed out anywhere, every write goes to the Farcaster app, where the reader does it as themselves (`components/handoff.rs`):

- **What opens there.** A like, a recast or a delete opens the cast (`allthing_core::compose::cast_url`: `https://farcaster.xyz/<username>/<hash's first 8 digits>`, or `~/conversations/<hash>` for an author without a username). A follow or an unfollow opens the profile (`profile_url`: `https://farcaster.xyz/<username>`, or `~/profiles/<fid>`). A Pepe reaction, a cast, a reply and a quote open the composer with the draft ready to post (`Draft::compose_url`).
- **The dialog.** The buttons are where they always are, for every reader: the heart and the recast icon, Follow beside a profile's name, Delete under the reader's own casts (signed in), React and the reaction chips, and the composer's **Post in Farcaster**. Each opens one dialog that names the action ("Like in Farcaster", "Follow @alice in Farcaster"), with a line only where the title doesn't say it all ("Your reply, ready to post."), and links to it. The link takes focus; Escape, the close button or a click outside closes it, and focus goes back to the button. Opening the link closes it.
- **A computer and a phone.** Where a pointer hovers, the dialog shows the link as a QR code too, for the reader's phone, and the link reads "Open on farcaster.xyz", for the app on the web. The Worker draws the code (`POST /api/v1/auth/qr`), which draws only Farcaster's links, once a visit for each link. On a phone the dialog has no code, and the link, "Open in Farcaster", opens the app; the composer's Post in Farcaster is that link itself.
- **What the page shows.** Signing in isn't needed for any of it, and signed out the buttons aren't toggles (no `aria-pressed`). A signed-in reader sees what they did in any app: their latest 100 likes and recasts, and on a post page that cast's, read from the node as where Allthing writes for them. The heart and the recast icon are pressed for those, and a pressed one opens "Unlike in Farcaster" or "Undo recast in Farcaster". Follow says Following when they follow the account (one public read of the node), offering Unfollow in the app.
- **At once.** Signed in, what a hand-off asks for shows here as the dialog opens, as the reader's but pending (`Writer::hand_off`, `Mine::pending`): the heart filled and the count up, Follow as Following, the Pepe's chip as theirs, each pulsing gently. A cast, a reply or a quote shows where it will be (`components::outgoing`): a reply in its post's thread, under what it answers ([a reply in its thread](#writing-a-cast)), with the reply counts up by one, and a cast or a quote above the home feed (a cast in a channel above that channel's too), dashed, with "Posting in Farcaster". A delete shows once it's done, not before. Closing the dialog without going to the app takes it back (`Ask::dismissed`); opening the link, or Done, keeps it.
- **When it lands.** The browser asks the node whether the reader has done it there (`Writer::watch`): at once, then every 3 s for a minute and every 10 s after, and at once when the page is back in view. A like or a recast is read by `/v1/reactionById`, a follow by `/v1/linkById`, a delete by `/v1/castById`; a cast, a reply, a quote or a Pepe reaction by the reader's 5 latest casts (`/v1/castsByFid`), among which `message::Sent::found` takes the first posted since the hand-off (30 s of clock difference allowed) that is a reply to the same cast, a quote of the same cast, a cast that is neither, or for a reaction a reply that is the emoji and nothing else, the one with the same text first, as the reader may change it in the app. Then it stops pulsing, a cast shows "Posted" and links to itself, the dialog closes if it is still open, and a notice says so ("Liked.", "Posted. View"). Found at the first ask, before the reader can have done anything, a like or a follow was so already (a like older than the reader's latest 100, which the page didn't know of): the button stays turned, the count goes back to the page's, and the notice says "Already done." Not done in 3 minutes (10 for a cast, which takes longer to write), what shows is taken back, and a draft is back in the composer if it holds no other. A newer hand-off of the same takes its place, and signing out ends it all. Signed out, Allthing doesn't know whose app it is: nothing shows at once, and it asks nothing.
- **Scheduled casts** need Allthing to post, so there is no clock in the composer and no "Scheduled casts" in the account menu, and `/scheduled`, with nothing waiting, says why.

Where the Worker does endorse keys (the `ALLTHING_CUSTODY_KEY` secret set), a signed-in reader writes from Allthing instead, with a key they approve once ([Liking and recasting](#liking-and-recasting)); a reader signed out still hands off.

### Scheduled casts

A reader who can post from here can schedule a cast, a reply or a quote for later (`allthing_core::scheduled`, `components/compose.rs`, `pages/scheduled.rs`, `allthing-worker/src/scheduled_casts.rs`, `allthing_data::scheduled`). It is signed in the browser like any other cast; the Worker only keeps it until its time.

1. **Picking a time.** The composer's clock, after the GIF button, opens a date-and-time field in the reader's own time zone, which it names, set to the first quarter hour an hour or more ahead, and **Cast** becomes **Schedule**. The time must be a minute to 30 days ahead; the composer says so before anything is signed. The clock again posts it now after all.
2. **Signing.** The browser builds the cast as it would to post it, mentions and all, and signs it with the reader's key, with the chosen time as its timestamp (`Writer::schedule`). It hands the signed message, in base64, and the draft (what the composer had: its text, GIF or sticker, the cast it answers or quotes, its channel) to `POST /api/v1/scheduled`, not to the node.
3. **Keeping it.** The Worker takes it only from a signed-in session, and from Allthing itself (`Origin`). It checks that the message is a cast by the session's account, well formed (its hash is BLAKE3 of its data), for a minute to 30 days ahead (`scheduled::check`), and keeps it in D1 (`scheduled`, `migrations/0005_scheduled.sql`): 25 waiting per reader at most, drafts up to 6 KB. It doesn't check the signature: the node does, when it is given the cast. Farcaster's nodes refuse a message timestamped more than ten minutes ahead, so a kept cast can't go out early, even if someone took it.
4. **Going out.** Every minute, the indexer's cron run first takes up to 5 casts whose time has come (`sending`, in one D1 statement that also reads them), gives the node `submitMessage` for each, through Hypersnap's guard, as they were signed, and keeps what the node says: posted; failed, with the node's reason (a key no longer on the account says so, and that editing signs it again with the key the browser has now); or, while the node is busy or down, again the next minute, 30 times at most. One the run didn't give the node (its breaker open, its bucket empty, or the run's budget spent) waits again as it was, with no try counted; one a run took and never settled, as when it ended first, is taken again 5 minutes on, and a node given a cast twice says it has it already. A cast goes out within a minute of its time.
5. **The list.** `/scheduled`, in the account menu and linked from the notice and the clock's row, lists the reader's casts waiting, soonest first, with when they go out in the reader's time and how long until; those that didn't go out, with why; and those posted this past week, linked. **Edit** opens the composer with the cast as it was, still scheduled; **Save** signs it again and puts it in the old one's place. **Cancel** deletes the kept message, once the reader confirms; a cast that didn't go out can be edited to try again, or removed. Casts that went out or failed are dropped after a week. The list is one request, `GET /api/v1/scheduled`, never cached.
   - **Confirming.** Cancel (or Remove) asks in its row ("Cancel this cast? It won't go out."), with focus on **Keep it**; Keep it, or Escape, closes the question and puts focus back on Cancel. On a phone the question has a row of its own, its two answers side by side, and the list's buttons take a 44 px tap.
   - **At once.** **Yes, cancel it** (or Yes, remove it) takes the cast off the list at once, while the Worker is asked: it folds away in 180 ms, from its own height, or just goes with reduced motion, and its group's count goes down with it. Focus moves to the cast after it, or the one before; with nothing left waiting, the list says so, and where the composer's clock is, with **Schedule a cast**, which opens the composer with its clock on, and focus goes there. Once the Worker has done it, the notice at the foot of the screen, a polite live region, says "Scheduled cast cancelled" (or "Removed from the list").
   - **When it can't.** If the Worker can't, the cast comes back where it was, with why in its row, and focus on its Cancel, which the error describes. If the cast had already gone out, or the node was being given it, the Worker says so: it becomes a posted one, with **View cast**, under Posted this week, and says it wasn't cancelled. From the moment a run takes a cast until it says what became of it, the Worker answers a change or a cancel that it is too late, so a cast the reader is told is cancelled never goes out.
   - **Asked again.** A cancel of a cast that is gone already says it is cancelled, so one sent twice is answered the same; one of another account's is refused (403).
   - **The menu's count.** The account menu's Scheduled casts says how many are waiting, as far as this browser knows: from the list when it was last read here, and from what was scheduled, changed or cancelled here since, kept in localStorage (`allthing.scheduled`, `scheduled::Known`), so no other page asks the Worker for it. A cast whose time has passed isn't counted, and what another device did shows once the list is read here again.
6. **Tested end to end.** `e2e/scheduled-cron.fixture.spec.ts` runs a Worker of its own, with an empty local D1, and schedules two casts from the composer for the same minute. It runs the cron (`/cdn-cgi/local/scheduled`) before that minute, when nothing goes out, and at it. There, the node is a stand-in on the test's machine, which takes one cast and refuses the other's key as the network does, through the Worker's `HYPERSNAP_ORIGIN` variable. That variable only ever names a local port (`message::is_local_stand_in`); anything else is ignored, and it is never set where Allthing is deployed. The test checks that the node is given each cast byte for byte as the browser signed it, that the list then shows one posted, linked, and the other not, with why, and that the next run gives the node nothing more. It waits for the minute, a minute or two.

### Liking and recasting

A signed-in reader can like and recast from Allthing, and post [casts, replies and quotes](#writing-a-cast), once they have approved an app key in the Farcaster app (`allthing_core::app_key` and `message`, `allthing-worker/src/app_key.rs`, `allthing-web/src/keys.rs` and `components/writer.rs`). That is how Farcaster's apps write for their users: an app key is an Ed25519 key added to the reader's account, and it signs their messages. Allthing asks for it as its own account, @allthingapp (`ALLTHING_FID`, 3356318): the Farcaster app names that account as the app asking, and records it as the key's app, so the casts the key signs show "via Allthing" (`allthing_core::clients::client_name`), linked to the account's profile, here and in apps that name a cast's app after its account's profile.

1. **Who can.** The heart and recast icons under every cast are buttons (`aria-pressed`, a hit area about 30 px across, the icon where it was), and none opens the list of who liked or recasted: pointing at an icon or its count previews them, as before, and the preview's "See everyone" or a click on the count opens the full list (on a touch screen a tap on the count, a target of its own, previews them). A reader signed out who clicks one, or any reader where the Worker endorses no keys, likes or recasts in the Farcaster app ([Handing writes to the Farcaster app](#handing-writes-to-the-farcaster-app)). For a signed-in reader, the app asks `GET /api/v1/signer` once, which the browser keeps for an hour, and a click before the answer waits for it. Where the Worker has the `ALLTHING_CUSTODY_KEY` secret, a click likes or recasts, after approving a key if the reader has none; where it hasn't, the click hands off to the Farcaster app, as a signed-out reader's does. The static copy's icons are pictures.
2. **The key.** A reader who signed in by [approving the key](#signing-in-by-approving-the-key) has one already. Otherwise their first write opens the sign-in dialog in its approve form ([one dialog](#one-dialog-one-approval)). The browser makes an Ed25519 key pair with WebCrypto, unexportable, and keeps it in IndexedDB (`allthing-keys`), one per account. IndexedDB holds the browser's own key object, so the private key never exists as bytes a script could read, and Allthing's servers never see it. A browser without WebCrypto's Ed25519 says so.
3. **The endorsement.** `POST /api/v1/auth/signer` with the public key answers a `SignedKeyRequest`: an EIP-712 signature over (requestFid, key, deadline), in the domain of Farcaster's SignedKeyRequestValidator on OP Mainnet, by the custody address of the account in `ALLTHING_FID`, valid for an hour. `/api/v1/status` names that address (`writes.address`), never the key, so whoever sets the secret can check it is the account's. With `ALLTHING_SPONSOR=1`, the account also pays the onchain fee: a second signature, EIP-191 over the first, which the Farcaster app charges to the account in warps. The validator's own `validate()` accepted a request the Worker signed (`eth_call` on OP Mainnet, 19 October 2026).
4. **The request and the code.** The browser hands the endorsement, as it is, to the Farcaster app's API (`POST api.farcaster.xyz/v2/signed-key-requests`), which answers a token and a `farcaster://signed-key-request?token=…` link. The dialog, "Approve Allthing to write from here", says that one approval lets them cast, reply, quote, like, recast, follow and delete from here. Where a pointer hovers, the Worker draws the link as a QR code for the reader's phone (`/api/v1/auth/qr`, which draws only these and sign-in links), and the dialog shows the code alone, as with sign-in; on a phone, which can't scan its own screen, it shows **Approve in Farcaster**, the link itself, which opens the Farcaster app.
5. **Approval.** The browser polls the request every 2 s (a hidden page doesn't). It shows "Approved" when the reader has approved and, once the Farcaster app has added the key (`completed`), asks Hypersnap for the account's keys (`/v1/signersByFid`) until the new one is listed, for 30 s at most. An approval from an account other than the one signed in is refused, and its key forgotten. A request left when the dialog is closed is kept until its endorsement lapses: the next like shows the same code, and a page load finds it approved if it was meanwhile. Then the like or recast that opened the dialog goes out.
6. **A like.** The browser builds the message as Snapchain's `message.proto` defines it (`allthing_core::message`: `MessageData` with the reader's fid, Farcaster time, mainnet and a `ReactionBody`), hashes it with BLAKE3 (its first 20 bytes), signs the hash with the key, and posts the envelope to Hypersnap's `submitMessage` (`application/octet-stream`), which passes it to Snapchain's validators. The button and its count change at once, and pulse until the node shows the like; it is then the reader's, or, if it doesn't show, it is undone ([How a write lands](#how-a-write-lands)). A message that undoes another is dated at least a second later, so it wins. A key the node doesn't know was removed in the Farcaster app, unless it was approved in the last 5 minutes, when the message is sent again after 2, 4 and 8 s: it is forgotten, the like is undone, and the notice offers **Approve again**, which opens the dialog for a new key and then likes.
7. **What the reader liked.** With a key, the browser reads the reader's latest 100 likes and 100 recasts from Hypersnap (`/v1/reactionsByFid`), and on a post page whether they liked and recasted that cast (`/v1/reactionById`). A like or a recast from here keeps the count it made: a page read before it, or from a cache, shows at least that many (or, taken back, at most), while the node says it stands (`Mine::counted`). The tab keeps those counts for 10 minutes (`allthing-reacted`), for reloads, and the cast's page and its lists of who liked and recasted are [refreshed](#writing-a-cast).
8. **Following, and deleting one's casts.** On anyone else's profile, a reader who can like sees **Follow** beside the name, once Hypersnap has said whether they follow the account already (`/v1/linkById`, one read from the browser per profile view, which needs no key); until then its place is kept, empty. Hovering **Following** offers **Unfollow**. Each is a `LinkAdd` or `LinkRemove` of type `follow` (`message::Body::Follow` and `Unfollow`), signed and handed to the node like a like, dated a second after the one it undoes, and the profile's follower count follows along. Under their own post and replies the reader sees **Delete**, which asks once more in place ("Delete this cast?", with **Keep** focused) and sends a `CastRemove` with the cast's hash (`Body::CastRemove`), showing "Deleting…" until the node no longer has the cast. The cast then reads "You deleted this cast." wherever it shows in that tab, after a reload too (`sessionStorage`), since cached pages may still carry it for a while.
9. **Off.** The account menu's **Revoke permissions**, and signing out, forget the key (`Writer::turn_off`, `WriterMenuItem`). Revoke permissions takes two clicks: the first arms it ("Click again to revoke", or "Tap again" on a touch screen, a gentle warning), and a second within 5 s revokes; it disarms after those 5 s, on Escape, when the pointer or focus leaves it for more than a moment, and as the menu closes. What it does is said under it, in Allthing's tooltip look (never a native tooltip), on hover after a moment, on keyboard focus, and once armed, phones included, as the button's description (`aria-describedby`); the menu grows to hold it, as a tooltip over its rows would make the menu, a scrolling box, scroll: writing from this browser stops until the reader approves Allthing again, they stay signed in, casts they scheduled still go out (signed already, the Worker keeps them), and the key stays on their account, among the Farcaster app's connected apps, until they remove it there. Nothing changes on chain: only the reader can remove a key from their account, in the Farcaster app, as Allthing connects no wallets. A notice then says "Write permission revoked in this browser." Tabs tell each other when a key is approved or forgotten.

#### How a write lands

Hypersnap is a read node of Snapchain mainnet: its `submitMessage` checks a message against the network as it stands and passes it to Snapchain's validators, and its answer (200) says it took it, not that the network merged it. The validators can still drop it. The node's own store has the message only once a block of theirs holds it, so after the node takes a message (or says it has it already), the browser reads it back from the store, after 0.5, 1.5, 3, 5, 8 and 15 s, until it shows (`message::read_back`, in writing's own code: `send`, `hand_in`, `confirm` in `components/writer.rs`). Only then does what the page shows stand; meanwhile the write pulses. Every message is signed in the browser by the reader's app key (`signer`), the one they approved for @allthingapp (FID 3356318), and goes from the browser to Hypersnap (`message::NODE`).

Writes land within a few seconds. On 21 October 2026, joining each `MERGE_MESSAGE` in Hypersnap's `/v1/events` (shards 1 and 2, the latest 1,000 events of each) to its block's `BLOCK_CONFIRMED`, blocks came every 1.01 s on both shards, and a message's block came after its own timestamp by 0 s at the median, 1 s at the 90th percentile and 2–3 s at the 99th for likes and recasts (140 of them, 3 s at most), by 2–4 s at the 99th for casts (68, 4 s at most), and by 1 s at most for follows; `/v1/info` put the node 0–2 s behind each shard. So a write shows within about 6 s, which the looks up to 8 s cover. The last, at 15 s, is for a node running behind: without it, a like that landed would be undone, and come back on the next page load.

| Write | Message | At once | Read back | Not shown within 15 s, refused, or the node out of reach |
|---|---|---|---|---|
| Like, recast | `ReactionAdd` (type 3) of the cast's id | the button pressed, the count one more, both pulsing | `reactionById`: a like or recast with this message's hash | undone exactly: the button and the count as they were, with why; Retry likes again |
| Unlike, undo a recast | `ReactionRemove` (4) | unpressed, one less, pulsing | `reactionById`: none there | the like or recast back as it was; Retry |
| A quote (or a cast or reply) | `CastAdd` (1); a quote embeds the quoted cast's `CastId` | the composer closes, and the cast shows above the reader's feed and on their profile (a reply in its thread, at once), "Posting…" | `castById` by its own hash | its card goes, the draft is back in the composer if that holds no other (a reply's opens again, with why), and Retry hands the node the same signed message |
| Deleting one's cast, a quote too | `CastRemove` (2) of its hash | "Deleting…" | `castById`: the cast gone | the cast stays, with why; Retry |
| Follow, unfollow | `LinkAdd`, `LinkRemove` (5, 6) of type `follow` | Following, the follower count one more, pulsing | `linkById` | as it was; Retry |
| A Pepe reaction | `CastAdd`: a reply that is the Pepe | "Reacting…" | `castById` | Retry hands the node the same reply |

What the node answers decides the rest (`message::submitted`):

- **Taken** (2xx): read back as above.
- **A duplicate** (`bad_request.duplicate`: the node has this very message, as when the answer to the first try was lost): as taken, and counted once, since it is the same message.
- **Busy or out of reach** (429, 5xx, no answer, or a 400 whose gRPC status is `Unavailable` or `Internal`: Hypersnap answers every failure with 400, its own too): the same bytes again after 1, 2 and 4 s; then it's taken back, "Couldn't reach Farcaster's network", with Retry.
- **The key unknown**: as in step 6.
- **Refused for another reason**: taken back, with the node's words ("Farcaster didn't take it: …"); no Retry, as the same would be refused again.

A like or a follow the node shows by another of the reader's messages (liked before, beyond the latest 100 the page knows, or in another app) stands, with the count the page read, which had it. Retry makes a like, a recast, a follow or a delete again, a new message (reactions and follows are sets: none counts twice), and hands a cast to the node again as it was signed, which the node keeps once. A notice with a button stays 15 s.

No other public node takes a browser's messages without a key we'd hold: Neynar's hub and Snapchain APIs answer 402 without an API key or an x402 payment, Farcaster's own node (`crackle.farcaster.xyz`) is password-protected, and Pinata's, wevm's and Standard Crypto's public hubs are gone. So writes go to Hypersnap and are read back from it. That still shows the network merged them, since a read node's store takes only what the validators' blocks hold (Hypersnap's `/v1/info` gives each message shard's `mempoolSize` as 4294967295: a read node keeps no mempool of its own). Hypersnap asks for no key, allowlist or origin: it answers any origin (`access-control-allow-origin: *`) and takes messages without credentials, and it limits no rate itself: once it has checked a message, a read node's mempool only looks for a duplicate and passes it on. Snapchain's validators can limit each account (100 messages an hour at least, more with more storage, where their operators turn it on), and a message they drop doesn't show, so it is taken back like any other.

The Worker never holds a reader's key or signs as a reader, and submits to Farcaster nothing but the [scheduled casts](#scheduled-casts) readers' browsers signed; its custody key endorses keys and nothing else. That key controls the whole of the account it belongs to, @allthingapp (moving it, changing its recovery address, adding and removing its keys), so it lives only in the Worker's secret, set in Cloudflare; the Worker never logs or returns it, and `/status` shows only its address. Any signed-in browser, or one signing in, can have a key of its own endorsed, so someone could show another person a key request in Allthing's name: the Farcaster app shows that @allthingapp asks, and whoever approves gives the request's key holder write access to their account. Endorsements last an hour, so such a request lapses quickly; it is the same trust that any app making signed key requests extends to its signed-in users.

## Attachments

A signed-in reader can attach images and videos to a cast. The Worker keeps them in R2, in the bucket `allthing-media` (the `MEDIA` binding), and serves them on the site's own origin, so the URL a cast embeds is Allthing's and any Farcaster app can load it (`allthing_core::media`, `allthing-worker/src/media.rs`). The composer attaches them ([Writing a cast](#writing-a-cast)) once `GET /api/v1/media` says this server takes them.

- **Uploading.** `POST /api/v1/media`, with the file itself as the body, its type as `Content-Type` and its size as `Content-Length`, from a signed-in session and from Allthing itself (`Origin`). It takes PNG, JPEG, GIF and WebP images up to 10 MiB, and MP4, MOV (QuickTime) and WebM videos up to 250 MiB. Images and small videos use this single request (internally stored through an abortable R2 multipart upload); larger videos use the multipart flow below, keeping each request under the zone’s 100 MB limit. It answers `{"url","type","bytes"}`. The URL is `https://allthing.social/m/<fid>/<id>.<ext>`: the reader's fid, 16 random bytes in hex (`crypto.getRandomValues`) and the type's extension, 84 bytes at most, well within a cast embed's 256. A cast carries two embeds at most.
- **Larger videos.** `POST /api/v1/media?upload=create` takes a bounded JSON descriptor (`id`, `type`, `bytes`, optional `hls`) and atomically reserves the reader's quota and storage before any data is sent. The browser creates a random 32-hex correlation id so a lost create response can be retried safely. The authenticated account owns the session; object keys and R2 upload ids are never accepted from the client. `?upload=part&id=…&part=N` streams exact 8 MiB parts (a shorter final part), and returns `{part_number,etag}`. Parts are recorded in order; a repeated acknowledged part returns its prior receipt. `?upload=complete&id=…` accepts the exact ordered receipts and returns the normal attachment response once storage and accounting are complete. Repeated completion returns the same URL. Retry in the same draft continues from the last acknowledged part. Remove calls `?upload=abort&id=…`, including before create completes; cancellation prevents later publication. Abandoned sessions are reclaimed at most one every other existing index-cron tick, within its reserved subrequest allowance. Pending sessions are capped at 128 globally. Reservations are released only after R2 confirms abort or deletion, never on time alone.
- **The Worker never reads the bytes.** It hands the request's own body stream to R2’s multipart part upload as a JavaScript value, so no byte of a file passes through WebAssembly, and an upload costs the same CPU at 1 KB as at 50 MB: the Worker's WebAssembly memory stayed at 1.31 MiB through two 45 MiB uploads, and the work around the stream is about a microsecond of Rust ([BUDGET.md](BUDGET.md#12-attachments-r2)). So nothing looks inside a file either: it is kept as the type it was declared, which must be one of the seven, and it is only ever served as that type.
- **Quotas**, counted in D1 (`media`, one row a file, `migrations/0007_media.sql`): per reader, 300 MiB and 60 files in any 24 hours; 2,000 files a UTC day from everyone together, with a separate 1,000 upload-work-attempt cap shared by multipart requests and the compatible single-file endpoint; and 9 GiB stored in all, under R2's free 10 GB-month. `media_total` keeps the sums (`all`, and a row a day), so a check reads the reader's own index entries for the day and two rows. Pending uploads reserve the same quotas atomically before anything is stored; past one, the answer is 507 and why, with when the reader's day, or the site's, frees up (`Retry-After`). A reader may also start 20 uploads a minute in each isolate (429), under the API's per-IP limit. Once R2 has a file, the Worker records it and adds it to the sums, in one D1 batch; a file it can't record, or that didn't arrive whole, is deleted again. Both run under `waitUntil`, so a reader who leaves as their file arrives leaves nothing stored that isn't counted. A cast never uploaded leaves its files kept and counted.
- **Serving.** `GET /m/<fid>/<id>.<ext>` (and `HEAD`) streams the file from R2 into the response, without the Cache API: every view is a Worker request anyway, and R2's free reads are many times what the Worker's daily requests could use. A `Range` gets those bytes (206, as Safari's video player asks for them; 416 past the end), and an `If-None-Match` naming the file 304. Each answer has the type kept with the file (one of the seven, or else `application/octet-stream`), `Cache-Control: public, max-age=31536000, immutable` (a name is never reused), `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; img-src 'self'; media-src 'self'; style-src 'unsafe-inline'; sandbox`, `Cross-Origin-Resource-Policy: cross-origin` and `Access-Control-Allow-Origin: *`. So a file that isn't what it says, opened in a tab of its own, runs nothing and loads nothing but itself, while the browser's own viewer still shows an image and plays a video (with `default-src 'none'` alone, a video opened in a tab wouldn't play). The path is read strictly: an fid, 32 lowercase hex digits and one of the seven extensions; anything else is 404, as is every path without the binding.
- **Videos for the Farcaster app.** The Farcaster app plays only HLS in a cast: an `.m3u8` from any host shows as a video (its server reads the stream for the size and a thumbnail), and an `.mp4` as "No preview found for shared link", however it is served (checked on 22 October 2026 against casts with live MP4s on other hosts, through the app's own API). So the composer remuxes an MP4 or MOV in the browser before uploading it (`allthing_core::fmp4`). It reads only bounded box headers and up to 8 MiB of movie metadata, then builds a Blob from small generated headers and slices of the original file; media payload bytes never need a full-file ArrayBuffer or a WebAssembly copy. Preparation yields between bounded steps, and preparation, upload progress and finishing have distinct visible states. This is lossless repackaging, not transcoding: the same coded samples, as one fragmented MP4, an init segment then a `moof` and `mdat` from each key frame at least 4 s after the last (fewer, longer segments for a long video, 80 at most), without `udta` and `meta`, where a phone writes where and with what it was recorded. Only H.264 or HEVC video, with AAC audio or none, is remuxed, which every HLS player decodes in fragmented MP4; anything else goes as it is. The upload carries the index (`x-allthing-hls`: size, codecs, the init's length and each segment's milliseconds and bytes); the Worker checks that it parses and adds up to the file, keeps it as the object's R2 custom metadata (2 KiB at most), and answers the playlist's URL, `/m/<fid>/<id>.m3u8`, which the cast embeds. From that metadata alone, it writes the master playlist (one rendition: `RESOLUTION`, `CODECS`, `BANDWIDTH`) and, at `<id>.v.m3u8`, the media playlist, whose `EXT-X-MAP` and segments are byte ranges of `<id>.mp4` (HLS version 7). Allthing's own player plays the MP4, which any browser plays by itself, in place of its own playlist (`media::progressive_of`).
- **Not set up.** A Worker without the bucket's binding ([DEPLOY.md](DEPLOY.md#attachments-r2)) answers 404 to uploads, `GET /api/v1/media` and `/m/`, and `/api/v1/status` says `media.ready: false`. allthing.social has had the binding since 21 October 2026.
- **Elsewhere.** Farcaster apps show an image embed by its type, which the Worker gives truthfully to a `HEAD` or a `GET` (Neynar's crawler, for one, records an embed's `content_type`). The Farcaster app's documentation describes video embeds as HLS playlists from domains its team has enabled, so there a plain MP4, MOV or WebM link may show as a link. Allthing plays MP4 and WebM itself.
- **Tested end to end.** `e2e/media-upload.fixture.spec.ts` runs a Worker of its own from `wrangler.toml` and its R2 binding, with a local R2 and an empty D1. It uploads an image and a video and reads them back byte for byte, in ranges, with their headers; refuses the wrong type, sizes, session, origin and pace; holds a reader to 60 files a day, everyone to 2,000 uploads a day and 9 GiB, with D1 seeded; opens an HTML file declared as a PNG in a browser, which shows it as a broken image and runs none of it; and checks that a Worker from `wrangler.toml` without the binding answers 404.

## Notifications

A [signed-in](#sign-in) reader's notifications: who liked, recasted, replied to, mentioned and quoted their casts, and who followed them (`allthing_core::notifications`, `allthing_data::pages::notifications`, `GET /api/v1/notifications`).

- **Whose.** The Worker reads the account from the session cookie, never from the query, and answers 401 without one. The static copy has no sign-in, and so none.
- **Where they come from.** Hypersnap's `notifications?fid=` lists a page of what happened to an account, newest first, with a cursor for older ones. Each item repeats its person and its cast whole, about 3 KB, so the Worker reads 30 a page (about 100 KB; [BUDGET.md](BUDGET.md#4-cpu-time)). It names three kinds only, `likes`, `follows` and `reply`, which `normalize::notifications` reads with two quirks:
  - **A recast comes as one more like**, the same item to the byte: an account that liked and recasted a cast shows twice, and one that only recasted shows as a like. So for the casts liked on the page that may have recasts, the Worker reads the hub's newest ones (`/v1/reactionsByCast` with `reverse`, 10 of each shard's; not `reactions/cast`, which lists each shard's oldest first and stops at its limit, so a cast with more recasts than that would show its first recasters, not its latest), and the item nearest in time to an account's recast is the recast (`notifications::sort_reactions`). The first page also reads the reader's 10 latest casts, and a cast whose count of recasts is the number of accounts that show twice on it needs no read. Six casts a page at most, the most recently liked first; for a cast not read, of an account's two items the later is the recast (people mostly like, then recast, seconds apart), and a single item stays a like.
  - **A mention or a quote comes as a reply** (`notifications::classify`): a cast that replies to one of the reader's is a reply, even one that mentions them too; one that quotes one of theirs is a quote; and one that mentions them is a mention.
- **Quotes** that neither reply to nor mention the reader aren't listed at all. With the first page, the Worker reads the quotes of the reader's 4 newest casts, replies last (`cast/quotes`), and keeps those at least as new as the page's oldest item, or all of them on a last page, since later pages don't read them.
- **What's left out**: the reader's own doings, and replies, mentions and quotes that are spam or mini apps (`Cast::hidden`, their links checked as a listing's are), as listings leave them out. The browser additionally applies the reader's [private Mute and Block](#private-mute-and-block) choices to whole groups and their unread counts; the Worker has no shared account blacklist.
- **Grouped as the Farcaster app groups them** (`notifications::group`): likes of one cast together ("alice and 5 others liked your cast"), recasts of one cast together, follows on one UTC day together ("alice and 3 others followed you"), and each reply, mention and quote on its own. A person counts once in a group, which keeps its 5 newest people and how many there are. Groups are in the order of their newest event. A page is a page of Hypersnap's: likes of one cast on two pages are two groups.
- **The payload** (`NotificationsPayload`) holds the groups (each with its kind, people, count, newest time, and the cast it's about: its hash and its start, `notifications::excerpt`), compact account `references` gathered before text/actor truncation, the cursor of the next page, the newest time, and in `notes` the profile cards of the people shown, from the user objects that come with them, and the verdicts on their casts' links, carried to the next build. It is cached at the edge per account and page, fresh for a minute and served while one rebuild runs for ten, and answered `private, no-store`, so no browser or shared cache keeps one reader's for another.
- **Read state follows the account.** The app keeps the newest notification time seen in the existing localStorage cache (`allthing-notifications-seen`, `{"<fid>": <Unix seconds>}`), so local reads and other tabs still work offline. `allthing_core::notification_state::ReadState` merges local progress, acknowledged writes and remote progress by maximum; failed writes remain pending, stale values never move the marker back, and invalid/future clocks cannot poison it. SpacetimeDB keeps only a private identity-to-FID binding (`notification_reader`) and one `notification_state(fid, seen_at)` watermark per account, with no notification content. Its `my_notification_state` view selects only the caller's attested FID. Tabs stay in the URL; only read progress syncs.
- **Background synchronization** (`notification_sync.rs`) is initially scheduled two seconds after account setup, waits for the page's API work to settle and browser idle time, and connects only while visible and online. A cached `/api/v1/status` capability check must advertise `spacetime.attest` before the shared SDK or socket loads. It uses a private synchronization identity/token in IndexedDB `allthing-notification-sync`, store `identities`, then a Worker attestation, `verify_notification_fid` and a subscription to `my_notification_state`. With `spacetime.library`, that socket also carries private Library metadata and bounded membership/page views; foreground Library/Home readiness skips the initial delay and unrelated API waits, while still yielding to browser idle time. It never registers a chat user, publishes a DM key, subscribes to chat or changes public presence. Writes coalesce for 200 ms with one in flight; remote updates are not echoed. Connection/subscription/reducer waits are bounded to 30 seconds; failures retry with backoff, and online/focus/visibility events wake sync. Sign-out/account changes stop the old connection and fence late completions, including A → B → A.
- **The bell** (`components/notifications.rs`), for a signed-in reader, sits beside the account's picture in the header: a link to `/notifications` with a badge of the visible groups not seen ("9+" past nine), named "Notifications, N unread" for screen readers, and marked as the current page there. The app reads the first page when it starts, every 3 minutes while the page is in view, and when it comes back into view or its window regains focus; a read within a minute is reused (`api`). When someone signs out or someone else signs in, here or in another tab, the app forgets the last reader's answers, and keeps none still on its way, and the page starts its list anew, so nothing of one reader's shows for the next. The bell decodes each group's lightweight time and account references (`notifications::Times`), enough to apply private filters without rendering the whole payload. The static copy has no bell.
- **The page**, `/notifications` (`pages/notifications.rs`), is code of its own (`split_notifications.wasm`), fetched as the bell is pointed at, touched or focused, or with the app when a visit starts on it (`index.html`'s early parts). It has the tabs All, Mentions (mentions, and quotes that mention the reader) and Replies, kept in the URL (`?tab=`) and moved through with the arrow keys, Home and End as a tab list. Each row has its kind's icon, up to 5 faces, its sentence ("**Alice** and 5 others liked your cast"), the cast's start with its Pepe as cards show them (`ExcerptText`), and when. A row opens its cast, or for follows the newest follower's profile; a face or a name links to that profile and opens its profile card. Groups newer than what the reader had seen before the visit are tinted, with an accent bar, while opening the page marks everything up to its newest seen, so the bell clears. If the initial remote watermark arrives after a cold page paints, it reconciles that visit's baseline once before pending local progress is uploaded; subsequent remote reads update the bell/cache without changing that visit's row tint. **Load more** reads the next page by its cursor, after the first; then the first page stays as it is, so nothing slips between two. Signed out, the page asks the reader to sign in; a read that fails says why, with **Try again**; placeholder rows hold the list's place while the data comes. On a touch screen, each face and name takes a 44 px tap of its own.
- **What it can't see.** Recasts come only as Hypersnap's likes do, and the hub's newest 10 a shard, for 6 casts a page; quotes only of the reader's 4 newest casts, with the first page. Hypersnap names no other kinds.

### Counts as current as notifications

Notifications and counts come from the same node (Hypersnap), and a like or reply should show on the post before, or as soon as, the bell says so. The post's own read (`/api/v1/cast`) and replies previews are fresh for 30 s at the edge (notifications: 60 s) and kept 30 s by the app. While a page is in view and the reader is active, `allthing-web/src/counts.rs` asks every 30 s for the counts of what is in view, `/api/v1/counts?casts=…` (up to 12 hashes, sorted: one bulk `casts` read at the Worker, fresh 15 s): each run of six feed cards in view (the runs the engagement batches follow, so readers share them), and an open post with its first 11 replies. `Engagement` (`components/chips.rs`) shows the newest count read; the writer's merge (`Writer::shown_count`, `replies_shown`) still applies on top, so a reader's own like, recast or reply waiting to land is never undone. Counts change in place, in rows whose height doesn't change. New replies are not pushed into an open thread: a "N new replies" button floats over the page, and reads the post again when pressed.

## Messages on SpacetimeDB
The public `#general` room and end-to-end encrypted conversations (Messages) live in a SpacetimeDB database, `allthing` on maincloud, off Farcaster: nothing is written to Snapchain. The module is in `spacetime/spacetimedb` (its handoff, schema and reducers in `spacetime/HANDOFF.md`), checked by CI's `SpacetimeDB module` job.
- **Who is who.** A browser connects with its own SpacetimeDB identity. After Sign In With Farcaster, it asks the Worker for an attestation (`POST /api/v1/auth/attest`): the Ed25519 signature, by the `ATTEST_KEY` secret, of its identity, the signed-in account and an expiry 10 minutes on (`allthing_core::stdb`, `crates/allthing-worker/src/attest.rs`). The module's `verify_fid` checks it against the public half pinned in `attest_key.rs` (ed25519-dalek, strict), against the caller's own identity, so an attestation is no use to anyone else, and marks the identity's FID verified. Once a key is pinned, only verified identities can publish a key, chat, create rooms or send messages. The key is the Worker's own; it is never the custody key, and the Worker never holds a reader's key.
- **The client.** `/messages`, from the account menu, is one inbox (`pages/messages`): a list of conversations, Allthing's public `#general` room first, then the reader's encrypted conversations, newest first; the one open beside it (`?room=general`, `?to=<fid>`), or New message (`?new=1`), which finds a person by name with the site's search. On a phone the list and the open conversation take turns, with a back button. Enter sends, Shift+Enter starts a new line. It asks for no API key and calls no Farcaster Direct Cast API: Farcaster's own Direct Casts stay in the Farcaster app. The page is a split part of its own (`split_realtime.wasm`, `pages/messages/realtime`), and it shares the SpacetimeDB TypeScript SDK, loaded once as a bundled module script, `assets/stdb-<hash>.js` (`web/stdb/bridge.ts`, `xtask/src/browser_assets.rs`), for a signed-in reader only. The Rust SDK builds for browsers but is BSL-1.1, which the license audit refuses. The Messages split part stays page-specific; eligible signed-in notification sync may load the shared SDK earlier through `stdb_bridge::load_bridge`. Names and pictures come from Hypersnap's `user/bulk`. The browser keeps its SpacetimeDB token and an X25519 key pair (WebCrypto, unexportable) in IndexedDB `allthing-stdb`, one record per account. After connecting it calls `register`, then `verify_fid` with the Worker's attestation, then `set_public_key`. Signed out, the page asks the reader to sign in; the static copy points to allthing.social. Tested by `e2e/realtime-messages.fixture.spec.ts` at 1280 and 390, with a stand-in database (axe included).
- **Content Security Policy.** SpacetimeDB 2.13.0 builds product and sum codecs with `Function`, which the site’s existing policy rejects. `web/stdb/csp-codec.ts`, imported before the generated bindings, replaces only those public codec factories with cached closures; SDK primitive and array codecs and BSATN wire encoding stay in use. `xtask/src/browser_assets.rs` requires a deliberate adapter review when the SDK version changes. `tests/stdb-codecs.test.mjs` compares wire bytes and decoded values with the unmodified SDK, including recursive types and inherited field names. `e2e/stdb-csp.fixture.spec.ts` runs the actual bundled SDK under the production policy against a BSATN WebSocket peer and mock Worker attestation: connection, rows, online count, verification and sending must work without a CSP violation. The mock attestation does not replace the release check with a real signed-in account and the live module. No `unsafe-eval` permission is added.
- **Encryption** is in `allthing_core::e2e`: X25519 (WebCrypto), then HKDF-SHA256, then XChaCha20-Poly1305, with associated data that binds both parties, their key versions and their keys. The explainer (`components/encryption.rs`, text in `e2e::messages_explainer`) is reusable by later encrypted features.

## Allthing's poll

The front page asks its readers one question of Allthing's own: "Would you like an Allthing mobile client?", Yes or No (`allthing_core::poll`, the poll `mobile-client-v1`). Anyone can vote, signed in or not.

- **Where it shows.** On the front page only (hot, new and top, and every time range), as one card in two places (`components/poll.rs`), labelled "Allthing poll". From 1280 px wide, it sits in the gutter right of the feed, placed beside the feed's column, which doesn't move, and stays in view under the header as the feed scrolls (`position: sticky`). Narrower, it is a card after the feed's fourth (`CastList`'s inset), drawn with the cards around it and kept after the fourth as they are sorted again: it comes once the four before it are drawn, it is keyed by the card it follows, so a list drawn anew (another sort, time range or tab) draws it anew too, as its cards are, rather than moving it, and it is laid out as they are (`content-visibility: auto`, its height kept while the front page is kept, `kept.rs`), so a new list never shifts it into view. The early renderer's first cards don't have it, so on a narrow screen they stop at the fourth, and nothing moves when the app takes over from them. Its body keeps one height (112 px), asking or showing the results, so a vote moves nothing. What fills the body (Yes and No, the results, voting, and reading and keeping the vote) is code of its own (`split_poll.wasm`), fetched once the front page is idle: the card's frame, with its question and its body's box, is drawn with the cards, and the body fills in place.
- **Voting.** Before a vote it shows no numbers. Yes or No shows pressed at once, and both wait while `POST /api/v1/poll` (`{"poll":"mobile-client-v1","choice":"yes"|"no"}`) is answered. Counted, the card shows each answer's share and count ("Yes 63% (5)", in whole percents that add up to 100, by the largest remainder), how many voted, and "You voted Yes.", and a polite live region says it all. A vote that doesn't go through (no answer, a 5xx) gives the buttons back, with why.
- **One vote per network.** The Worker counts a vote for the address Cloudflare saw it come from (`CF-Connecting-IP`): an IPv4 address, or an IPv6 address's /64, which one device's addresses rotate within (an IPv4 address written as IPv6 is that IPv4 address). A network that has voted is told so, with the counts, and never which way it voted: "A vote from your network was already counted." People who share an address, behind an office's or a carrier's NAT (common on phones), share one vote, and a reader on two networks can vote twice: it is a show of hands, not a count of people.
- **What is kept.** For each network that voted, D1 keeps an HMAC-SHA256 of the poll and the network, keyed with the `SESSION_SECRET` secret (of `allthing poll v1`, a newline and `mobile-client-v1|<network>`), in hex, and its choice (`poll_votes`, from `migrations/0008_poll.sql`), and each answer's count (`poll_counts`). Never the address: it isn't logged, kept or answered with. Without the secret the keys can't be matched to addresses, and with the poll in them, a network's votes in two polls can't be matched to each other. One D1 batch, one transaction, counts the vote and keeps it unless the network has voted, and reads the counts, so a vote counts once and nothing counts the votes again. Changing the secret lets every network vote again.
- **Checks.** It takes votes from Allthing's own pages only (`Origin`; 403 otherwise), well formed and 256 bytes at most (400), under the per-client limit (`API_LIMITER`). Its answers are never cached (`no-store`). Without the secret, or D1, it answers 503 "Polls aren't set up here", the card goes, and `/api/v1/status` says `poll.ready: false`.
- **Kept in the browser.** The vote, the counts it was answered with and when are kept in localStorage (`allthing-poll`), so a later visit shows the results without asking. The front page's payload carries the counts too (`poll`, on the first page, once anyone has voted: one D1 read of two rows, beside the trending read), and the card shows whichever were counted later, the payload's (`meta.fetched_at`) or the vote's own.
- **The static copy** has no Worker to vote with, and no poll.
- **Tested** by `e2e/poll.fixture.spec.ts` at 1280 and 390 px (where it shows and that it moves nothing, voting, the results kept, a network that has voted, a vote that didn't go through, a server that keeps no votes, newer counts, axe, and the static copy) and `e2e/poll-worker.fixture.spec.ts`, which runs a Worker of its own with a local D1 (wrangler dev passes a request's `CF-Connecting-IP` on, so each vote comes from the address it names).

## Presence

The header's small "● 12" says how many people are reading Allthing now. Hovering it, a click, a tap or Enter opens a popover with those of them who show themselves by name (`allthing_core::presence`, `allthing-web/src/components/presence.rs`, `allthing-worker/src/presence.rs`). It is in front of the Worker only; the static copy has none.

- **The beat.** A browser tells the Worker it is here with `POST /api/v1/presence`, whose JSON body (256 bytes at most) is its id and whether a signed-in reader hides: `{"id","hidden","refresh"}`. A beat is never part of a page view, which still makes one API call: the first goes once the page's own call is in and the browser is idle (`requestIdleCallback`), two seconds after the app starts at the soonest, and only from a visible tab. After that, one goes every `next` seconds, the interval the Worker answers with, while the tab is visible, online and in use: a pointer, a key, a scroll or a touch in the last five minutes, or a video playing. A hidden or idle tab sends nothing, and back in view or in use, it beats at once if its turn has passed.
- **One tab beats for the browser.** localStorage `allthing.presence` keeps the browser's id, the UTC day it was made, when a tab of it last beat, the interval and the answer. A tab looks when its turn comes (the interval plus 0–30 seconds of positive jitter for each tab) and beats only if no tab has meanwhile, claiming the turn first; otherwise it shows what the other tab heard, which the `storage` event brings it. Navigating, reloading and opening tabs within the interval cost nothing.
- **The interval adapts.** `next = clamp(10 × online, 240, 900)` seconds, and a reader counts as here for `next + 60` seconds after their last beat. Up to about 90 readers at once, that is at most 8,640 beats a day in all; past that, each reader adds about 96 ([BUDGET.md](BUDGET.md#14-presence)).
- **What is stored, and for how long** (D1, `presence`, `migrations/0009_presence.sql`): a row per visitor, `visitor`, `fid` and `seen` (the last beat's second).
  - A signed-in reader who shows themselves is `f:<fid>`, from the sealed session cookie: never from anything the browser says, a fid, a name or a picture in the beat, or the readable `__Host-allthing-user` cookie. Kept by account, one reader on two devices counts once.
  - Anyone else is `a:` and the hex of an HMAC-SHA256 of their browser's id under `SESSION_SECRET` (`auth::mac`, for `allthing presence v1`), with no fid. The id is 16 random bytes that the browser makes afresh each UTC day, so a browser can be told apart within a day and never across days. It is never stored.
  - A row is written at most once a minute, and deleted at a recount once it is 1,000 s old: the table holds the last quarter of an hour at most. It has no index besides its key, since an index row would double every write.
  - No IP, user agent or raw id is ever stored or logged.
- **Counted, never named.** The answer is `{"online","readers","next"}`: how many were seen in the window; up to 12 of those shown by name, most recent first, with their names and pictures from Hypersnap's `user/bulk`; and the interval. Nothing else is said about anyone, and the popover says "and N more" for the rest.
- **The opt-out.** The popover has a "Show me here" switch for a signed-in reader, on unless they turn it off, kept in localStorage `allthing.presence-hidden`. Off, the browser beats at once with `hidden: true`: the Worker stores the reader as one signed out and deletes their row by name, so they are counted and not named. On again, it beats at once too, atomically replacing its anonymous row with its named row, so the count never includes both. Signing out deletes the authenticated named row before the session is cleared. A reader who shows themselves but is missing from an answer counted before their beat leads the list in their own browser without increasing the server's count.
- **On the Worker.** A beat must come from Allthing itself (`Origin`, else 403) with a well-formed id (else 400); `API_LIMITER` applies, and every answer is `no-store`. Its work: the answer this Cloudflare location counted, from the Cache API, which is kept 30 s; one D1 batch, which always writes the beat, and only where that answer is missing or 30 s old also deletes the rows past keeping and counts who was seen in the window, with those shown by name, in one more pass; on that recount, `user/bulk` for those named; then the new answer, cached. Ordinary public beats reuse a count for 30 seconds; hiding, an account change (`refresh`) or a newly public reader forces a recount. Every cached response checks its at most twelve named rows in the same D1 batch, so a hide processed by another location cannot leak through an old cached list. Other open clients drop the name on their next beat; there is no push subscription. A beat makes at most four subrequests, plus the schema once per isolate.
- **The chip.** A 6 px green dot and the count in 12.5 px muted text, with no frame and no word: "● 12". Its accessible name is "12 readers online" (`chip_name`), and it has no native tooltip. Home and DAU stay visible: the chip sits after the navigation, out of the flow, so it moves nothing as it comes, and fades in over 600 ms (not under reduced motion), as a new count does. At 920 px and narrower it stays visible as a compact dot and count. Both the boot and app headers reserve its width before the count arrives, keeping Home, DAU and the search box clear, including on phones. The count is `format::short_number` (1.2k), and at least 1, the reader being here. Escape closes the popover and puts focus back on the chip, which a key opens and focus alone doesn't.
- **Off.** `PRESENCE = "on"` in `wrangler.toml`'s `[vars]` turns it on, and `/api/v1/status` says `presence.ready`. With anything else, the endpoint answers 404, and a browser shows no chip and sends no beat for 6 hours. It is the same where `SESSION_SECRET` isn't set (503, "Presence isn't set up here"). See [DEPLOY.md](DEPLOY.md#presence).
- **Tested** by `e2e/presence.fixture.spec.ts` at 1280, 920 and 390: the chip coming after the page's own call and moving nothing (CLS 0), Home kept, and the chip visible and clear of the search box from 360 to 1280 px; the popover by hover, click and keyboard; the opt-out; no beat from a hidden tab or after five idle minutes (a fake clock); one beat for two tabs; the early paint's header; axe. `e2e/presence-worker.fixture.spec.ts` runs a Worker of its own with a local D1 and a stand-in node: counting, naming, hiding, pruning, refusals, the rows' contents, and presence off.

## Security and privacy

- **Reads, and a reader's own likes, recasts, casts, follows and deletions**: the Worker posts nothing of its own. Until the Worker endorses keys, as on allthing.social until its `ALLTHING_CUSTODY_KEY` secret is set, the reader does them in the Farcaster app ([Handing writes to the Farcaster app](#handing-writes-to-the-farcaster-app)). Where a server endorses keys, they are signed in the reader's browser, with a key they approved in the Farcaster app, and go from the browser to Hypersnap ([Liking and recasting](#liking-and-recasting), [Writing a cast](#writing-a-cast)); a [scheduled cast](#scheduled-casts) is signed in the browser too, and kept by the Worker, which hands it to Hypersnap at its time. Until then its text and draft are in D1, which the operator can read, and a week after. The Worker's exchanges that aren't reads are [sign-in](#sign-in), the endorsement of a key, scheduled casts, [attachments](#attachments) and the [presence](#presence) beat: their endpoints take same-origin POSTs, and the session is an HMAC-signed, HttpOnly cookie. Every other endpoint accepts only `GET` and `HEAD`.
- **Credentials**: Farcaster and the public RPCs need no key. The key that signs session cookies lives in the Worker's `SESSION_SECRET` secret. The custody key of the account Allthing asks for readers' keys as, its own @allthingapp, lives in the Worker's `ALLTHING_CUSTODY_KEY` secret, set in Cloudflare only: it only endorses readers' keys, but it controls that whole account, and `/status` shows its address, never the key. Readers' keys never leave their browsers. KLIPY's app key lives in the Worker's `KLIPY_API_KEY` secret and goes only to signed-in browsers, which must call KLIPY themselves: it is in every request they make to KLIPY, public by KLIPY's design. The optional keyed Solana RPC URL lives in the Worker's `SOLANA_RPC_URL` secret; new wallet payloads omit its transport and parse diagnostics. Previously cached copies are checked at the public response boundary too, retaining their counts and cache lifetimes while removing opaque diagnostics. `/status` reports only its host. The Workers Builds token lives in Cloudflare, never in the repository.
- **Content Security Policy** (`web/_headers`): scripts are self-hosted, with `'wasm-unsafe-eval'` for WebAssembly only. The one exception is `static.cloudflareinsights.com`, for Cloudflare Web Analytics, which Cloudflare injects when it is switched on for the zone. It is cookieless, and turning it off in the dashboard removes the script. Its POST of page timings to `/cdn-cgi/rum`, handled by Cloudflare rather than the Worker, is the only non-GET request a page makes. Frames are limited to the four video providers. Images and media take `blob:` URLs, for the composer's previews of files not yet uploaded and the HLS player. `connect-src` allows any https origin, because HLS playlists are fetched from wherever a video is hosted (it also covers Farcaster's sign-in relay, which the browser polls, KLIPY's API, the Farcaster app's API and Hypersnap, which take a reader's key request and messages, and Cloudflare Images' descriptions of image sizes, which the front page's early cards read). There is no `unsafe-eval` and no framing of the site, and the only inline scripts are the early data request and the speculation rules in `web/index.html`, each allowed by its hash.
- **Attachments** are kept as the reader's browser sent them, since the Worker never reads them. The browser takes a JPEG's, PNG's or WebP's metadata out before it's sent (where it was taken, the camera; [Writing a cast](#writing-a-cast)), and a remuxed MP4's or MOV's (its `udta` and `meta`), but not a GIF's, a WebM's or another video's that can't be remuxed: that video's own data (where it was taken, if the phone wrote it) goes with it. They are public at their URL, as a cast's embeds are, under a random name, and only ever served as their declared type, with `nosniff` and a sandbox policy ([Attachments](#attachments)).
- **Votes** in [Allthing's poll](#allthings-poll) keep an HMAC of the poll and the network, keyed with `SESSION_SECRET`, never the address.
- **Links** in casts get `rel="noopener noreferrer nofollow ugc"`. Cast text is tokenized and rendered as text nodes, never as HTML.
- **Abuse**: a per-IP rate limit (`API_LIMITER`, 120 a minute), the caching above, and guards that refuse to send rather than queue. See [BUDGET.md](BUDGET.md).

## Testing

- **Unit tests**: `cargo test` covers the core against recorded Hypersnap responses, link shortening in the app, and the xtask's CSS minifier and fingerprinting.
- **Protocol test vectors**: `crates/allthing-core/tests/message_vectors.rs` checks the messages a reader signs (`allthing_core::message`) against known Farcaster messages, byte for byte by their BLAKE3 hash, with their Ed25519 signatures verified against their signers: Snapchain's own test vectors (two casts in `farcasterxyz/snapchain`'s `engine_tests.rs`, signed by its test key), the `reactionById` example in Snapchain's HTTP API reference (a like, by its hash), and five messages on mainnet as Hypersnap served them (`tests/fixtures/snapchain-messages.json`, each with its URL): a like, a recast, an unlike, a quote embedding another cast's id, and a deleted cast. These are what Allthing writes for a like, a recast, a quote and their undoing (`ReactionAdd`, `ReactionRemove`, `CastAdd` with a `CastId` embed, `CastRemove`). Apps differ in how they encode a cast (`@farcaster/core` writes empty mention lists that Snapchain's own encoder leaves out), and the network keeps either as signed; the quote is one encoded as Allthing and Snapchain encode it.
- **Lints**: `cargo xtask check` runs rustfmt and Clippy with `-D warnings` for the native and wasm32 targets, and the `cargo deny` license audit.
- **Tooling**: `cargo test --locked -p xtask` covers native build/check policy, metadata/CSP/release links, credit terms, attestation handling and the deployment wait (revision matching, local Git ancestry/fetching, transient HTTP errors, bounded stalled bodies and child cleanup). `npm run test:tools` retains the Node static-server oracles, actual SDK/browser interfaces and browser-specific fixture contracts. CI runs native checks in its check job and the remaining Node tests before browser fixtures.
- **SpacetimeDB module**: `cargo xtask module-check` runs in the isolated `spacetime/spacetimedb` crate with workspace `RUSTFLAGS` cleared: rustfmt, native and Wasm Clippy, unit tests, a release Wasm build and the license audit when `cargo-deny` is installed. CI installs it, so the license check remains required there. `spacetime/check.sh` only forwards to that native command.
- **Browser regressions**: `cargo xtask browser-fixtures` runs functional fixtures with two workers, then calibrated smoothness alone with one; both phases run and either failure fails the job. The underlying `npx playwright test '\.fixture\.spec\.ts$'` runner exercises deterministic browser tests against the local build, with API and media responses supplied by fixtures. CI runs these on pull requests and pushes to `main`; new deterministic suites should use the `.fixture.spec.ts` suffix. They exercise the code under review without depending on live data. Failure reports are uploaded for 7 days.
- **Static payloads**: CI also builds the `/Allthing` copy and runs `E2E_PAGES=1 npx playwright test e2e/static-body-limit.fixture.spec.ts e2e/static-metadata.fixture.spec.ts e2e/static-navigation.fixture.spec.ts e2e/static-follows.fixture.spec.ts e2e/preloaded-replies.fixture.spec.ts e2e/poll.fixture.spec.ts`. These fixtures exercise the browser Host's capped HTML streams, cleanup after read failures, complete uncapped JSON responses, and linked-page metadata filtering with inert fallback text and actual frame declarations, check that what the app opens itself (a cast's card, a search, a replies count, the time range) stays under `/Allthing`, that follows navigation works under that prefix, that a replies preview built in the browser, by the code a popover batch builds replies with, leaves out spam and mini apps, and that the copy has no poll.
- **Performance**: `e2e/perf.spec.ts` checks the budget in [PERFORMANCE.md](PERFORMANCE.md); CI runs it against production after each push to `main`, after `cargo xtask wait-for-deploy` has checked the intended version without warming Home.
- **Writes land, or are taken back**: `e2e/verified-writes.fixture.spec.ts`, at 1280 and 390 px, likes, recasts, quotes and their undoing with the reader's real WebCrypto key against a stand-in node (`e2e/helpers/node.ts`, which every spec that writes uses). The stand-in checks each message as Snapchain would (BLAKE3 of its data is its hash, its Ed25519 signature is by the key the reader approved, mainnet, the reader's fid, the time) and answers the read-backs from what it merged. It covers a write merged and shown; taken but never shown, which is undone after 15 s, with Retry; refused, with the node's reason; an unknown key, which offers the approval; a busy node, then success; a lost answer, the same message again and a duplicate, counted once; each undoing; and a quote shown at once, posted once shown, or gone with its draft back.
- **A reply in its thread**: `e2e/reply-in-thread.fixture.spec.ts`, at 1280 and 390 px: a reply at the top of its post's replies the moment Reply is pressed, before the node answers, as posting (faded, its actions inert), then posted, with its time linking to it, and once when the page lists it; a reply to a reply under it; the count on the post and in the feed; refused, or not shown in 15 s, gone with the count back and the composer open again with the draft and why, and Retry sending the same message.
- **Smoothness**: `e2e/smoothness.fixture.spec.ts`, one of the browser regressions, times a signed-in reader's taps, navigations, Back and presses at 390 px (touch, the CPU slowed 2×) and at 1280 px against fixture data: INP, long tasks, layout shift, blank frames, where Back puts the reader, and whether a press shows in its first frame ([PERFORMANCE.md](PERFORMANCE.md#smoothness)).
- **End to end**: `e2e/allthing.spec.ts` runs Playwright against `wrangler dev`, or against production with `E2E_BASE_URL`, using live data. Video playback runs against a small VP9/Opus HLS fixture (`e2e/fixtures/hls`), because Playwright's Chromium cannot decode H.264.
